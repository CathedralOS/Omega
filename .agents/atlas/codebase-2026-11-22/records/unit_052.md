## Five things a maintainer most needs to know

1. The parser decides most things by token spelling, not by a keyword kind: `at_contextual` compares text for any Identifier or Keyword token (cursor.rs:479-484), and clause words, `entry`, `invariant`, `_`, `true`, `false`, `Build`, `bind`, `Join`, `Slice`, `Trap`, `Abort` are all string compares (primary.rs:191-204, machine_bodies.rs:95, expressions.rs:13/43, references.rs:240/245, parse.rs:110-113).
2. Binding use inside a pattern arm is rewritten by name: `patterns/bindings.rs` replaces any one-member `Name` whose text equals a bound name with a member read or saved-subject read (bindings.rs:233-238, 425-437), and tracks shadowing by name (bindings.rs:85-89, 349). Four call sites apply this (blocks.rs:62, targets.rs:49, guards.rs:219/422/489/568).
3. Seven hand-written depth-counting token scanners exist for the same "find a top-level delimiter" job (listed under primary.rs item 6); they differ in which bracket kinds count and in what they do on an unmatched closer.
4. Stage 02 constant handling accepts early in several places and leaves the check to a later stage: `validate_const_definition` returns `Ok(())` for constants needing evaluation or proof (declaration_values.rs:258-265); `retain_scalar_carrier` ignores non-literal nodes (carrier.rs:110); `initializer_leaves.rs` accepts `Name`/scalar literals at nominal destinations without a leaf (:170-172, :232-236). Whether the later stage catches each is not traced.
5. `initializer_dependencies.rs` keeps every visited set as a `Vec` and checks `contains` linearly, and looks up declarations by filtering whole tables by symbol (:56-66, :260-270, :1393-1402), repeated six times; it matches every `ExpressionNode` and `Statement` variant explicitly with no wildcard in `expression_dependencies` and `machine`, so a new variant is a compile error there.
