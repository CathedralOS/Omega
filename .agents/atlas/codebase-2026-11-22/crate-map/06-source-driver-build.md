## 1. What the area does

The area is the Rust driver for source compilation (`source-rust/subsystems/compiler/source-to-psi/`, crate `source-compiler`) and the Rust "Build" subsystem (`source-rust/subsystems/compiler/build/`, 25 crates). The source driver takes parsed package sources and runs the numbered stages 00-07 (lexer, parser, resolver, typer, preparation, lowering, lowered-form checker, publication; those stage crates are other areas) to produce Psi or a verdict. The Build subsystem runs a project's authored Build (an Omega program) inside the interpreter: it assembles package and toolchain sources, admits the Build program, runs it with granted filesystem authority and accounting, decodes the returned settings and requests, records provider plans, and publishes finished products into an owned output directory. Input: captured package sources, grants and a target request (from the package manager and `omega` CLI). Output: an `EvaluatedBuild` and `ProductStage` handed to the compiler, a checked and published Psi artifact (`PublishedPsi`, `PublishedTargetProgram`), and installed Psi/native files with receipts.

## 3. How data flows through the area

1. The package manager or `omega` builds `PackageCompilationInputs` (`package-compilation`, `inputs/package.rs:63`) from captured roots and toolchain library.
2. `project_build::prepare` (`planning/source.rs:173`) calls `ImmutableSourceParseCheckpoint::prepare` and `assemble` (`package-compilation`, `source/assembly/mod.rs`), which load and parse sources through `source_compiler` parsing (stages 00-01 via `driver/parse_source_batch.rs`).
3. `prepare` calls `resolve` into `source_compiler`'s `BuildStageSource` / `TypedBuildInterval` (`compile_build.rs`), which runs 02-06 on the Build source and publishes the Build invocation (07).
4. `prepare_build_evaluation` (`build-execution`, `build_evaluation.rs:301`) admits the checked program (`evaluation-admission`, `build_admission.rs`), sets up filesystem scope (`filesystem-authority`, `package-compilation/build_execution/filesystem_scope`) and accounting (`evaluation-accounting`).
5. `project_build::interpret` (`project_build.rs:194`) starts `TerminalBuildHost` (`activation.rs:301`) and loops: `advance`, service host calls through `PlanningServices` (product queries, dependency preparation, provider requests); at a dependency wait `source_compiler` re-types and checks the continuation (`compile_build/continuation.rs`, `waits/mod.rs`) and `PreparedBuildExecution::resume` (`preparation.rs:296`) continues the interpreter.
6. On return, `ReturnedPlanningStage::complete` -> `complete_with_sources` (`build_evaluation.rs:242`) settles outputs and generated sources, decodes settings (`build-settings::extract`, `settings.rs:30`; `build_value/configuration.rs`) and yields `EvaluatedBuild` (`build-evaluation-result`) with the receipts (`evaluation-receipts`).
7. `PlannedProduct::product_stage` (`planning/product.rs:37`) builds a `ProductStage`; `ProductStage::source()` gives a `StageSource` back to `source_compiler` for `compile_for_target` / `review_package` / `check` / `inspect` (`source_to_psi.rs`), which run `compile_product` provider choices, `prepare_lower_and_check` (05-06) and publication (07), giving `PublishedTargetProgram`.
8. `ProductStage::program` and the `compiler` crate run the native stages; `product-publication` (`CompletedProduct`, `output_directory::acquire`) installs files and issues receipts. `ProductStage::package_review` produces `CheckedPackagePolicy` for review.

## 4. Where this area's map differs from what the documents say

- `build/README.md` lists directories `inputs`, `evaluation`, `settings`, `providers`, `publication` in its table; it does not list `planning/`, which holds the crate root's real modules (`planning/source.rs`, `product.rs`, `registered_tests.rs`, `package_review/`; about 40 percent of the `project-build` crate's lines by `crates.tsv`/file listing). The prose names Product planning (`planning/product.rs`) but not package review or registered tests.
- `build/README.md` says "The package manager starts a project Build with `project_build::prepare`". `prepare` is defined in `planning/source.rs:173` and re-exported at `project_build.rs:13`. Consistent, but the README's "crate root" link points at a file that only declares modules via `#[path]` (`project_build.rs:3-12`).
- `source-to-psi/README.md` and `source_to_psi.rs:1-2` describe the crate as the source driver that owns the numbered transformations. The code makes `source-compiler` depend on build crates (`build-invocation`, `build-scalar-evaluation`, `evaluation-*`, `build-time-values`, per `source-to-psi/Cargo.toml`), while `build/evaluation/README.md` presents Build execution as consuming the source compiler. The dependency runs both ways at crate level, resolved only because the leaf build crates do not depend on `source-compiler`.
- `source-compiler`'s `Cargo.toml` also owns 30 test, 10 example and 4 bench targets whose source files sit in the pipeline-stage and representation directories (`source-to-psi/Cargo.toml`, `[[test]]` entries). Neither the README nor the crate doc mentions this; a reader looking for stage tests inside each stage crate will not find their targets there.
- `AGENTS.md` says the native root entry and private callables use "the shared body driver" and describes `build/` as running authored planning stages; both match. `AGENTS.md` places stage-order authority in `source-rust/subsystems/compiler/source-to-psi/driver.rs`; `driver.rs` (108 lines) holds `publish_stage` and the `StageSource` glue, while most stage sequencing sits in `compile_product.rs` (`prepare_lower_and_check`) and `compile_build.rs`.
