## Repaired in this PR

**Receipt 3. The stage 03 field-range check judged the wrong field after an `[erased]` field.** `validate_structural_field_range_authority` paired a record or case constructor's initializers with the type's field declarations by position (`UV:2420`, `:2453`). Initializers cover only relevant fields, in declaration order. That is the operation contract in `field_initializers_match` (`UV:11476-11566`), and Psi wire validation enforces the same order. The declaration roster also lists `[erased]` fields, so one erased field shifted every later initializer onto the wrong declaration. The check then decided whether a range fact was required from the wrong field type: it skipped a bounded field's check, or it refused a valid unbounded one. A case of a mixed (common fields plus cases) type also skipped the check entirely, because only `Sum` shapes matched (`UV:2410-2419`).

The repair pairs each scalar initializer with the relevant declaration that has its field id, over a mixed type's common fields plus the case's own fields. It refuses an initializer or a result type it cannot match. The operation contract in `validate_function` runs first and already refuses those shapes, so a valid unit sees no new refusal.

Reproducer. The fixture is a record `{ [erased] ghost: u8, count: u8 in 0..=9 }` built with one initializer, for `count`. Before the repair, the removed `declarations.iter().zip(fields)` paired the `count` initializer with the erased declaration:

```
BEFORE pairs (declaration, initializer) = [(1, 2)]
assertion `left == right` failed: positional pairing checks the wrong declaration
  left: [(1, 2)]
 right: [(2, 2)]
```

After the repair, `field_range_pairing_tests` in `UV`'s `mod catalogs` pin the bounded declaration for that initializer, the mixed-type common and case pairing, and refusal of an initializer that has no relevant declaration.

## Build note

At the baseline, `optimization-unit-semantics` does not compile. #5393 added `Proposition::DeclarationIdentity`, but `proposition_structural_roots` (`UV:10634`) has no arm for it (E0004). The optimization-unit identity encoder has the same gap, which open PR [#5427](https://github.com/CathedralOS/Omega/pull/5427) repairs. This PR adds the stage 03 checker arm. It collects the roots of each clause value's scalar and input operands. Formals and applications refer to other clause values by index, so those two operand kinds name every place the proposition reads. The focused tests below ran with #5427's `identity.rs` change applied locally and not committed.
