## 47-216 `atomic_fences`
- Purpose: decide which `FenceOrdering` an `Atomic::fence` call uses, from the captured operand's live case evidence (comment 48-54). Reports an error if no single case is proved.
- Shape: `check` (61) loops every flow state and call; `contract` (84) finds the operator declaration whose symbol equals `call.target_symbol` (88-91) and asks `validation::exact_toolchain_atomic_fence_contract`; `ordering` (95) returns `Result<FenceOrdering, &'static str>`; `case_at_capture` (183) asks `crate::flow::place_case_has_value`.
- Inputs/outputs: reads `facts.flow.control.{states,calls,operands}`, `program.operators()`; pushes `Diagnostic::error("Atomic::fence requires one proof-static FenceOrdering case ...")` (72-74). No mutation of facts.
- Decides: keyed on identities. Declaration is matched by symbol (102); operand matched by expression handle, state symbol, statement index and normalized type identity (121-126). Candidate cases come from `contract.cases` (143); a case is a candidate when every captured value proves it by one of three routes (146-171): observation row case evidence, a structural zero-field constructor of that case, or the operand row's case evidence. Exactly one candidate is required (175-180: "no live ordering case is proved" / "ordering case proof is ambiguous").
- Cases by shape: `let [expression] = arguments.as_slice() else Err("expected exactly one ordering argument")` (109-111); exactly one operand (112-120). Rejects other shapes.
- Fail-open: `contract` returns `None` (88-93) when the call's target is not a fence operator, so `check` does `continue` (68-70): this is the intended filter (calls that are not fences are skipped), traced by reading: only declarations that `exact_toolchain_atomic_fence_contract` accepts are checked. Everything else in the module is `Err` (fail closed). One note: a call to a fence-named declaration that is NOT the exact toolchain one is skipped silently (inferred from 92).

## Five things a maintainer most needs to know about this unit

1. `checks.rs` is both the orchestrator and the home of about 12 inline checks. `check_checked_facts_recording` (12022) is the only entry (one caller, `checking.rs:1139`) and it MUTATES `facts` (crash plans, retained custodies, carry facts, proven indexes, qualifications) as well as collecting diagnostics; the header comment (1-37) does not list five of the checks that run (`runtime_indices`, `atomic_fences`, `stored_integer_calls`, `indexed_writes`, `zero_value_qualifications`).
