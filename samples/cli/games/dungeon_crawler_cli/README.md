# Dungeon Crawler CLI Sample

This sample explores Omega as a console program rather than a windowed game.

What it is trying to prove:

- an attached entry machine with an explicit mutable `Main` data argument can drive a stateful
  terminal application
- console input/output goes through the standard library `Console` boundary
- room entry is explicit and visible in the state graph
- level data can be hardcoded without hardcoding traversal logic
- the game loop can act like a render loop where each submitted line advances a frame
- user input drives explicit `transition` dispatch
- invalid input can loop back without hidden branches

## Runtime acceptance

The closed-stdin and help/exit routes have verified native execution on macOS
ARM64 and Windows x86_64. [build.omg](build.omg) declares four hosted entry
bindings; the other hosts still need their own execution evidence. Checking and
a zero exit status alone do not establish correct native output; see
[native realization](../../../../omega-rust/omega/compilation/driver/README.md#native-realization)
and the [compiler completion plan](../../../../wiki/drafts/reference/rust_compiler_completion.md).

The intended interactive path accepts commands at a live terminal. The closed-
stdin acceptance case instead reaches EOF at the first prompt and should exit
with status 0. Never run a stale image after a failed build.

Run the actual product command from the repository root (POSIX shell):

```sh
omega run samples/cli/games/dungeon_crawler_cli/main.omg </dev/null
printf 'help\nexit\n\n' | omega run samples/cli/games/dungeon_crawler_cli/main.omg
```

Both cases should exit 0 after the initial room and goodbye output; the second
also prints command help.

Verified on 2026-10-16 on macOS ARM64 through `omega run --both` with the
optimized Rust reference compiler (`CARGO_PROFILE_DEV_OPT_LEVEL=1`). Closed
stdin and scripted `help\nexit\n\n` each returned 0 natively and in the Terminal
interpreter with identical output. Both printed the authored opening room and
goodbye; the scripted route repeated command help. Compilation plus execution
took 18.42 seconds for EOF and 19.68 seconds for help/exit after package review.
These observations cover those two routes, not every gameplay path or another
host, and are not a controlled performance comparison.

Verified on 2026-10-16 on Windows x86_64 with the optimized Rust reference
compiler (`CARGO_PROFILE_DEV_OPT_LEVEL=1`). Closed stdin printed the authored
opening room and goodbye before exit 0 in 15.80 seconds. Scripted
`help\nexit\n\n` input repeated the command help and exited 0 in 20.91 seconds.
These times include compilation and execution; the preceding package refresh
took 38.67 seconds. Both routes used the public `omega run` command with native
EOF or a byte pipe as stdin. Other gameplay paths and hosts remain unverified
by this run.

The existing sample gate reads the standalone `Expected exit` and
`Expected output contains` lines in [main.omg](main.omg). Its closed-stdin
oracle requires the generated room description, not just exit 0: native lookup
previously lost the description while the process still exited successfully.

```sh
python3 tools/sample_native_gate.py --filter cli/games/dungeon_crawler_cli --jobs 1 --timeout 7200
```

The timeout is a runner budget, not a language limit; the current qualified
commands complete in under thirty seconds after package preparation. This gate does not replace the separate
`help`/`exit` input acceptance above.

Current state cycle:

- enter a room
- render the room through the CLI view
- read a user command
- classify the command into owned navigation data
- move if the command names an adjacent room
- render room details for `look` or `info`
- render command and exit help for `paths` or `help`
- otherwise render an invalid-command message and ask again
- complete back to parent control flow from the terminal game state

Sample layout:

- `main.omg`: process-level runner
- `game/`: submitted-input game loop and frame advancement
- `view/`: CLI rendering over dungeon snapshots
- `dungeon/`: dungeon state and domain mutation
- `generation/`: small deterministic dungeon generation
- `rooms/`, `inventory/`, `events/`, `combat/`, `player/`, `enemies/`,
  and `rewards/`: domain-owned models plus their behavior

The build declares the std dependency and binds `Main::main` explicitly for
Windows x64, Linux x64/ARM64 and macOS ARM64. Ordinary target defaults select
console and process-exit providers; the sample does not bind each provider
separately. Selection is not proof of native provider implementation or runtime
acceptance.

Build output:

- `build/`: ignored local phase artifacts and executable output generated by
  the compiler beside this sample's entrypoint
