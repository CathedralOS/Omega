# Source-checking CPU on published PR 788

The exact post-merge smoke passed. On the unchanged Dungeon EOF program, the
published compiler spends **24.63 process CPU seconds / 14.82 elapsed seconds**
inside its source-check requests on cold retained caches. That is **56.08% of
compiler process CPU**, across four profiles. Large parts already run on workers.
The coordinating threads account for 9.67 CPU seconds (39.26% of checking CPU);
that ratio is an observation, not the compiler's serial fraction.

With the same private retained caches warm, these requests cost just
**0.031-0.047 CPU seconds**. Source-checking improvements primarily affect cache
misses on this workload. No optimization is implemented by this iteration.

## Measurement boundary

Temporary callbacks attach process and current-thread CPU snapshots to 96
existing coarse pass names. Two small admission regions receive temporary
scopes. All platform FFI stays in host `artifacts`; Psi's unsafe prohibition
and Cargo dependencies are unchanged. The ordinary fine-grained wall profiler
is disabled in every observation. No semantic decision reads the measurements.

The denominator is the three `CheckRequest::check` windows named `05` per
compilation. Actual wall coordinates and thread IDs construct an interval
forest; sibling windows must be disjoint. Subtract immediate children only.
Exclusive process CPU, thread CPU and wall time close exactly to the root
totals in every profile. This avoids adding inclusive parent and child timers.
All selected windows within each request run on that request's coordinating
thread; process snapshots include its workers as well.

Cold traces additionally contain 86 selected helper windows outside those
requests. Their ten disjoint outer windows cover 0.063-0.141 CPU seconds
(median 0.070), and are reported separately in [summary.json](summary.json).
They do not overlap the check requests. Warm traces have no such windows.
Uninstrumented frontend, build evaluation, Terminal production and emission
remain outside this source-checking denominator.

Windows API values use 100ns units, but observed CPU changes are quantized in
15.625ms steps. Zero CPU ticks do not prove zero work. Small rows and the warm
checking observations should not be interpreted at microsecond precision.
The CPU method and primary references are in [research.md](research.md).

## Cold breakdown

Four probe-on compilations: 33.04-34.45 seconds elapsed, 42.95-44.31 process CPU
seconds. Source checks: 23.94-24.91 process CPU seconds, 13.83-15.02 elapsed
seconds, 8.95-9.77 coordinating-thread CPU seconds.

The following are mutually disjoint leaf buckets, aggregated across all three
requests. Entries are medians; the raw forest retains every observation and
residual, and medians are not an additive partition.

| Owner | Process CPU seconds | CPU range | Elapsed seconds | Coordinating-thread CPU seconds |
|---|---:|---:|---:|---:|
| Flow-fact construction | 5.34 | 5.23-5.44 | 2.14 | 0.10 |
| Call/write contracts and exit obligations | 4.88 | 4.59-5.20 | 3.08 | 2.62 |
| Per-machine validation | 4.70 | 4.53-5.03 | 2.24 | 0.00 at clock resolution |
| Unit-effect planning | 1.59 | 1.44-1.63 | 1.59 | 1.59 |
| Permission-event preparation | 1.06 | 0.97-1.13 | 1.07 | 1.06 |

Higher-level inclusive owners explain where the remaining work sits:

| Source-check owner | Process CPU seconds | Elapsed seconds |
|---|---:|---:|
| Typed preparation / specialization | 1.35 | 1.35 |
| Typed-program validation and proof-plan preparation | 6.07 | 2.86 |
| Building checked facts, including flow and permissions | 8.63 | 4.15 |
| Checking those facts, including call/exit obligations | 5.72 | 3.46 |
| Execution and identity finalization | 2.24 | 2.27 |
| Selection/custody/type/boundary finalization | 0.45 | 0.48 |

These parent rows overlap the first table and must not be summed with it.
The remaining measured residuals include immutable-program setup, mutation
summary prewarming, metadata transfer, adoption/destruction and probe bookkeeping;
this experiment does not assign all of a residual to one operation.

Source agrees with the CPU observations: machine validation uses a dedicated
Rayon pool in `checking/src/program_validation.rs`; flow groups use it in
`src/flow/builder.rs`; call/write obligations use it in `src/checks/contracts.rs`.
That last owner then gathers the results and checks exit obligations on its
coordinating thread. Process CPU exceeding elapsed time demonstrates concurrent
execution in these intervals. Neither thread accounting nor a source loop alone
proves which work is safely parallelizable.

## All observations and observer limits

Schedule was fixed before execution: cold off/on/on/off/on/on; warm profiles
reuse cold 1 and cold 5 respectively; one fresh-cache BOTH control. Each cold
private retained cache starts with zero files. A completed cold cache contains
one retained entry of 245,962,076-245,963,098 bytes. Warm trials reuse their own entry and use
new output directories. OS file pages are not flushed; cold means an empty
compiler retained cache, not cold disk or cold CPU caches.

| Observation | CPU probes | Compiler elapsed seconds | Compiler process CPU seconds | Recorded check CPU seconds |
|---|---|---:|---:|---:|
| cold 0 | off | 35.454 | 46.734 | unrecorded |
| cold 1 | on | 34.439 | 44.313 | 24.906 |
| cold 2 | on | 33.039 | 43.406 | 24.500 |
| cold 3 | off | 34.984 | 44.391 | unrecorded |
| cold 4 | on | 33.942 | 42.953 | 23.938 |
| cold 5 | on | 34.450 | 44.266 | 24.766 |
| warm from cold 1 | on | 15.976 | 15.172 | 0.047 |
| warm from cold 5 | on | 13.425 | 13.219 | 0.031 |
| native/Terminal comparison | off | 32.938 | 42.859 | unrecorded |

The same-binary probe-off controls are slower than the probe-on observations;
that does not establish negative observer overhead or prove the observer is
free. Endpoint system accounting reports other work consuming 34.5-41.1% of
total host CPU capacity in the profiled cold runs. Two controls on this busy
shared host cannot estimate a precise overhead correction. No observation is
dropped, trimmed or retried, and no timing speedup is claimed. Process CPU
excludes child processes; native runtime is measured and checked separately.

Warm checking is negligible in these two observations, yet full warm compilation
still takes 13.43-15.98 seconds. A cold-only checker improvement cannot promise
the same benefit on that retained route.

## Decision and next question

Retain this attribution record and remove all diagnostic compiler changes.
The old single opaque CPU figure hid both real worker activity and a warm route
that already reuses its checked result.

The next useful cold-checking question is **how much of the 3.08-second
call/exit-contract interval belongs to the sequential exit tail, and what work
does that tail repeat?** Its 2.62 coordinating-thread CPU seconds make it worth
splitting worker call/write work from result adoption, domain checks and exit
guarantees. The present measurements do not prove duplicate judgments or
authorize deleting obligations, caching across changed fact contexts, or
parallelizing mutable proof state. Unit-effect planning (1.59 seconds) and
permission preparation (1.07 seconds) are the next visible coordinator-heavy
owners. No additional optimization or experiment was appended to this bounded run.

## Replay and retained evidence

The evidence and scripts are hashed in [manifest.json](manifest.json).
Compressed case streams and status/CPU records live under [raw](raw/).
[summary.json](summary.json) retains every bucket's range, per-trial values,
counts, process/thread CPU and residuals. The manifests, locks, producer and
accepted current source distinguish this iteration from all old producers.
`validate.py` verifies the hashes, original streams, identities, every CPU
forest, the source manifest, exact native/Terminal stdout agreement and smoke.

To analyze the archived observations from this repository:

```powershell
python wiki/drafts/measurements/proof_parallelism_2026_10_28/source_checking_cpu/analyze.py wiki/drafts/measurements/proof_parallelism_2026_10_28/source_checking_cpu/raw
```

For fresh measurements, use an isolated detached worktree at the recorded base.
Apply `diagnostic.patch` (or copy `prepare.py` into ignored
`build/proof-profile/prepare_check_cpu.py` and run it on a clean worktree).
Build `omega` optimized under one `tools/build_slot.py` hold, using a guarded
short Windows path and target directory `build/proof-profile/compiler`.
Run the focused tests for `phase-profile` and `artifacts::compile_timings`.
Freeze the successful producer with `freeze.py source-checking-cpu`, retaining
its normal updater-generated lock. Record fresh executable/lock hashes.
`restore.py` verifies exact patch replay and restores only the owned source files;
`run.py` then consumes the frozen producer and the unchanged program/library.
The preparer creates the diagnostic directory and the runner refuses existing
case/cache directories; use a fresh ignored evidence root for a replay.
The Python runner's `--self-check` verifies partition closure and rejects
partially overlapping sibling windows. `analyze.py` rechecks outside coverage.

Skipped: full corpus, other hosts, interactive gameplay and any new optimization.
This is source-bound attribution on one fixed program, with coarse clocks and
shared-host timing variation.
