# Function allocation: measure pressure distribution before partitioning recovery

Read-only investigation at `bb3f3c457e7682ad92ef97fca02f89790d6260b6`, 2026-10-29. No builds, executions, source/config changes, or Git mutations. This is a next-experiment diagnosis, not semantic approval of the custody change.

**Recommendation: one diagnostic that attributes allocation time to the existing function ordinal and exact `MachineId`, with global recovery/sealing time separate.** Plain home placement already has a usable function boundary, but it is a small part of this trace. The heavy spill path has function-local data and whole-plan custody: it is not currently an independently mergeable function-allocation API. Do not introduce threads until the timing distribution justifies changing that owner.

## Actual owners and identities

All following paths are under `omega-rust/omega/compilation/` unless stated otherwise.

* `native-production/src/pipeline.rs:67–104`: `emit_target` calls `stage_register_allocation(selected)` once for the entire target selected plan. Only after it returns does the path produce the post-allocation machine, frame, encoding, layout, fixed-frame realization and object. Its caller must keep this single admitted output boundary.
* `pipeline/05_selected-instructions-to-register-homes/src/register_allocation.rs:61–139`: allocation preserves the selected-lowering/pre-allocation completion or declared recovery route. The direct route retains `FunctionHomeReuse` through runtime recovery; a function partition cannot silently replace these routes with a fresh identity route.
* `assignment/home_assignment/compute/mod.rs:19–163` and `compute/placement.rs:18`: `compute_function(index, legality, ranges, physical, pressure)` reads only its function's rows plus the immutable physical model. `FunctionHomeReuse` already owns one cached row per ordinal and reuses exact Arc storage or equal content under the same environment identity. `compute_terminal_register_homes` assembles rows in source order and checks root identities, target infrastructure and machine agreement. `home_assignment/receipt.rs` then hashes the whole ordered plan. These functions show a genuine computation partition; there is no allocation-global register cursor here.
* `representations/selected-instructions/src/selected_instructions/control_flow.rs:9` owns each function's registers, blocks, local slots, calls, memory accesses, entry and boundary settlements. `identity.rs:1–8` supplies local scalar IDs. Stage 04 `rewrites/runtime_spill.rs:435–479` takes the next register/instruction ID from **that function**, with overflow checks and terminators included. `runtime_spill/slot.rs:244` names the private spill slot `Spill { register: victim }` within the function and proves reaching-writer/reload windows against that function. Machine/provenance identities and target/PSI/fuel identities stay the existing exact coordinates; never renumber local rows globally or confuse equal local IDs in different machines.
* `selected_instructions/functions.rs:56,208–245`: function pages and entries are Arc-backed COW; `mutate_preserving_register_prefix` detaches the chosen entry and exposes only slots, register tail, settlements and blocks, retaining static contracts and verified register prefixes. Stage 04 `rewrites/runtime_spill/rewrite.rs:103–151` clones the selected plan shallowly and edits that single function. COW makes data isolation possible; it does **not** authorize merging separately sealed plans.
* Stage 04 `analyses/mod.rs:103–319`: `UnsealedRecoveryFacts` already holds per-function Arc liveness/ranges/legality rows. It detects changed function storage, recomputes each changed function, then `seal` rematerializes full liveness where needed and binds ordered facts to the **final whole selected identity**, optimization unit, fuel schedule, availability and environment. Keep the liveness/ABI entry pins, call clobbers and fixed-use facts intact. There is no callee allocation read in `compute_function`; call constraints are already inputs, not permission to omit them.
* `assignment/runtime_spill/recovery.rs:1128–1500`: one `current` rewrite and `analysis_source` advance sequentially; rosters and batch indices are keyed by function. `probe_all` stops on the first function that fails; its pressure vector describes that attempted placement, not a complete simultaneous list of all pressured functions. Each individual rewrite is admitted against the current plan, and only fresh successful placement can finish a batch. Do not parallelize stale failures (the rejected cap32 experiment already tested that distinct mechanism).
* Stage 04 `rewrites/mod.rs:519–548` seals each transformation with exact **whole-plan** source and transformed hashes plus optimization-unit/fuel identities. `publish_recovery` at `recovery.rs:1083` seals final analyses, assigns homes and projects the ordered transformation ledger. Stage 05 `assignment/post_allocation_manifest/reconstruction.rs:80–150` joins exact ranges/legality/homes/environment/availability identities and rejects unresolved transitions. `output/retained.rs:17–48` retains the produced facts under declared selections. Independent branches from source S produce S→A and S→B; neither receipt proves A→AB. Copying function B into A and concatenating these receipts would not preserve that provenance.

Thus **global identity generation does not forbid independent computation**, but the existing whole-plan rewrite and publication contracts forbid the naive minimal merge. A future function recovery owner would need an explicit checked function transformation/composition operation, preserving the original function contracts and current policy, followed by coordinator-owned deterministic whole-plan settlement. It must not synthesize replacement receipt hashes, discard transformations, or rerun every admitted rewrite serially merely to recreate custody. That is an owner-boundary change, not a scheduling wrapper, and is not justified yet.

Keep downstream dependencies after the join. `backend/machine-emission/src/function_realization/frame.rs:40–77` derives callee-save requirements, storage, frame layout and frame protocol from current allocation and the post-allocation machine; no worker should publish frame demand early. `backend/runtime/task-plans/src/task_plans/stack_composition/mod.rs:1–22` explicitly owns whole-call-graph WCSU, checked callee edges and unresolved-call evidence. Function-local spills can change frame bytes even when calls remain unchanged: preserve exact composition and all downstream checks. This research did not establish an independent per-function WCSU publication API.

The selected digest TLS is scratch (`selected_instructions/plan_identity.rs:398`), not a thread-local arena lookup. The effect catalog uses a synchronized immutable canonical cache (`effects/catalog.rs:1197–1229`). Neither observation proves the complete staged owner is `Send`; any later experiment must let Rust check the concrete borrowed inputs/owned outputs, preserve arena generations and compiler-worker stack/TLS policy, and account for target-level queue nesting. Do not add unsafe `Send`, move the generic application owner, or start another generic pool.

## Smallest decisive diagnostic and stop rule

Add **diagnostic-only attribution**, not parallel allocation. Accumulate one summary row per original ordinal plus exact machine identity, emitted once after the target allocation returns (also preserve the original error on early exit). Record:

1. Time and attempts for `compute_function` in `home_assignment/compute/placement.rs`; count reuse hits separately in `FunctionHomeReuse` so cheap reused rows are not charged as placement.
2. Per-function inclusive split/rematerialization/crossing/bounded-spill attempt time at the existing recovery calls; successful rewrites and declined attempts separately. For spill detail, attribute existing derive/mutate/seal scopes in Stage 04 `runtime_spill/rewrite.rs` using its existing `function_index` argument. Do not sum nested detail into inclusive rewrite time again.
3. Per-function liveness, ranges and legality time at the existing indexed calls in Stage 04 `UnsealedRecoveryFacts::reanalyze_changed_functions`; include final full-liveness rematerialization if material. Keep changed-row discovery, whole-plan hashing, final receipt/manifest work, and uncategorized allocation time **global**, not charged to whichever function happened to trigger the batch.

Include initial/final register/block/instruction/slot counts for context; no per-victim formatted logging or new scans in the hot loop. `psi/foundation/phase-profile/src/lib.rs:59` requires static scope names, so do not leak dynamically formatted names to encode ordinals. A small diagnostic-local table with one final ordered print is sufficient; no production telemetry framework is needed.

Use the same frozen stack32 source/Build, generic optimized producer, warm private cache, target and guards as the current custody record. First prove unchanged choices, spill/split counts, exact images, native exits, malformed/reject/lookup and partial-target behavior. Compare uninstrumented and instrumented whole-run timing to bound measurement perturbation; this read-only task executes none of these steps.

Let independently attributable function totals be `F_i`, their sum `P`, and largest `L`; global serial work is excluded. Even with unlimited workers, saving is bounded above by `P - L`. With two workers it is bounded by `P - max(L, P/2)`, before thread overhead, merge costs or cache/memory contention. **Stop this direction if that bound is materially below 20% of contemporaneous complete-process wall, or only one function dominates.** If the bound looks large only because of noisy/perturbed timings, repeat the attribution before changing ownership. Do not multiply historical victim counts by average spill time or combine the older clean denominator with this busy profile.

If sufficient headroom survives, the next design question is specifically function-scoped admitted recovery composition using existing COW function owners, preserving canonical result/error order and exact final validation. Parallelizing only `compute_function` or the ~43 ms analysis detail is a smaller experiment with a correspondingly small maximum opportunity; it does not meet the requested substantial-win case on this capture. No threshold or worker count is proposed from counts alone.

## Primary precedent, applicability and searches

Read `wiki/drafts/reference/compiler_parallelism.md` first, especially its pinned Go preparation/queue section and Omega ownership map. No broad online search was repeated. The new question was whether function backend independence requires preparation of shared mutable metadata. Directly reopened and read the implementation at **Go commit `430d19f07a57ee5ed4e3b1a04b0ab54dd5a24487`**: [`src/cmd/compile/internal/gc/compile.go`](https://github.com/golang/go/blob/430d19f07a57ee5ed4e3b1a04b0ab54dd5a24487/src/cmd/compile/internal/gc/compile.go), [raw source](https://raw.githubusercontent.com/golang/go/430d19f07a57ee5ed4e3b1a04b0ab54dd5a24487/src/cmd/compile/internal/gc/compile.go). `prepareFunc` initializes symbols and parameter sizes before concurrency. `compileFunctions` runs prepared functions under bounded workers, orders larger functions early, joins before `PostCompile`, and disables unsafe concurrent size computation. This supports preparing shared facts before independent backend work; it says nothing about Omega receipt composition or expected speedup. No LLVM lookup was needed after the local custody blocker and diagnostic were concrete.

Rejected unchanged leads remain rejected: slot-private/slot-layout/buffer-vector changes, generation-map container, cap32 stale-failure batching, parser workers, PGO/LTO and whole-graph decode splitting. This note proposes none of those experiments.
