## Summary

Counts: **Enforced 55**, **Refused wholesale 22**, **Not found 1**, **Unclear 5**, **Not looked up 1**. That is 84 rules. I skipped nine rows as the old code's bookkeeping or as leniencies, not rules: R21 (an overwritten assignment was left unchecked; data clauses now get invariant windows instead, `S06/README.md:509-546`), R52 (place equality by rendered label), R59 (acceptance views that could not reject), R65 (hashes rebuilt from a record's own fields), R66 (nominal-use commitment bookkeeping), R72 (declaration-call handle checks, covered by R64), R76 (compiler coverage), R86 (cleanup shape lists) and R90 (the unproduced `lowered-psi` form).

Three things stand out.

The range checker's rules all have a successor, in a different shape. The bracketed range type (`T [lo..=hi]`) is retired at the parser (`S01/types/references.rs:268`), so "a value must fit the range of the type it flows into" is now a `requires`, `ensures` or data `requires` clause. Stage 05 writes each as an obligation and stage 06 accepts it only with a certificate the kernel accepted (`S06/src/lib.rs:2575-2630`). There is no interval verdict to fall back on. Facts belong to values, so the old per-placement copies are gone: one function compares a supplied type with a receiving type for all six placements (`S05/src/read/rejections.rs:61-152`).

The mathematical declarations elaborator has no successor. No code under `source-to-psi/` calls the mathematical kernel's `check_signature`, `infer_type` or `infer_sort`; only `K/bounded` does. Stage 05 reads one narrow form: a closed, non-recursive, transparent predicate over builtin scalars whose result is `core::Strict<0>` (`S05/src/read/mathematics.rs:251-332`). Every binder, universe level, arrow type, assumed (`boundary let`) declaration, proposition declaration, indexed `data` family and erased data value is refused by name. That accounts for 19 of the 22 wholesale refusals, and nothing is silently accepted in their place.

The one rule with no counterpart is float arithmetic ranges (R17). The kernel has no rule that bounds a float sum, product or quotient, so an obligation that needs one stays unproved. That refuses programs the old compiler accepted; I found nothing it accepts without proof.

The Unclear items matter more than the Not found one. Two of them repeat a pattern the synthesis lists as an old defect: an operator expression with no recorded selection is completed as builtin with no check (`S05/src/read/source_operators.rs:447-484`), and a certificate the kernel's mathematical core declined to re-derive is still accepted, with a `Refused` marker that no production code reads (`K/bounded/proof.rs:238-262`).

## Unclear and not looked up

Unclear:

- **R10. `a - b` under `a > b` is at least 1.** The prover proves an unsigned `a - b` safe from `b <= a` (`S06/README.md:947-953`; test `S06/src/tests.rs:1040`). I did not confirm that it derives the lower bound 1 for the difference.
- **R61. A constant recipe closes under the target; two endpoint recipes agree.** A pending target constant becomes a deferred scalar application (`S05/src/read/constant_values.rs:148-181`) with completion conditions that the execution inputs check (`psi/execution-inputs/scalar-applications/completion.rs`). I did not find the endpoint-agreement check.
- **R67. Content claims.** Claim transport is reconstructed from the operations and compared (`S06/src/minted.rs:768`; `SEM/plain_affine/claims.rs:1-4`; test `S06/src/tests/call_claims.rs:94`). I did not trace the frontier rule for content transformations (`SEM/content_transformations.rs`).
- **R68 and R78. Builtin meaning only where resolution chose it.** On the lowered form a user operator is a call and a primitive is an operation, so the checker cannot confuse them. The risk is upstream. `complete_operator` checks every recorded `Operator` selection, but when an expression has no such occurrence it returns `Ok(())` (`S05/src/read/source_operators.rs:447-484`). The later capture pass checks that every recorded occurrence was answered (`S05/src/selection_questions.rs:1129-1140`), not that every operator expression has one. If typing can leave an operator unrecorded, this repeats the old "status `Missing` counts as builtin" defect. Cross-check G08 raised the same point.

Two findings that belong to no single row but bear on R37 and R48:

- **A certificate the mathematical core declined is still accepted.** `re_decide_in_mathematical_core` maps `Unsupported(family)` to `MathematicalCoreDecision::Refused(family)` and returns `Ok` (`K/bounded/proof.rs:238-262`). No code outside tests reads that field (searched all of `source-rust` for `mathematical_core` and `MathematicalCoreDecision`). The bounded kernel's own rule check still ran, so this is weaker than the old "accepted without evidence". `S06/README.md:982-1001` documents three such trusted rules; the code path covers any unsupported family.
- **No gate on trusted rules.** `AcceptedProofRule::foundation()` classifies each rule as constructive, trusted admission or classical "so consumers can audit" (`K/bounded/classicality.rs:1-50`). Nothing outside that file calls it. The old elaborator compared each theorem's assumptions with an audited roster; I found no equivalent comparison for certificates.

Not looked up:

- **R75. Allowed combinations of a unit call plan** (completion, route, result, transfers, x86 descriptor-table entry limits). This sits in calling plans and the native compiler, outside the stages the brief names.
