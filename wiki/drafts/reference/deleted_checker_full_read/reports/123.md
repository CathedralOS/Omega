## What this code is for
This file is the coordinator of whole-program validation in the old tree-based checker. `validate` (F:4069) runs checks in order: conformance-application and boundary-completion declarations, a declaration prologue of about 45 validators (F:301-587), static-argument and static-machine-binding checks, then a per-machine, per-state, per-statement walk that threads an interval/fact `ValueEnvironment` through statements and dispatches to per-statement-kind modules (assignment, call, expression, local data, transition, assembly fact; F:3736-3831). A second phase, `judge_machines` / `judge_contract_entailment` (F:4669-4818), checks each machine's `ensures` contracts and loan handbacks, optionally reusing prior judgments through a hash-keyed `DependencyBodyIndex` (F:650-1461). The file also hosts the rayon pool (F:4985), the `completion_results` check that every normal completion supplies the declared return value (F:52-158), unreachable-branch warnings (F:3402-3574), cleanup-machine normal-completion checks (F:4907-4972), and the post-ownership effect admission entry `admit_prepared_program_effects` (F:4840). Almost all actual rules live in other modules called from here (arithmetic_domains, expression_types, calls, contract_entailment, etc.); this file decides order, scoping, and diagnostic span attachment. The result is a `ProgramValidationFacts` bundle (F:3873) of decisions (integer-range obligations, trap-free expressions, expression intervals, etc.) handed to later stages.

## Mechanisms
- Parallel prologue (F:589-648): validators are `Box<dyn Fn>`; `run` tries `run_apart` on the rayon pool when no diagnostics exist yet and at least 2 threads. If any validator emitted a diagnostic, or any obligation of one validator equals one from an earlier validator (`own.contains(earlier)`, F:632-641), it discards the parallel result and reruns sequentially so diagnostic order and obligation dedup match the sequential order. Cost: validators run twice on failure.
- Per-machine parallel validation (F:4513-4521): `par_iter().map_init` over machines; each machine gets its own `bound_lookup` scratch; results merged in order. 256 MiB stack per worker (F:4983).
- Statement walk with ValueEnvironment (F:4277-4490): per state, starts from `requires_value_environment` for state 0 and `incoming_guard_environments` for later states (found by linear scan on symbol, F:4307); walks `finite_execution_order`; statements not in the finite order are walked afterwards with the environment cleared at each one (F:4325-4329). Before each statement, environment entries are invalidated for paths the statement may write (`invalidate_call_paths` with `value_written`) or all unknowns (`invalidate_unknown_writes`) when write set is not known (F:4390-4398). After assignments, the environment records the interval for the target path (F:2032-2054).
- Interval arithmetic for atomic fetch ops (F:1860-1910): resident interval plus operand interval via `Interval::add`/`subtract`/`bitwise_binary`; unknown operators give UNBOUNDED.
- Narrowing on guards (F:3260-3283): positive branch environment via `guard_narrowed_environment`; fall-through via `fall_through_narrowed_environment`, stored back into the live environment if the transition has a target and no continuation.
- Dependency body reuse (F:650-1461): FNV-1a hash of the machine's authored source text per statement (F:1241-1242) and of contract fact text (F:1325); `dependency_context` hash of callee identities, callee body hashes, and producer package digests (F:1158-1214); specialization context added (F:1033-1123). Reuse requires equal hash, equal context, equal callees' priors, equal ensures count (F:860-887). Machines with complete private uses, and all their transitive callers, are excluded via worklist (F:1125-1156). Prior judgments sharing an identity but disagreeing are dropped (F:994-1026). Serves incremental/dependency-package checking. No explicit budget.
- Two-phase error recovery (F:4556-4570): on errors, exact-overflow diagnostics are deferred; if non-overflow errors remain, entailment judging is also run to collect more diagnostics, then overflow diagnostics appended.
- Post-pass dedup of decisions (F:4576-4612): trapping decisions combined with AND per expression; exact integer casts merged by widening min/max.
- Cleanup-closure DFS (F:4907-4972): worklist with a `visited: Vec` (linear contains), no budget.

## Surprises
- No proof-kernel use in this file: every verdict is either a diagnostic list emptiness check (`finish_diagnostics`, F:4820) or a delegated call. The only reference to "proving" is `completed_value_fits_integer_interval` (F:2256) and `entailment_covers_all_exits` (F:4741), both in `contract_entailment`, outside this slice. Acceptance is "no error diagnostics produced".
- The final verdict has a side effect: `finish_diagnostics` prints warnings to stderr with `eprintln!` (F:4825), so the checker writes to stderr during validation, including from helper entries (`validate_checked_operator_realization_contract`).
- Incremental reuse of entailment verdicts is keyed on a 64-bit FNV hash of source text and name strings (F:1216-1327): a prior proof is trusted for a body whose text and callee text hash match. Whitespace or comment changes inside a statement span change the hash (text is hashed verbatim); a change in a non-hashed part (e.g. generic arguments not in text, trait impl bodies reached by dynamic dispatch) is covered only if `dependency_context` hashes it.
- The statement walk is order dependent: environment facts flow along `finite_execution_order`; statements not in it are validated with an empty environment (F:4325-4329).
- A diagnostic's span is attached only if none is present, in five separate places (see repetition).
- `validate_program` (F:3948) passes `OpaquePropertyValidation::Required(&[])` (empty receipts) and `QuotientRequestAdmission::AtValidation`; `prepare_specialized_program` passes `PendingBuildSelection`-capable and `AfterCheckedFacts` / `AfterOwnership`. So the checker has two modes with different effect-admission timing, and several validators produce empty results in the second mode until `admit_prepared_program_effects` is run.
- `Report::transition` uses `TransitionGuardNode::When(guard) else` to check the target even with no guard (F:3460-3463), but `matches` (F:3507) recurses into match arms inside targets with the arm's selected environment; unreachable-branch is a warning so such code is accepted.
- `exact arithmetic ... may overflow` errors are held back and appended after entailment diagnostics (F:4556-4569), so error order depends on message text matching.
- Several `unreachable!("dispatched ...")` panics (F:1476, 1547, 2302, 2395, 2658, 3184) assume the dispatcher matched the variant; a mismatch would panic rather than refuse.
- `validate_machine` closure holds an unused `incoming_environments` lazily computed per machine for states after the first, scanning a Vec linearly for each state (F:4294-4311).
- `.expect("machine validation worker pool")` on pool build (F:4992) panics if the pool cannot be created.
- `completion_results::validate` treats `Expression` as last statement completing normally even when it is e.g. a non-value call (F:101); the value-type check elsewhere is what catches it.
