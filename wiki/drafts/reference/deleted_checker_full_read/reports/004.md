## What this code is for

This slice is not the checker that decides whether a program's proofs hold. It is the "review evidence" package: after a program has been checked, it turns the checked program into a portable record of what a package publishes (callable surfaces, contracts, calling plans, callback layouts), called a `PackagePolicyBaseline` (`package_policy.rs:45-115`). Every function either returns a record or returns a refusal diagnostic, so it is a second gate on publication: a package whose contracts it cannot express is refused even though the checker admitted it.

The first third (`callables/`, `calling/`) projects a machine's published surface (service reach, suspension, blocking, synchronous-invocation ceilings) and the native calling plan of a boundary requirement (ABI key, native parameters, callbacks, opaque representations, register state). The larger part (`contracts/`) walks each `requires`/`ensures` fact of a callable or trait requirement and rewrites it into a name-free expression tree (`PackageReviewContractExpression`): parameters become ordinals, declarations become nominal identities, members become field identities.

Its working method is the same everywhere: take a fact table that an earlier stage wrote (`facts.proof.*`, `facts.semantic.*`, authored-selection rows, provider realizations), find the rows that match the thing being projected, require exactly one, and require it to equal something recomputed or something in a second copy of the program called "custody". The input type `PackageReviewInput` pairs a "supplied candidate" program with the compiler-issued original (`input.rs:1-15`, `input.rs:79-97`), and many checks are "candidate equals original".

## Rules enforced

"Own judgment" means the code compares values itself. Where it compares rows written by another stage, the table is named. The recurring diagnostic prefixes are: `calling policy rejects {reason}` (`calling.rs:13`), `calling opaque policy cannot retain {reason}` (`calling/opaque.rs:147`), `package policy rejects {reason}` (`package_policy.rs:117`), `reviewed {kind} \`{name}\` {detail}` (`contracts/facts.rs:43-48`), and `reviewed callable \`{subject}\` has no exact checked {kind} row` / `has duplicate checked {kind} rows` (`semantics/facts.rs:6-20`, outside the slice).

## Mechanisms

**Join and count.** The dominant mechanism is: filter a table by symbols and handles, collect the matches, and require exactly one (`let [x] = matches.as_slice() else { refuse }`). It appears about 45 times, for example `calling/application.rs:23-41`, `contracts/evidence.rs:29-48`, `contracts/expressions/calls.rs:124-140`, `contracts/expressions/members.rs:106-115`, `contracts/expressions/static_arguments.rs:260-269`. Every lookup is a linear scan of the whole table; there is no index. Its limit is that it shows a row exists and is unique, not that the row is right.

**Replay and compare.** For several facts the code recomputes the value and requires equality with the recorded one: service reach against an independent inference plan (`callables/reach_dependency.rs:35-74`), the calling application (`calling/application.rs:77-85`), opaque representation selections (`calling/opaque.rs:40`, `:124-145`), the closed conformance application (`contracts/expressions/static_arguments/conformance.rs:105-111`), evidence parameters and instantiations (`contracts/expressions/evidence.rs:53-58`, `:92-103`), and a constant's encoding against its type (`contracts/expressions/static_arguments/const_values.rs:33-42`). The recomputation is always done by another crate; this code only compares.

**Candidate and custody.** `PackageReviewInput` carries two programs: the supplied candidate and the original (`input.rs:27-48`, `:79-97`). `SourceDeclarationInput::original()` switches a query to the original (`input.rs:68-76`). Operator selections, layout queries and authored targets are compared between the two (`contracts/expressions/operators.rs:111-136`, `contracts/expressions/layout_queries.rs:26-93`, `input.rs:157-182`). `package_policy.rs:29-43` builds two separate `validation::CheckingContext`s so the two programs do not share memoized query state.

**Trait inheritance walk for calling requirements.** `inheritance::collect` (`calling/application/signature/inheritance.rs:23-141`) walks boundary-trait parents depth first, carrying a substitution list (type parameter symbol to argument) and a lifetime renaming list. It stops at depth 64 or on revisiting a trait on the active stack (`:31-35`). Each trait that declares the requirement is recorded; afterwards all recorded paths must project to identical arguments (`calling/application/signature.rs:151-173`), which is how inheritance diamonds are accepted.

**Type instantiation.** `instantiation::project` (`calling/application/signature/instantiation.rs:63-230`) substitutes type parameters and renames lifetimes through named, reference, constrained, fixed-array, slice and generic types, inserting new nodes into a scratch type table. Depth limit 64 (`:73-77`). It has two lifetime modes: a name-to-name list, or resolution through the declaration that lexically owns the operand (`:52-61`, `:91-109`).

**Lifetime name normalization.** Method and nested lifetimes that collide with an outer name are renamed to generated identifiers (`calling/application/signature.rs:213-217`; `signature/parameters.rs:55-66`, with a loop that increments a collision counter until the name is free). This serves nested structural machine parameters whose authored lifetime names shadow outer ones (`signature/parameters.rs:1-4`).

**Recursive contract-expression projection.** `project_contract_expression_with_substitutions` (`contracts/expressions/projection/mod.rs:48-271`) is one exhaustive `match` over 21 expression node kinds, depth limit 256. It threads two substitution lists: projected values for proposition parameters, and raw expression handles used to detect a parameter that stands for a call (`projection/member_expression.rs:48-82`).

**Transparent proposition expansion.** `project_contract_proposition` (`contracts/propositions/application.rs:41-295`) expands a transparent proposition into its body with binder and value substitutions (newest binding wins, `contracts/propositions/binders.rs:36-40`), a `visiting` stack for cycles and a depth limit of 64. Primitive and witness propositions stop the expansion and become endpoints.

**Member-path recovery from fact places.** `checked_contract_member_path` (`contracts/expressions/members.rs:392-496`) recovers which fields a source path like `packet.bytes` denotes by finding the places the checker recorded for the same fact: it gathers the fact's subject places and its storage-dependency places, keeps those with the same root, and matches the first N field segments against the N authored members (`checked_member_prefix`, `:570-621`). A mismatch is repaired by an attached-field alias (`members/aliases.rs`) or by a recorded member projection row (`members/projections.rs`). Exactly one distinct result is required.

**Evidence-requirement closure.** `collect_evidence_requirements` (`contracts/propositions/evidence.rs:88-245`) collects every requirement of a witness trait and its parents, with a visited list keyed by trait identity, lifetime ordinals and argument identities. It has no depth limit.

**Lazy per-batch caches.** `ContractOwnerQueries` builds one `OwnerEnvironmentIndex` on first use (`input.rs:223-256`); `MathematicalCallQueries` runs the mathematical proof check once (`contracts/mathematical_calls.rs:24-45`).

**Canonical ordering.** Output rows are sorted and often de-duplicated so the record does not depend on traversal order (`calling/callbacks.rs:31`, `:50`, `:140`, `:180`; `calling/opaque.rs:101`, `:120`; `contracts/facts.rs:278-279`; `contracts/propositions/evidence.rs:78-79`).

Paths here are relative to `contracts/expressions/` unless a longer path is given.

## Accepts or skips without proof

Paths here are relative to `contracts/expressions/` unless a longer path is given.

## Surprises

**What the three properties look like here.**

1. *Acceptance by own judgment.* The slice contains about 250 distinct refusals and one call into the proof crate: `proof::mathematical_declarations::check_mathematical_declarations` followed by a presence test (`contracts/mathematical_calls.rs:28-43`). The names `proof_admission`, `ProofNode` and `verify_obligation` do not occur anywhere under `capture/`. Everything else that touches proof (`facts.proof.contract_facts`, `evidence_terms`, `outcome_specific_guarantees`, `contract_expression_evidence_calls`, `contract_expression_static_conformance_applications`, `proposition_vocabulary`) is a table of rows written by an earlier stage; this code counts and compares rows. The word "certificates" appears only in a diagnostic about `fact_call_projections` rows (`contracts/expressions/calls.rs:137`). Where the code does more than count, it re-derives a value through another crate and compares (see "Replay and compare").
2. *Identity by text.* Mixed. Most joins use symbol handles and arena handles. Text decides meaning for proof views, byte-sequence predicates, Carry permissions, `self`, `result`, `len`/`capacity`, lifetimes, evidence terms, evidence-projection members, integer type names and target names (list above). The output record is deliberately name-free for parameters (ordinals) but keeps rendered text for type identities.
3. *One rule per placement.* Present but moderate, about 12% (list above). The strongest cases are owner kind (machine, state, state signature, domain, data, operator) and receiver shape.

**Things a careful reader would want to know.**

- **This code can refuse programs the checker admitted.** It has its own, narrower vocabulary. A package that uses any item in the "not yet" list above cannot be reviewed. A declared (user-defined) unary operator in a contract is refused (`contracts/expressions/projection/mod.rs:226-233`), although declared binary and index operators are projected (`:186`, `:220`). A caller's `Value`-kind binder passed to a constant slot is refused because only `Const` matches (`contracts/expressions/static_arguments.rs:362-374`), although `Value` and `Const` are treated alike earlier in the same file (`:40-42`).
- **A trait requirement cannot publish an `ensures` for a specific result case.** `checked_outcome_specific_guarantee` requires a machine owner (`contracts/evidence.rs:24-27`), and `project_trait_requirement_contracts` runs the same loop with a caller-supplied, non-machine owner (`contracts/facts.rs:104-116`, `:233-241`).
- **Evidence passed to a contract call must come from a `requires` term.** An `ensures` evidence term cannot feed a lane (`contracts/expressions/evidence.rs:100`), and evidence projections look only at `requires` terms (`contracts/propositions/binders.rs:99`).
- **Missing type identity becomes an empty string.** Three `unwrap_or_default()` calls (`contracts/expressions/static_arguments.rs:320`, `:401`; `contracts/propositions/binders.rs:69`) would make two different types with no rendered identity compare equal in the record. Everywhere else in the slice a missing value is a refusal.
- **Field aliasing is decided by source position.** `attached_field` accepts a machine field as the same field as a data field when both symbols have the same non-empty source span (`contracts/expressions/members/aliases.rs:53-61`). The header calls these "resolver-seeded machine field aliases" (`aliases.rs:1-2`), so the resolver creates a second symbol for one declaration and this code reunites them by span.
- **Candidate equals custody on the common path.** `From<&CheckedCompilation>` calls `supplied(compilation, compilation)` (`input.rs:195-199`). On that path the custody comparisons in `contracts/expressions/operators.rs:111-136`, `contracts/expressions/layout_queries.rs:26-93` and `input.rs:171-180` compare a program with itself.
- **The mathematical proof check may be re-run per call.** When `compilation.mathematical_calls` is `None`, `require_checked_contract_call_arguments` builds a fresh `MathematicalCallQueries` and checks all mathematical declarations again for that one call (`contracts/expressions/calls.rs:81-88`). `mathematical_calls` is `None` in `supplied` and `checked` (`input.rs:61`, `:88`) and set only by `package_policy.rs:65` and by `runtime_permissions.rs:54` (outside the slice).
- **One recursion has no depth limit.** Every other recursive walk stops at 64 or 256. `collect_evidence_requirements` relies only on its visited list (`contracts/propositions/evidence.rs:178-186`); a trait whose parent application grows its arguments would never repeat a visited key. Cannot tell whether an earlier stage forbids that.
- **Depth restarts inside proposition expansion.** Each expression projected from a proposition starts again at depth 0 (`contracts/propositions/application.rs:141`, `:221`, `:286`), so the 256 limit applies per expansion level, not to the whole contract.
- **A refusal that cannot fire.** `project_contract_binary_operator` returns `None` only for `CaseMembership` (`contracts/expressions/operators.rs:171`), but `is_case_membership` is already true for that operator (`contracts/expressions/case_membership.rs:26`), so the branch returns before `contracts/expressions/projection/mod.rs:218` is reached. "contract operator has no ordinary binary representation" is dead.
- **`is_case_membership` is wider than the operator.** Any binary expression carrying a `CaseMembership` or `CaseReference` selection is treated as a case test, whatever its operator (`contracts/expressions/case_membership.rs:26-40`). The four validators are then asked to confirm it, and the binary operator itself is never recorded.
- **Misleading diagnostics.** `exactly_one` always says "reviewed callable `{subject}`" (`semantics/facts.rs:11-17`), but it is called with a domain or data name as subject (`contracts/expressions/case_membership.rs:89-96`, `:104-111`) and with the literal "contract member path" (`contracts/expressions/members/points.rs:25-36`, `:41-48`), giving "reviewed callable `contract member path` has no exact checked checked declaration fact row". `exact_checked_expression_selection` is generic over selection kind but its messages say "operator" (`contracts/expressions/operators.rs:106-135`). `contracts/facts.rs:155` says "empty public ... contract" for private contracts too.
- **Visibility rule is uneven.** Casts, constructors and membership domains refuse a non-public declaration only when the reviewed package owns it (`contracts/expressions/casts.rs:32-34`; `constructors.rs:33-35`; `contracts/facts.rs:199-201`). Case membership and conformance traits refuse on `!is_public` alone (`contracts/expressions/case_membership.rs:155`; `static_arguments/conformance.rs:189`).
- **Selection checks differ in depth.** Named constants are collected recursively through nested applications (`contracts/expressions/static_arguments.rs:169-184`); conformances only at the top level (`static_arguments/conformance.rs:25-32`).
- **Name-root priority differs between two functions.** In `contracts/expressions/names.rs:120-136` a parameter wins over `result`, so a parameter named `result` is projected as a parameter, and a substitution wins over everything. `contracts/expressions/members.rs:248-258` tests `result` first.
- **Fact-call projection ignores derived targets.** `exact_fact_call_projection` matches `projection.target_state == call.target_symbol` (`contracts/expressions/calls.rs:131`), while the call-target rule also accepts a target derived from the owner when `target_symbol` is invalid (`calls.rs:199-209`). A field read from such a call would find no projection row.
- **A zero fingerprint is a sentinel.** `report == 0` is refused as stale (`calling/application.rs:80-85`).
- **Whole-table scans by symbol.** `contracts/expressions/static_arguments.rs:350-356` and `contracts/propositions/application.rs:71-77` search every type parameter in the program for one symbol; `calling/callbacks/binders.rs:25-59` scans every trait requirement and every machine per binder.
- **Lines not formatted by rustfmt.** `contracts/expressions/members/aliases.rs:50-52`, `calling/callbacks/layouts.rs:284-286` and `contracts/expressions/projection/mod.rs:218` are long single lines in otherwise formatted files.
- **`unreachable!` and `expect` on guarded paths.** `contracts/propositions/endpoint.rs:40`; `contracts/expressions/projection/member_expression.rs:59-66`, `:189-191`; `contracts/expressions/names.rs:75`. Each is guarded by a test a few lines above.
- **Deref chain hides which program is read.** `PackageReviewInput` derefs to `SourceDeclarationInput`, which derefs to the candidate `CheckedTrees` (`input.rs:207-221`). So `compilation.facts`, `compilation.symbols` and `compilation.expression_table` always mean the candidate, while `compilation.custody` and `compilation.original_program` mean the original. The "checked" row in `callables/reach_dependency.rs:25-34` is therefore the candidate's row.
