## What this code is for

This file does not judge a program against language rules and report errors. It builds the execution plan for one state body: an ordered list of `CheckedUnitEffectOperationPlan` operations (establish a local, store, call, release a reference, clean up) that the next stage lowers. The header says so: "The single-state body producer" (seq.rs:2), and "Each statement is planned by the emitter its kind and evidence select" (seq.rs:8).

The first 2,287 lines plan three things: one assignment (`mod assignments`, seq.rs:52-501), one `let` (`mod local_data`, seq.rs:1211-2287, with `mod bounded_byte_values` at seq.rs:502-617 for bounded byte locals), and the body's result (`mod completion`, seq.rs:618-1208). Each planner returns `Option`. `None` means "this producer declines the statement"; the caller (outside the slice) turns that into a refusal. The only record of why is a trace phase string.

The remaining 2,580 lines (`mod reference_retirement`, seq.rs:2288-4867) decide when a stored reference ("descriptor", "carrier", "holder") can be released. They read the borrow ledger (`facts.borrow`), the flow facts (`facts.flow`), the structural value graph (`facts.values.structural_values`) and the cleanup dispositions (`facts.contextual_cleanup`), all computed by earlier checking. They answer yes/no questions such as "has every holder of this loan retired by this statement" and emit `ReleaseReference` operations, owner cleanups, selection complements and runtime case conditions.

All of this is plan construction on source-tree coordinates: statement ordinals, call ordinals, expression handles, binding ordinals. The code consumes facts and re-derives their consistency with the plan it is building.

## Mechanisms

- **First-match producer chain.** `local_data::plan_inner` (seq.rs:1312-1925) and `assignments::plan` (seq.rs:107-371) try producers in a fixed order and return at the first that accepts. The order carries meaning: for example a structural value root suppresses subslice, reference-capture and place-loan handling (`structural_root.is_none()` at seq.rs:1558-1559, 1628, 1659). No budget.
- **Store queue merge by statement ordinal.** A `Peekable` iterator of pre-planned stores is drained per statement (seq.rs:152-158); a leftover earlier store blocks planning (seq.rs:317-326). Serves assignment ordering.
- **Binding ordinal allocation.** `scalar_count` and `structural_count` are counters; every new binding takes the current value and increments with `checked_add` (for example seq.rs:181, 206-207, 1446-1451). Assignment replacement adds `1 + replacement.displaced_bindings()` (seq.rs:206-207, 295-296).
- **Enter/leave depth-first walks with cycle refusal.** `dispatch_observation` walks expression trees with an epoch-stamped `HashMap` and refuses on a re-entered node (seq.rs:1977-2033). `completed_descriptor_sources` walks loan predecessors with `active` and `completed` vectors and refuses on a cycle or a loan outside the state (seq.rs:2389-2452). No depth budget; membership tests are linear `Vec::contains`.
- **Retirement recursion.** `carrier_retired` pushes a `RetirementNode::Carrier(ordinal)` on an `active` stack and answers `false` when it meets itself (seq.rs:3231-3244). It then tries five ways a carrier can be settled (seq.rs:3246-3499) and recurses through `Destination::{Holder, Backing, Storage, Call}`. Serves reference lifetime scheduling.
- **Transport relation and reachability.** `transport::collect` builds a list of `(receiver loan, supplier loan)` pairs from the ledger's `supplying_loans` and from the value graph's stored carrier sources, picking the latest supplier formation by execution position (seq.rs:4575-4719). `transport::supplies` is a transitive reachability search over that list (seq.rs:4726-4746).
- **Differential closure test.** `prepare_owner_cleanups` evaluates, for each pending release and each anonymous owner, whether the owner is "closed" with the release included and not closed without it; it attaches the owner cleanup to exactly that release (seq.rs:3787-3873). Cost is pending releases × owners × two full retirement queries.
- **Static-or-runtime case test.** `prepare_case_conditions` asks whether a case is proved selected at every exit (deferred release) or at the statement entry; if not it emits a runtime `CheckedCleanupCaseCondition` (seq.rs:2912-2981).
- **Sorted rows with binary search.** `StorageBorrowers` sorts `(root, loan)` rows by `group_key` and uses `partition_point` (seq.rs:4777-4807).
- **Claim roster equality.** A forwarded linear parameter's entry claims are sorted by path and compared for equality with the reconstructed return claims (seq.rs:1168-1186).

There is no fixpoint, unification, interval analysis or budgeted search in this slice.

## Surprises

1. **This is plan construction, not rule checking, and it lives in the checker stage.** The file decides which executable operations a body gets (stores, releases, cleanups, runtime case conditions). A refusal is a bare `None` from an `Option` chain hundreds of lines long. The only explanation kept is the last trace phase string, which the authors themselves call "not proof of the cause" (seq.rs:1292-1295).

2. **More than half the slice (seq.rs:2288-4867) re-derives when references die, from facts another stage already computed.** It joins the borrow ledger, flow facts, the value graph and cleanup dispositions by statement ordinal, call ordinal, owner symbol and path. The joins are defensive: nearly every lookup checks that exactly one row matches and refuses on two. This is evidence that the facts and the plan are two descriptions of the same body that must be reconciled, not one description.

3. **Property 2 is weak here.** I found no meaning decided by a string. Identity is by source coordinates and ordinals instead. The fragility is the same kind (a place is named by where it was written), but the mechanism is handles, not text.

4. **Three different notions of "same type" are used in one file** (raw handle, normalized identity, shape identity; see Identity by text). The returned-value check uses raw handle equality (seq.rs:785) while the forwarded-parameter check a few lines later uses normalized identity (seq.rs:1127-1128).

5. **The three scalar-array copies disagree.** The assignment copy hard-codes `Unrestricted` multiplicity and registers no domains with `shapes` (seq.rs:179-185, 208-220); the return and local copies ask the type and register each domain (seq.rs:913-928, 1795-1825).

6. **`Call` completion is reachable only when there is no tail expression.** `exit` is `tail.map(Value).or_else(Call)` (seq.rs:755-781), so a body whose tail is an expression always gets a `Value` completion, even in the `returned_call` branch (seq.rs:874-890).

7. **Reference sources are computed twice for a forwarded reference record.** `forwarded_parameter` fills `reference_sources` (seq.rs:1196-1205), then `complete` overwrites it with the same call (seq.rs:945-956).

8. **Debug printing is compiled into the product path.** Six `eprintln!("CHECKSITE ...")` sites gated on `trace_flags::check_sites()` (seq.rs:2573-2597, 2742-2755, 2803-2821, 3137-3142, 3275-3280, 4516-4525). One prints the fixed text `all_matching_owners=true` regardless of what was found (seq.rs:2818-2820). One uses `any_state_disposition` with a closure that always returns `false`, purely to iterate and print (seq.rs:2810-2817).

9. **Cycle protection is reset in places.** `RetirementNode`'s comment says neither graph "can erase the other's active recursion" (seq.rs:4858-4861), but `carrier_children_retired` and `prepare_owner_cleanups` start each `carrier_retired` query with a fresh `&mut Vec::new()` (seq.rs:3136, 3180, 3197, 3828). Within this slice those callers are not reached from inside `carrier_retired`, so I see no loop, but the stack is not shared.

10. **Quadratic and repeated work.** Visited sets are `Vec::contains` (seq.rs:2401-2404, 2584, 4737). `prepare_owner_cleanups` runs two full retirement queries per pending release per owner (seq.rs:3836-3845). `complete` recomputes the reachable statement list four times. `dispatch_observation` uses a `HashMap` keyed by expression handle (seq.rs:1977).

11. **`reference_capture` is planned before it is known to be needed** (seq.rs:1417-1418) and discarded whenever a structural root exists or an earlier producer accepts.

12. **The dispatch-observation rule is a whole-suffix syntactic scan.** To let one `let` skip its descriptor, the code walks every expression of every later statement of the state and requires all of them to be transitions (seq.rs:1972-2034). That is a rule about one local decided by the shape of the rest of the body, contrary to the header's "no whole-body shape chooses a different producer".

13. **A possibly dead path.** The `uninit_zeroed` case (seq.rs:1376-1379) has no visible producer in this slice; see Accepts or skips.

14. **A capability I did not expect:** the planner emits runtime case tests for cleanup (`CheckedCleanupCaseCondition`, seq.rs:2944-2981) when it cannot show statically which case of a sum holds a dying reference. Cleanup correctness can therefore depend on a run-time branch chosen here.
