## What this code is for

This slice is the middle of the old checker's numeric reasoning. It answers one kind of question for the rest of the checker: "what range of values can this integer or float expression have at this point in this state of this machine?" It does that by keeping a `ValueEnvironment`, a table of facts keyed mostly by the rendered text of a storage place, and by walking a state's statements in execution order while it adds facts from guards and contracts and removes facts when something is written.

The slice holds these modules: float interval reasoning (`float_arithmetic`, `float_contracts`, 8892-9884); the statement walk that carries facts between states of one machine and infers return ranges from callee bodies (`guard_narrowing::arrivals`, 9895-12484); remembered boolean locals, variant requirements, collection predicates, and contract seeding (12485-13682); guard narrowing proper, including recognition of hand-written overflow guards (13696-14837); the check that a call's `requires` holds at the call site (`guard_requirements`, 14839-14985); integer range validation and its three diagnostics (`integer_ranges`, 15014-15571); a small prover for orderings between integer terms (`ordering_premises`, 15573-16274); three interval data types (`interval`, `integer_sets`, `integer_operations`, 16353-16974); and bounds that hold for the whole life of a state because they come from declared types and `requires` (`invariant_bounds`, 16976-18142).

Most functions here are oracles: they return an interval, an `Option<bool>`, or a `bool`, and the caller (outside the slice) decides whether to emit a diagnostic. Only three diagnostics are created inside the slice.

## Mechanisms

**Statement walk with a fact table (`ArrivalWalk`, arithmetic_domains.rs:11086-12272).** It walks one state's statements in `finite_execution_order`, carrying a `ValueEnvironment`. For each statement kind it visits sub-expressions, drops facts for written places, and records new facts for the destination. It serves three uses, selected by fields: collecting the facts each transition delivers to another state of the same machine (`collect_arrivals`), recording the interval and environment at chosen expressions (`observations`, found by binary search on handle index and generation, arithmetic_domains.rs:12212-12270), and collecting the argument ranges at chosen cross-machine transitions (arithmetic_domains.rs:11490-11509). A walk stops at the first transition that cannot fall through (arithmetic_domains.rs:11618-11620). It serves guards, `requires`, and every "bounds at this occurrence" query.

**Fixpoint over the states of a machine (`incoming_environments`, arithmetic_domains.rs:10846-11014).** Every state starts with an empty environment (no facts), except the externally entered state, which starts from its `requires`. Each round walks every state that has transitions to states of the same machine, joins the arriving environments per target state, and stops when nothing changes or after `states.len() + 1` rounds (arithmetic_domains.rs:10950). A `stale` flag skips states whose input did not change. The result is memoized per machine symbol (arithmetic_domains.rs:14791-14815). Because the start is "no facts", the iteration moves from fewer facts to more; `ValueEnvironment::join` (arithmetic_domains.rs:26809, outside the slice) keeps only shared facts and I found no widening step in the file.

**Return-range inference from a callee's body (`normal_returns`, arithmetic_domains.rs:9919-10327).** Given a machine, an entry state and the argument ranges, it finds every returned expression and every transition into another machine, walks the states with the argument ranges seeded, and unions the observed intervals. It follows transitions into other machines recursively with the observed argument ranges (arithmetic_domains.rs:10271-10318). Limits: a stack-linked list of active (machine, entry) pairs returns `None` on a cycle (arithmetic_domains.rs:10044-10047); results are memoized by (machine, entry, primitive, argument intervals), only when a result exists and no argument carries a symbolic recipe (arithmetic_domains.rs:10020-10043, 10092-10097). The answer must have both ends bounded or carry a recipe (arithmetic_domains.rs:10324).

**Integer ordering prover (`prove_integer_ordering`, arithmetic_domains.rs:15639-15752).** Terms are `IntegerBound` values (a literal, a symbol plus offset, a storage symbol, a projected field path, a sum of two symbols plus offset, a call result). `bound_shift` gives the constant difference between two terms of the same base (arithmetic_domains.rs:15988-16058). A query is proven by one premise (a 4x4 table of premise relation against query relation, arithmetic_domains.rs:15858-15875), by a chain of two premises that share a middle term (arithmetic_domains.rs:15937-15986), or by replacing either side with a term a premise states equal and trying again (arithmetic_domains.rs:15659-15712). Budget: `premises² + 4096` premise consultations (arithmetic_domains.rs:15645-15649); when it runs out the answer is false. Premises taken from a callee are translated through parameter-to-argument symbol pairs (arithmetic_domains.rs:15786-15841).

**Upper-bound closure (`propagate_integer_upper_bounds`, arithmetic_domains.rs:16122-16162).** A loop to a fixed point: from "upper is an index of C" and "lower <= upper" it adds "lower is an index of C"; from "upper is a range bound of C" it adds an index (strict) or a range bound (non-strict). No budget; it ends because the sets only grow over a finite set of subjects.

**Type-parameter interval solving (`solved_integer_binder_interval`, arithmetic_domains.rs:17784-17824).** Jacobi-style iteration: each const/value type parameter starts at its declared range; each round intersects with bounds read from `requires` facts using the previous round's intervals for the other parameters; at most one round per parameter.

**Interval arithmetic on `Option<i64>` endpoints (`Interval`, arithmetic_domains.rs:16353-16601).** Add, subtract, multiply (four corners, unbounded on any overflow), shift left (corners in `i128`), shift right, divide (four corners; a missing divisor endpoint counts as quotient 0, arithmetic_domains.rs:16524-16527), modulo (bounded by divisor magnitude minus one), min, max, union, intersect, contains. `None` means unbounded on that side, which is also how values above `i64::MAX` in `u64` are represented (arithmetic_domains.rs:15362).

**Sets of integer ranges (`IntegerSet`, arithmetic_domains.rs:16604-16734).** Sorted disjoint `i128` ranges with union, intersect, difference, subset, and "the set satisfying `op bound`". This is the only representation in the slice that can hold a hole such as `x != 0`.

**Arbitrary-precision interval operations (`integer_binary_range`, arithmetic_domains.rs:16777-16821).** Works on `BigInt` ranges through `BigIntInterval` (defined outside the slice); covers add, subtract, multiply, divide, modulo, shift right, and bitwise and/or/xor for non-negative operands. Shift left is not handled.

**Float interval projection from contracts (`project`, `project_parameter`, arithmetic_domains.rs:9447-9664).** Reads `ensures`/`requires` expressions: `and` intersects, `or` unions, a comparison of the subject with a literal gives a half-line, a comparison of the result with a parameter uses that parameter's own `requires` interval. Anything it does not recognize contributes "unbounded".

**Guard evaluation under writes (`evaluated_condition_with_frames`, arithmetic_domains.rs:13985-14060).** Splits `not`, `and`, `or`, and `b == true/false`, then for a leaf condition drops facts for the places the condition's calls may write, narrows, and drops them again.

## Accepts or skips without proof

- **Assembly statements are skipped and no fact is dropped.** `StatementNode::Assembly(_) | AssemblyFact(_) => continue` (arithmetic_domains.rs:11637-11639; also 12004, 12055, 12360). Facts about places stay as they were across the statement. I cannot see in this slice what limits the places an assembly block may write.
- **Declared ranges are trusted at arrival.** A parameter's interval is the argument's interval intersected with the parameter type's `enforced_declared_range` (arithmetic_domains.rs:11395-11399); fields of every parameter get their declared integer and float ranges (arithmetic_domains.rs:10894-10906, 13847-13859); record parameters get the record's `requires` field intervals, through a reference too (arithmetic_domains.rs:13328-13354, 13360-13363). The check that the argument satisfied them is not in this slice.
- **Declared field ranges are trusted as standing bounds for mutable storage** when the parameter is the machine's own data or when `declared_mutable_leaves` is set (arithmetic_domains.rs:17005-17012, 17389-17401). Cannot tell from here where each write is checked.
- **Callee `ensures` are taken as facts about a call result** (arithmetic_domains.rs:9392-9433, 17654-17686) and **a trait signature's `ensures` as facts about caller places** after a boundary-trait call (arithmetic_domains.rs:11975-11989). This is ordinary contract-based reasoning; for a boundary trait I cannot see a body that the `ensures` is checked against.
- **When requirements contradict arriving facts, the arriving facts are thrown away.** If any interval is empty after applying a state's `requires`, the environment is replaced with one built from the requirements alone (arithmetic_domains.rs:13522-13543). No diagnostic here; cannot tell whether the contradiction is reported elsewhere.
- **`comparison_meaning_is_available` returns true for a non-binary expression and for any operator other than the six comparisons** (arithmetic_domains.rs:13738-13754). The consumers that follow only act on recognized shapes (arithmetic_domains.rs:13871-13889, 13918-13925), and `seed_state_requirements` re-checks meaning (arithmetic_domains.rs:14231-14251), so I see no fact created by this default.
- **Wrong argument count at an in-machine transition**: the target receives an empty environment and the walk goes on (arithmetic_domains.rs:11362-11365). Conservative; no error here.
- **Unknown target state or invalid symbol**: `join` returns silently (arithmetic_domains.rs:11100-11108).
- **Failed analysis becomes "unbounded"** rather than an error: arithmetic_domains.rs:11152-11155, 11176-11178, 12222-12224, 11775. Conservative.
- **A failed lookup of a state's incoming facts becomes an empty environment** (arithmetic_domains.rs:14832-14835); failed occurrence queries return "no bounds" (arithmetic_domains.rs:10538-10546). Conservative.
- **Without a call-frame resolver, cleanup writes drop facts only when the stored value contains a call or struct literal and the program has at least one cleanup** (arithmetic_domains.rs:11268-11285). Other shapes that end a value's life are not considered on this path; cannot tell whether the resolver is always present in real checks.
- **An untyped value stored in `addr` that fits `u64` skips the fit check in `validate_anonymous_integer_primitive_range`** (arithmetic_domains.rs:15123-15125). `validate_anonymous_address_landing` then asks for the `addr::Bound` proof (arithmetic_domains.rs:15322-15336) on the `validate_value_range` route; for the other caller, `validate_anonymous_integer_range` (arithmetic_domains.rs:15045-15060), I cannot tell.
- **An invalid expression handle validates as "unbounded" with no diagnostic** (arithmetic_domains.rs:15254-15256).
- **A source interval outside its own primitive's range is replaced by the primitive's full range** before the fit test (arithmetic_domains.rs:15387-15391).
- **`u64` overflow is checked in standing bounds; `addr` is not.** Both have the range `(0, unbounded)` (arithmetic_domains.rs:15362), but the explicit fit test is only for `PrimitiveType::U64` (arithmetic_domains.rs:17499-17513). For `addr`, an add whose `i64` endpoint overflows yields an unbounded high end that passes `carrier.contains` (arithmetic_domains.rs:17545). Cannot tell whether `addr` arithmetic reaches this function with the Exact domain.
- **In-machine arrival detection is a separate scan.** A state is walked for arrivals only if `state_has_in_machine_arrivals` says so (arithmetic_domains.rs:10954). That scan pushes only `MatchPattern::Value` patterns (arithmetic_domains.rs:12371-12375) and uses `ordinary_value_initializer()` for locals (arithmetic_domains.rs:12343), while the walk also visits `Destructure` conditions (arithmetic_domains.rs:12087-12089) and uses `initial_value` (arithmetic_domains.rs:11660). A call to a state of the same machine that appears only where the scan does not look would leave that arrival out of the target's joined facts. Cannot tell whether such a program can be written.
- **Arrivals from outside the machine are represented for one state only** (`external_index`, arithmetic_domains.rs:10885-10945). If another machine could enter a non-entry state directly, its facts would not be joined. Cannot tell whether the language allows that.
- **`evaluated_call_requires_proven` uses the facts at the last argument's occurrence** (arithmetic_domains.rs:14886-14893), or, failing that, facts from the guard alone starting from an empty environment (arithmetic_domains.rs:14976-14983). Both are no stronger than the true facts as far as I can see.
- **Float `x == x` on one path string returns true** (arithmetic_domains.rs:9849-9856). It is reached only after both sides have bounds (arithmetic_domains.rs:9844-9845), which requires non-NaN evidence or a declared interval (arithmetic_domains.rs:9108-9110).

## Notes the authors left

Without a resolver the dying values cannot be named: a statement that builds or calls anything then has an unknown footprint."

- `scalar_reevaluation_does_not_consume_an_earlier_child_recipe` (arithmetic_domains.rs:12430-12482): evaluating a plain integer literal `8` returns `[8, 8]` and records no stored range, even when a stale entry for the same handle (`[7, 7]`) sits in `completed_children`. ## Surprises

1. **No proof kernel anywhere in this file.** A grep of the whole file for `proof_admission`, `ProofNode`, `verify_obligation`, `certificate` and `kernel` finds nothing. Every yes/no in the slice is interval or shape reasoning done here or in a sibling module. What the code does produce for later stages is a record of its own decisions: `IntegerRangeObligation`, `IntegerRangeRecipe`, `ArithmeticDecisions`, and "execution receipts" (arithmetic_domains.rs:15217-15237, 15329). These support property 1 as stated: the output is the checker's verdict plus notes, not evidence checked by something else.

2. **A caller's check can depend on a callee's body, across machines.** `inferred_normal_return_interval` reads the callee's statements to find its return range, follows transitions into further machines (arithmetic_domains.rs:10271-10318), and records the dependency with `note_dependency_body_read(..., DependencyBodyRead::ReturnInterval)` (arithmetic_domains.rs:9983-9987). So a callee with no `ensures` can still supply a range to its callers, and changing a callee's body can change whether a caller is accepted.

3. **Assembly statements leave all facts in place** (arithmetic_domains.rs:11637-11639). Every other statement kind drops facts for what it may write.

4. **Overflow safety is granted by recognizing exact spellings of a guard.** `a <= MAX / b` must use a literal equal to the type's maximum (arithmetic_domains.rs:14554-14565); `MIN + b <= a` must use the exact minimum (arithmetic_domains.rs:14527-14530). A guard that is mathematically stronger but spelled differently (for example a smaller constant divided by b) does not match these functions. The fact recorded is a pair of path strings marked "joint bound" (arithmetic_domains.rs:14259), not a relation between values.

5. **Requirements replace contradictory facts silently** (arithmetic_domains.rs:13522-13543). An empty interval means the state cannot be reached with those facts, or one side is wrong; the code keeps the `requires` side and continues.

6. **Two scans that must agree do not match exactly**: `state_has_in_machine_arrivals` versus `ArrivalWalk::expression` on `Destructure` pattern conditions and on which local initializer is read (arithmetic_domains.rs:12371-12375 against 12087-12089; 12343 against 11660). If the scan misses an arrival, the target state's facts are joined without it.

7. **`integer_bound_terms_equal` has no case for `Storage` or `StorageProjected`** (arithmetic_domains.rs:16060-16108), so two identical storage terms compare as not equal there, while `bound_shift` treats them as equal with difference 0 (arithmetic_domains.rs:16004-16031). The same function returns true for any two `Integer` terms whatever their values (arithmetic_domains.rs:16063); read with `integer_bound_offset` this may be intended ("same base, compare offsets"), but the name does not say so.

8. **The `ensures` interval of a machine is cached in the memo named `parameter_requires_intervals`** under the key `(machine, state, invalid symbol, true)` (arithmetic_domains.rs:17724-17757), the same map `requires_interval` uses with `(machine, state, parameter, include_machine_contracts)` (arithmetic_domains.rs:18049-18091). In this slice `requires_interval` is always called with `false` (arithmetic_domains.rs:17189, 17382), so the keys do not collide here.

9. **Four different representations of an integer range live side by side**: `Interval` with `Option<i64>` ends, where "above `i64::MAX`" and "unbounded" are the same thing (arithmetic_domains.rs:16355-16358, 15339-15351); `IntegerSet` on `i128` (arithmetic_domains.rs:16608-16610); `IntegerRange`/`BigIntInterval` on `BigInt` (arithmetic_domains.rs:16777-16821); and the symbolic `IntegerRangeRecipe` carried next to intervals (arithmetic_domains.rs:9974, 11026). Code converts between them at many points (for example arithmetic_domains.rs:10638-10647, 13073-13076, 16294-16303). `u64` needs its own side channel, `known_u64_values`, because `Interval` cannot hold `u64::MAX` (arithmetic_domains.rs:14296-14315, 14558-14560, 15495-15509).

10. **The interval fixpoint is capped at `states.len() + 1` rounds with no widening and no report when it does not settle** (arithmetic_domains.rs:10950-11003). It starts from "no facts", so stopping early leaves the facts of the last completed round. I could not confirm from this slice that every round's result is safe to use when the loop has not settled.

11. **`evaluated_call_requires_proven` computes "any argument has a call" twice in a row** (arithmetic_domains.rs:14878-14880, 14882-14884), and when it falls back to the guard it starts from an empty environment, so the facts known on entry to the state are not available on that route (arithmetic_domains.rs:14982).

12. **`arrival_integer_expression_bounds` ignores incoming facts for transition arguments**: `transition_arguments::integer_bounds` starts from `ValueEnvironment::new()` and uses only the transition's own guard (arithmetic_domains.rs:10359-10372), while the non-transition branch uses the full occurrence walk (arithmetic_domains.rs:10475-10481).

13. **Small leftovers.** `callee_parameter_interval` takes `_other_type` and never uses it (arithmetic_domains.rs:9573). `comparison_meaning` only forwards to another function (arithmetic_domains.rs:9666-9680). The "does not fit destination" diagnostic has no source span while its sibling has one (arithmetic_domains.rs:15130-15133 against 15112-15120). Debug `eprintln!` tracing is compiled into the checker (arithmetic_domains.rs:10062-10089). `FloatSourceBounds::from_comparison` and `is_exact_integer` (arithmetic_domains.rs:8982-8997, 9018-9020) have no caller inside the slice.

14. **Float bounds for `f32` are computed in `f64`** with the neighbor taken after `value as f32` (arithmetic_domains.rs:9244-9259). This is exact only if the literal was already rounded to `f32` before it got here; `float_literal_value` returns `landed_f64()` (arithmetic_domains.rs:8911) and the cast branch demands an exact conversion (arithmetic_domains.rs:8926), so it probably is, but the function itself does not check.

15. **A capability I did not expect**: `FloatSourceBounds::is_integral` proves that a whole float interval holds only integers when it lies at or beyond 2^23 (`f32`) or 2^52 (`f64`) in magnitude (arithmetic_domains.rs:9022-9035), and boolean locals carry both branches' facts so that `let ok = i < n; ... when ok` narrows `i` later (arithmetic_domains.rs:12593-12676).

16. **On property 3**, the strongest single piece of evidence in this slice is the set of eight separate readers of "a comparison in a contract or guard" listed under Repetition item 2; each handles a different subset of operators and shapes (for example `or` is a union at arithmetic_domains.rs:9492 and 17924, is ignored at arithmetic_domains.rs:12754-12775 and 14726-14730, and narrows nothing when true at arithmetic_domains.rs:14203).
