## What this code is for

This is stage 04 of the old pipeline, "typed trees to typed trees". It takes the typed program from stage 03, rewrites it in place, and hands a frozen copy plus a `TypedPreparation` record of "judgments" to the stage-05 checker (lib.rs:20-25, preparation.rs:1945-2062). It is mostly an elaborator, not a checker: its main job is to make every generic thing concrete before checking. `monomorphization.rs` is the coordinator of that work. It finds every generic machine ("candidate template"), infers the type, const, runtime-value, machine and conformance arguments at each call, clones a specialized machine for each distinct argument tuple, and redirects the call to the clone, repeating until nothing changes (monomorphization.rs:3746-3910). Around that loop it closes generic domains, cleanup machines, conformance-owned bodies ("captures"), boundary-trait providers, finite families, `dyn` slots and generic operator providers. `policy_operators.rs` rewrites the suffixed arithmetic operators (`+%`, `+|`, `+!`) into casts around the plain operator (policy_operators.rs:1-26). `preparation.rs` holds the three public pipelines (`prepare_typed_trees`, `prepare_execution_applications`, `prepare_constant_execution`) and several small passes: array lengths, constant evaluation entries, implicit "runtime index" fields of struct literals, hoisting of runtime value indexes out of types, `align_of(value)` settlement, and late binding of authored selections. `lib.rs` holds three more small passes: the receiving type of an assignment, record-pattern field binding, and a mutable local "home" for a parameter that the body assigns. The code refuses programs in about 130 places, but almost all refusals are internal-consistency messages ("... lost its ...") rather than language rules.

## Mechanisms

**Specialization fixed point** (monomorphization.rs:3746-3910). `monomorphize_generic_machine_value_calls` is an unbounded `loop`. Each round runs about twenty sub-passes in a fixed order (named-result overloads, occurrence selections, constructed result types, inferred result locals, dispatch subjects, reference observations, domain applications, static argument types, cleanup applications, native query lifetimes, projected receivers, contextual calls, const recipes, const folding, trait implementation arguments, layout storage policies, conformance scopes and demands, captures), then collects every machine with specialization parameters as a candidate, collects a `CallSelection` per call site, clones a machine per distinct complete tuple, and rewrites the calls. It restarts whenever a sub-pass reports change and returns when a round applies nothing. It serves generic machines, generic conformances, const and value parameters, machine parameters and conformance parameters. There is no round limit and no depth limit in this slice.

**Outer preparation loop** (preparation.rs:1990-2023). `prepare_typed_trees` wraps that fixed point in a second loop that also specializes operator providers, finite families, requirement applications, boundary providers, inferred result locals and constant entries, and re-binds operator calls in the changed declarations. It ends when a round "materialized" nothing. A third loop repeats specialization while `prepare_installed_interrupts` reports work (preparation.rs:2034-2037). `prepare_execution_applications` has its own loop ending when nothing materialized and the count of closed requirement applications is unchanged (preparation.rs:2090-2101). None has a budget.

**Static argument inference by proposals** (used at monomorphization.rs:1179-1206, 1345-1369, 1669-1690; the implementation is in another file). Each source of evidence proposes a binding for a slot (type, const, machine, conformance, runtime value). `selection::proposal_bindings` merges proposals into one tuple and reports `conflicted` and four `unresolved_*` flags. This slice reads those flags and decides whether to specialize, defer or refuse.

**Specialization identity and reuse** (monomorphization.rs:3313-3355, 3739-3744, 4404-4424). An existing specialization is found by comparing: the template symbol; the normalized type identity *text* of each type argument; the same text for each const argument; the symbols of machine arguments; the symbols of conformance arguments plus their closed conformance applications. `SpecializationKey` stores type and const arguments as `Vec<String>`.

**Target-family co-specialization** (monomorphization.rs:3365-3554). When the template belongs to a target-machine family (one interface plus one member per target), every member is specialized with the same binding tuple, and a closed family roster is recorded and compared with any roster already retained.

**Finite family expansion** (monomorphization.rs:2336-2428). For a boundary requirement whose signature has a finite family of const tuples (`FamilyProbe::Finite`), the provider is specialized once per tuple. Tuples are deduplicated by their identity strings.

**Dynamic slot instantiation** (monomorphization.rs:2664-2895). One slot signature is created per (normalized identity of the selector type, call requirement). The slot gets a leading `selector` parameter, the requirement's parameters with trait arguments substituted scope by scope, and a generated symbol. Calls through the selector are then retargeted to the slot.

**Const substitution with projection folding** (monomorphization.rs:2913-3161). For each const parameter of a specialized machine the pass scans the expression table (from a start index, or all of it) for bare names of the parameter and for member/index chains rooted at one. It replaces a chain `N.field[2]` by the selected part of the literal value and a bare name by the whole value. A chain that cannot be folded is left alone and its root name is replaced by the whole value.

**Const value materialization** (monomorphization.rs:3163-3215). A const binding is a type reference. The pass turns it into an expression by, in order: copying a const expression; decoding a const declaration's evaluated encoding; parsing the reference's *name* as a canonical atom; parsing it as a boolean spelling when the declared type is `bool`; reading it as an integer literal with the declared type's landing.

**Closed domain instances** (monomorphization.rs:1521-1646, 4943-5118). A loop collects every domain constraint in a type and every membership fact, evaluates const index arguments, builds an instance name with `indexed_domain_instance_name`, interns it in `semantic_domains`, and prepares the closed application. The same naming step then stamps a semantic id on type constraints, casts and membership facts.

**Inertness analysis for runtime index descriptors** (preparation.rs:520-553, 725-768, 882-1143). For data types with value parameters, the pass decides whether an argument expression can be evaluated a second time. A call is inert only if `CallFrameResolver` reports a complete, empty write frame for it; a binary operation only if it has builtin meaning; anything else per `inert_value_tree_with_operations`. `fill` walks a constructing expression against its receiving type, tracks whether effects happened earlier in evaluation order, records the receiving type on each struct literal, and prepends omitted descriptor fields rebuilt from the type's arguments, substituting caller arguments for callee parameters.

**Runtime value index hoisting** (preparation.rs:1163-1350). For an explicitly typed local whose type applies a data type to a non-literal expression in a value-parameter position, the pass inserts a generated local `__value_index#<n>#<k>` before it, initialised with that expression, and rewrites the type argument to a named reference to that local.

**Closed-input visitor** (preparation.rs:173-265). `ClosedInputs` visits an expression and its result type, keeps a stack of lexically bound symbols, and marks the inputs open if any free symbol is a parameter, local, type parameter, machine parameter, conformance parameter, proposition parameter, unknown, or a const with an open scope.

**Policy operator desugaring** (policy_operators.rs:56-445). Collects suffixed binary nodes from executable values and from machine and state contracts, plans a carrier type for each, then replaces `a OP? b` in place by `((a as T in P) OP (b as T in P)) as T`, casting only typed operands (and only the left operand of a shift). It first ensures a `T in P` type reference exists because "the checker finds a policy-qualified result type by lookup" (policy_operators.rs:416-417).

**Type reference walk** (monomorphization.rs:3563-3607). A worklist with a visited set over references, constrained types (base and domain arguments), arrays, slices and generic arguments.

**Opaque receipt propagation** (preparation.rs:444-501). A Copy receipt for one data declaration is copied to every data definition that has the same source span in the same file.

- lib.rs:136-145: record-pattern rows get field symbols here "so checking and later readers decide coverage by identity and never read a spelling again. A row naming no field, or one spelling two fields share, stays without a symbol; a subject that is not a plain record leaves the whole roster unresolved, and checking rejects both."
- lib.rs:194-198: "Each marker receives rows of its own: a specialized body may still share its template's rows, and the two subjects need not be the same record."

So the pass may be skipped only when no domain is generic and every referenced membership already has its identity. A program narrowed to its validation subjects can lose every generic domain and still hold such a membership."

- policy_operators.rs:21-25: a `!` form "is refused here by name, because an operation that can transfer control forms no specification term".
- policy_operators.rs:66-73: "a suffixed node that one of these walks reaches and cannot type is an error, never a node left for later. A projection of the program that leaves a machine out keeps that machine's nodes in the table with nothing reading them; those are not reached here and stay as written."
- policy_operators.rs:102-104: "A contract is read against the parameters of the machine that declares it: the entry state for a machine contract, the state itself for its own. That is the owner checking uses for the same contract."
- policy_operators.rs:149: "A stable sort keeps the executable site when one node is reached twice."

- preparation.rs:1561-1563: "One walk with one seen set: every expression is itself a root, so walking each root's tree separately revisited each subtree once per enclosing expression."

## Surprises

**Against the three properties.**

- Property 1 holds for this slice. A grep of the four files for `proof_admission`, `ProofNode`, `verify_obligation` and `certificate` finds nothing. The only use of the `proof` crate is `check_mathematical_declarations`, called at the end of two pipelines (preparation.rs:2051, 2110); its result is passed on as a "judgment" and nothing here inspects it. Every refusal in the slice is the code's own comparison or another module's `Result`.
- Property 2 holds, with one form I did not expect: const generic arguments travel as type references whose *name is the value*, with no symbol, and are recovered by parsing the name (monomorphization.rs:1144-1149, 1610-1615, 2602-2605, 3188-3197, 4006-4011). A second form is parsing the rendered identity string (2609-2632). The authors were also working against the property: lib.rs:136-145 binds record-pattern rows to field symbols once so later code stops reading spellings.
- Property 3 holds only partly. Most repetition here is by node kind (statement call versus expression call) and by parameter kind, not by where a value is stored. The clear placement cases are domain identity (three), cleanup holders (four), runtime index destinations (eight), `align_of` contexts (two), and runtime value hoisting, which exists for locals only.

**Things that look like bugs or gaps.**

1. **Trapping operator in a contract can escape its refusal.** Sites are deduplicated by expression after a stable sort, keeping the executable entry (policy_operators.rs:149-151). If one node is reached both from an executable value and from a contract, `in_contract` is false and the "cannot be used in a contract" refusal at 155-167 is not applied. The comment says a node can be reached twice.
2. **Two functions named `const_identity_type_reference` with different power.** The one for finite families takes an identity string, supports integers and booleans, and inserts the carrier if missing (monomorphization.rs:2586-2632). The one for operator providers takes a `CanonicalConstIdentity`, supports integers only, and only looks up a carrier that `materialize_static_argument_types` must already have inserted (4486-4499). A boolean const argument to a generic operator provider therefore fails with "without a supported canonical integer carrier" (4463), and an integer that was never spelled as a literal anywhere fails the same way.
3. **`layout_storage_policies` swallows a conformance error that its sibling reports** (monomorphization.rs:1748-1751 versus 2173-2176).
4. **Enforcement gap at expression call sites** (monomorphization.rs:3893) and **type-only partial evidence** (4806-4812), described above.
5. **Array length expressions that fail to evaluate are never reported in this slice** (preparation.rs:44-61, 377-403).
6. **The specialization loops have no bound** (monomorphization.rs:3751; preparation.rs:1990, 2034, 2090; monomorphization.rs:1522). A generic machine that calls itself at an ever-larger type or const would keep producing new tuples. I cannot see a limit in this slice.
7. **Panics where the same condition is a diagnostic elsewhere.** "generic template must retain a normalized callable identity" is an `expect` at monomorphization.rs:2567 and 4835 but a diagnostic at 1408, 1983 and 3457. Other `expect`s on program-dependent facts: 4205, 4252, 4261, 4291, 4454, 4472, 4937, 5136; preparation.rs:739, 775, 832, 1293, 1315; lib.rs:287.
8. **`validate_domain_membership_carriers` is run twice against an empty contract-facts arena** (preparation.rs:1369, 1395 and 2043-2046). Whatever that validator would read from contract facts it cannot read here.
9. **The `align_of` second pass judges every expression in the table**, including nodes no declaration reaches (preparation.rs:1557-1573), while the policy-operator pass deliberately leaves unreachable nodes alone (policy_operators.rs:71-73). An orphaned `align_of(value)` node would produce a diagnostic.
10. **Machine arguments are compared by symbol only when looking for an existing specialization** (monomorphization.rs:3328-3332, 3347). A nested application on a machine argument is not part of the key. `operands_are_open` treats a machine argument with an application as open (1857-1862), so this may never be reached with one; I cannot tell.

**Capabilities I did not expect.**

- **Runtime values in type argument positions.** A value parameter can be bound to a runtime expression. The pass hoists the expression into a generated local and rewrites the type argument to a *named type reference to that local's symbol* (preparation.rs:1306-1332). Struct literals of such types get implicit descriptor fields prepended (preparation.rs:1016-1022), guarded by an evaluation-order and write-effect analysis that uses call write frames (725-768).
- **`align_of(slice)` reuses bounds checking as its proof.** The pass inserts `slice[0]` as a "nonempty view" so that some later check on the index stands for "the slice is not empty" (preparation.rs:1532-1547).
- **Const folding of projections on const parameters** (`N.field`, `N[2]`) at specialization time (monomorphization.rs:3056-3161).
- **Opaque Copy receipts spread by source location**: a clone of a data declaration inherits Copy because it was declared at the same span in the same file (preparation.rs:469-497). There is no template-to-instance link used for this.
- **The whole typed program is cloned to serve as an operator-template source** (monomorphization.rs:4148), and cloned again per provider request (4229).
- **Refusal substitution**: when specialization fails, the code re-runs the static-binding validator and reports its diagnostics instead, on the stated ground that the internal message is not the author's mistake (preparation.rs:2165-2182). The fallback arm keeps the original refusal, so this cannot turn a refusal into an acceptance.
- **Three pipelines differ in what they check.** `prepare_constant_execution` (preparation.rs:2115-2135) never runs assembly validation, the wire protocol check, the unresolved-constant check, dynamic slot instantiation, runtime index fields, runtime value hoisting, or operator call binding. `prepare_execution_applications` runs five validators (2103-2112) that `prepare_typed_trees` does not call directly. A program is therefore held to different checks in this stage depending on which entry the caller uses; the stage-05 checker presumably covers the difference for `prepare_typed_trees`, but that is outside this slice.
