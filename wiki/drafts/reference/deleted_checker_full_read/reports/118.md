## What this code is for

This slice is the first part of the old checker's "machine call" utilities. It holds seven modules. `assembly_services` (7-107) finds the one core `MachineControl` and `PortIo` service that an inline-assembly body may use in its Build or Product dependency scope. `attached_method_bounds` (109-337) checks that a method attached to generic data, once some code calls it, has owner type arguments that satisfy the declared type bounds. `boundary_calls` (339-808) lists every call that crosses a boundary trait and refuses calls whose trait is not "approved"; most of its lines check that the compiler's own flow tables agree with its typed trees. `callable_overloads` (810-912) refuses two named machines or two trait requirements with the same callable identity. `compiler_operations` (914-2749) recognises compiler-owned operations (Build declaration selections, byte predicates, `address_of`, inline assembly, wire `encode`/`decode`, x86 descriptor-table, segment-register, task-register and static-interrupt primitives) and checks that the declaration of each primitive still has the exact shape the compiler expects. `contract_dependencies` (2751-2862) answers whether a callee is independent of its caller in the call graph. `contract_identities` (2864-4215) serialises a generic machine template's signature, contracts, effects and termination into canonical bytes and hashes them into "commitments" for templates, specializations and captured applications. Nothing in the slice calls the proof kernel, and the slice contains no tests.

## Mechanisms

- **Three-state selection** (mcc.rs:25-51). `Selection` moves Missing to Unique to Ambiguous as services are seen. It serves the rule that an assembly body gets exactly one core service per dependency scope.
- **Selected-method fixpoint** (mcc.rs:126-215). The checker starts from every machine that is not a generic-data method, gathers the target symbols and static machine arguments of every call it can find in that machine, and marks them selected. It then repeats over generic-data methods that have become selected until a pass visits nothing new. It has no budget; it ends because each machine is visited once. It serves generic data methods: only methods some code calls are checked against their type bounds.
- **Sorted lookup by symbol key** (mcc.rs:398-411, 466-493). Machines and states are sorted by `(arena_index, generation)` and looked up with `partition_point`. Duplicate flow coordinates are found by sorting and comparing neighbours.
- **Closed-type search** (mcc.rs:1883-1917). `context_is_closed` walks the type symbols a type depends on, following generic data instances, and returns false at the first type, machine, conformance or value parameter or local. The visited set is a `Vec` searched linearly. It serves the installed interrupt context.
- **Call-graph independence search** (mcc.rs:2819-2861). `independent_declarations` pops declarations from a stack, asks `call_cycles::declaration_call_dependencies` for each one's owner and callees, returns false if any lookup fails or any owner is the caller, and true when the stack empties. No budget; the visited list is a `Vec`.
- **Canonical contract bytes and commitments** (mcc.rs:2887-3013, 3050-3245, 3535-3716, 3751-3852, 3939-4168). The code writes a machine template's name, supply mode, parameter kinds and bounds, declared type equations, conformance bounds, sorted state shapes, sorted service names, effect flags, a contracts commitment and a termination commitment into a byte vector, then hashes it under the domain tag `omega.machine-template.v3`. Specializations hash under `omega.machine-specialization.v2`, captures under `omega.machine-capture-application.v1`, requirement schemas are tagged `omega.requirement-schema.v3`. Type parameters are renamed by position (`$T0`, `$C1`, `$M2`, `$P3`, `$V4`, `$I5`, captured ones `$capture...`) and value parameters `$argument0...` (mcc.rs:3866-3906), so the bytes do not depend on authored parameter names. Lifetime binders are numbered by walking scope parents outward (mcc.rs:3908-3937). These bytes compare declarations for sameness; they do not prove anything about them.
- **Report fingerprints** (mcc.rs:3247-3251, 4170-4187). A 64-bit FNV-1a hash of a commitment or of selection strings, for reports.

## Surprises

- **Evidence on the three properties.** (1) Every decision in the slice is the code's own comparison or another validation module's answer; a grep of the file for `proof_admission`, `ProofNode`, `verify_obligation` and "certificate" finds nothing. The "commitments" in `contract_identities` are hashes of declarations, not checked evidence. (2) Text identity is heavy in `compiler_operations` and `contract_identities` (see above). (3) Placement repetition is small here; the repetition is per primitive and per encoder.
- **"Approved" means "declared once".** `approved_boundary_traits` (362-396) approves any boundary trait with a unique symbol and name. `validate_boundary_calls` can therefore only refuse a call when a boundary trait is declared twice. The diagnostic at 353 speaks of an "approved provider", which this code never looks for.
- **About 270 lines check the compiler against itself.** `checked_boundary_call_coordinates` (424-693) verifies that the checked flow tables and typed trees agree (span sizes, duplicate coordinates, owners). These are internal invariants reported as user diagnostics beginning "provider approval checked flow ...". They are not language rules.
- **Unused record fields.** `BoundaryCallCoordinate` stores `machine_symbol`, `target_state_symbol`, `boundary_signature_symbol`, `statement_index` and `call_ordinal` (414-422), but within this slice only `boundary_trait_symbol` and `state_symbol` are read (350-355). The function that builds them is private to the module.
- **x86 hardware knowledge in the source checker.** The slice hard-codes GDT word limits (1..=8192 at 1504, 2..=8192 at 2326), a 104-byte task state (2249, 2332), a 10-byte pseudo-descriptor (1544, 2255, 2338, 2714), six segment registers (1407-1414), and `lgdt`/`sgdt` access rules (2694-2699). The two GDT lower bounds differ (1 for segment reload, 2 for task activation) with no comment.
- **Two recognition routes for Build operations that disagree on resolution.** `has_explicit_build_argument` requires `!call.target_symbol.is_valid()` (1052), so a Build operation is a call that did not resolve. `build_product_request_intrinsic` uses `call.target_symbol` to find a signature in `BuildBindingOperations` (1127-1146), so it needs a resolved call. Provider selection also allows 2 or 3 value arguments (1040) while the other operations require exactly 1 (2549-2552).
- **An admission claim's commitment is its name.** `accepted_template_commitment` (3307-3314) returns `machine.name` for `AdmissionClaim` machines. That string is then folded into capture and specialization digests (3605-3611, 3697-3703).
- **The template bytes name a bound's trait by bare string, the signature bytes by hermetic identity.** `canonical_template_contract_bytes` writes `bound.trait_name` (3136); `encode_state_signature` writes `normalized_hermetic_symbol_identity(bound.trait_symbol)` (3964-3971). Two traits with the same name in different modules encode the same in the first and differently in the second. The machine itself is written as its bare name, with no path or package (3070). Service reaches are bare names in both (3197, 4029).
- **State names and state order are not part of a template commitment.** `encode_state_shape` (4115-4147) writes parameters, return type and contracts but no name, and the shapes are sorted (3161). Machine contracts are bound using only the first state's parameters (3217-3221).
- **Two different tag tables for one enum.** `TypeParameterKind` is numbered Type 1, Const 2, Machine 3, Proposition 4, Value 5, Implementation 6 at 3081-3088 and Type 1, Const 2, Value 3, Machine 4, Implementation 5, Proposition 6 at 4098-4105.
- **Mixed framing in the byte encoding.** Some fields are length-prefixed (`encode_identity_text`, 3718-3725) while others in the same stream use terminator bytes `0xff`, `0xfe`, `0xf9`, `0xfb`, `0xfd` and `0` (3071, 3098, 3114, 3153, 3164, 3203, 3863). The carry property is written as unframed display text followed by `0` (3860-3863).
- **The report fingerprint does not separate its lists.** `specialization_selection_report_fingerprint` (4170-4187) hashes template, type, const, machine and evidence argument strings as one flat sequence, so `(["a"], [])` and `([], ["a"])` give the same value. It is used for reports.
- **Whole-program inference is rerun per query.** `prepared_template_for_symbol` (3268-3286) calls `crate::infer_operational_may` and `crate::infer_service_reaches` on the entire program each time someone asks for one template's fingerprint or commitment. In `prepare_specialization_contract_identities`, captures call `prepare_template_contract` every time (3418) while specializations use a cache (3442-3462).
- **Debug printing inside the checker.** `static_interrupt_context` writes `INSTALLED_CONTEXT ...` lines to stderr under `crate::trace_flags::trace_installed_context()` (1598-1618, 1630-1635).
- **Small oddities.** `classify_statement_call_intrinsic` ignores its `_program` argument and passes a `target_symbol` it has just shown to be invalid (2486-2498). `boundary_state` already refuses a public unspecialized declaration (1216), and its callers test `is_public` again (1421, 2186). `exact_symbol_owners` (369-373) counts rows with the definition's own symbol, so it is at least 1 by construction. `validate_exact_boundary_requirement` also refuses a requirement whose symbol equals any typed state's symbol (778-784), a collision check between two different kinds of declaration.
- **The header promises more than the slice holds.** The comment at 1-6 lists denotational calls, effects, fact citations, invocations, result overloads and terminal transitions; none of those modules starts before line 4216.
