## What this code is for
DC is the "declarations" group of the old validation crate. It holds nine inline modules: `data_queries`, `declaration_visibility`, `definition_facts`, `selection_authority`, `selection_resolution`, `source_completion`, `standard_declarations`, `state_signatures`, `symbols` (with `machine` and `top_level`), `transitions` and `type_aliases` (DC:1-6 header comment). It checks that a public interface or public const or conformance header does not expose a private declaration (DC:119-349). It turns `requires` facts on `data` and `domain` definitions into entries of a `FactPlan` with places and dependencies (DC:364-893). It checks that a package selecting another package's declaration declared it as a direct dependency (DC:905-951) and normalizes each selection into a requester/owner request (DC:988-1105). It resolves late-bound call selections inside terminal-call targets (DC:1336-1428). It discovers or accepts a "process exit" completion role (DC:1580-1643). It validates state signatures, trait requirement signatures, machine-parameter requirement signatures and contract shapes (DC:1818-2410). It builds per-machine and top-level name tables and reports duplicate members, states, data, machines and traits (DC:2412-3040). It validates terminal calls (`transitions`) for result-shape agreement and argument checks (DC:3042-3492), and type aliases (DC:3494-3567). Almost every check here is a structural/name/handle comparison; nothing here calls a proof kernel.

## Mechanisms
- Place building for definition facts (DC:586-681, 740-797, 695-705): converts an expression in a `requires` fact into a `PlaceHandle` with `Field`, `Case{variant}` and element segments. It uses resolved symbols first and falls back to a member-name lookup (`facts::resolve_place_member_symbol`) and, for domains, to a field/variant name match on the target data type (DC:799-835). Serves per-field `requires` on `data` and `domain` refinements.
- Dependency collection (DC:505-546): a generic traversal over an expression that records each leaf place (`SavedSubject`, `Name`, `Member`, `Indexed`) and recurses through other nodes via `expression_traversal::children`. A `Member` whose receiver is a `Call` recurses into the receiver instead of recording a place.
- Selection normalization (DC:988-1105): a decision tree over the source file origin (Toolchain / ToolchainContract / User), target kind and symbol package identity that produces a requester/owner pair. It serves package dependency checks (direct-dependency rule).
- Authority comparison (DC:1107-1199): captures the dependency scope as a sorted `BTreeMap<requester, Vec<owner>>` and compares retained to current per requesting package, so cached results can be invalidated when package dependencies change.
- Specialization unwinding (DC:1264-1311): walks from a specialized machine or state back to its generic template, iterating at most `machine_specializations.len()+1` times; the bound is the cycle detector.
- Generic-instance field mapping (DC:1429-1528): zips instance members with template members and maps one instance field symbol to the template field symbol, only if the whole shapes match.
- Nested signature scope (DC:2103-2183): recursion over machine-parameter requirements, building a growing local type/lifetime parameter scope (dedup by symbol / lifetime equality), no stated depth bound beyond the finite data.
- Name tables (DC:2447-2558, 2720-2909): `MachineSymbols` and `TopLevelSymbols` collect names in vectors and look up by linear scan (`named_value`, DC:3023-3039), with `SymbolKeyMap<&str,...>` maps for duplicate detection.
- Terminal-call environment propagation (DC:3065-3156): computes per-target, per-argument value environments: guard-narrowed (positive) or fall-through-narrowed (continuation) environment, then for each argument expression invalidates paths possibly written by calls in it (`expression_may_write_paths`) or invalidates all unknown writes. Serves terminal calls with `guard` and `continuation`.
- Caller-site memo structures (DC:2652-2683): `CallerSiteCaches` with `Mutex<HashMap>` for tracked origin machines, site statements, prefix site entries, and completed state write summaries (`Vec<String>`). Only declared here, filled elsewhere.

## Surprises
- Name-keyed vs symbol-keyed contradiction: `MachineSymbols` stores symbols but looks up by name and accepts a symbol only if its stored name text equals the spelling (DC:2613-2621); a symbol whose name differs becomes `invalid()`, which then makes `has_member` false (DC:2568-2570). Duplicate-member detection only fires when the first occurrence had a *valid* symbol (`or_insert(symbol.is_valid())`, DC:2514-2516, read at DC:2486-2490 with `unwrap_or(false)`), so a first occurrence with an invalid symbol hides a duplicate. Same for states (DC:2531-2550).
- `member_symbols` and `owned_data_symbols` are populated with identical content (DC:2520-2527), and `member_verdicts` / `owned_data_verdicts` are both filled the same way (DC:2514-2519): both "duplicate member" and "duplicate owned data" fire on the same condition, so a second owned datum with the same name gets two error messages.
- The "duplicate data" diagnostic is emitted in two places: for data in non-primary source files (DC:1724-1735, when more than one calling-vocabulary source file exists) and in `TopLevelSymbols::build` (DC:2760-2765). The first does not look at names at all: it flags every data definition in the later source files.
- `validate_calling_vocabulary_uniqueness` skips the first path in a `BTreeSet` ordering (DC:1720), so which file is "the original" depends on path sort order, not source order.
- `is_core_vector` (DC:1739-1745) and the placeholder machine test (DC:1756-1767) identify a library type by data name `Vec` plus the file name `vec.omg` under a toolchain package root; the placeholder check requires exactly one state with zero statements. So the compiler special-cases library `Vec` surface machines.
- `nominate_source_completion` (DC:1619-1643) hard-codes the trait name `Console` as the process-exit role candidate during discovery (DC:1625), while the accepted path takes the name from a caller-supplied `declaration_path` (DC:1601).
- Specialized machine copies are skipped when collecting terminal-call selections (DC:1341-1343) and re-resolved via `authored_callable`, with a consistency check across copies (DC:1245-1257). The authors treat specialization as producing copies that must agree.
- `data_field_type_by_symbol` (DC:35-54) scans every field of every data definition on every call (linear, no index), unlike `memoized_data_definition_lookup` just above it.
- `CallerSiteCaches` (DC:2652-2660) puts `Mutex<HashMap<...>>` caches keyed with tuples `(SymbolHandle, u8, usize, usize)` into the validation inputs; it is a hidden, mutable memo (ratcheted against in the project rules) and `complete_state_summaries` stores `Vec<String>` of written paths. `record_completed_state_writes` keeps the first value written (`or_insert_with`, DC:2680), and a poisoned lock silently returns None / skips writing (DC:2668-2670, 2679).
- `selection_authority::RecordedDeclarationAuthority::capture` refuses (Err) if the authority cannot export a complete scope (DC:1119-1121), the one place where "cannot tell" is turned into a refusal.
- `cross_expression_effects` (DC:3138-3156) conservatively invalidates on unknown writes (see Accepts section); it is a fail-safe default.
- Terminal-call result agreement uses `ResultShape::Primitive(type, ArithmeticDomain)`; data types compare by symbol only, so generic arguments are not compared (DC:3239); other shapes (generic, array, slice, reference) give `None` and skip (DC:3241).
- `validate_declaration_visibility` calls `finish_strict_diagnostics` (DC:235, 950): diagnostics are gathered and returned as a `Result`, i.e. refuse-on-any.
