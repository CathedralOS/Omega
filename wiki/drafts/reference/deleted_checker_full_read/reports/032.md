## What this code is for

This file is the contract prover of the old checker: the code the contract checks call to ask "do the facts known at this point prove this `requires`, `ensures` or domain membership?" (ccp:1-28). It has three public entries: a Boolean expression against a set of fact contexts (ccp:5897-5917), a callee's Boolean contract expression at one call site (ccp:6065-6166), and one contract fact by payload kind (ccp:6168-6279). Around those it holds the helper provers: domain membership from live assigned values (`assigned_values`, ccp:35-597), scalar values of captured call operands (`captured_values`, ccp:602-759), byte and case predicates at a place (`place_predicates`, ccp:929-1320), and the truth of a stored Boolean (`current_boolean`, ccp:5446-5779).

The largest part (`call_guarantees`, ccp:1322-5445, about half the file) decides when a completed call's `ensures` may be used by the caller, and then uses it either by matching it structurally against the obligation or by handing it as a hypothesis to an arithmetic implication engine in the `validation` crate. It also contains the rule that a recursive call's guarantee is usable only after a strictly decreasing rank edge (`induction`, ccp:3377-3446) and the handling of const-generic machine arguments (`static_operands`, ccp:3447-4144).

The last part (`propositions`, ccp:6413-6555, and `instruction_effects`, ccp:6558-8150) proves proposition applications: transparent propositions by evaluating their body, and "instruction effect" propositions (an inline-assembly register operation or an atomic release store was performed with these operands) by finding the performed event in the flow facts and issuing a receipt that can be spent once.

Every function returns `bool` or `Option`. The file emits no user diagnostic; its only output text is `CHECKSITE` trace lines on stderr behind a trace flag (ccp:1035-1062, 1083-1095, 1135-1278). There are no tests in the file.

## Mechanisms

- **Element-by-element extent proof** (ccp:94-142). For the first range or runtime-index segment of a place, it replaces the segment by each fixed index in the extent and proves the domain for each. The extent comes from the range bounds, or for the whole extent from the declared closed collection length. There is no budget on the loop. It serves domain membership of ranges and dynamically indexed elements.
- **Domain predicate evaluation over live values** (ccp:326-596). A recursive walk over a domain's facts that evaluates each expression fact with the scalar evaluator, reading leaves from live assigned values, and recurses into nested memberships. A symbol list (`active`) stops recursion. It serves `domain` refinement checks at initialisers and calls.
- **One fact walk with two predicates** (ccp:150-189). `live_fact_at_place` scans all facts of all selected contexts with a payload test and a place test. Membership, carry permission and carry origin all use it.
- **Captured-scalar agreement** (ccp:617-758). For each captured value of an operand it builds the fact contexts of the right frontier (the producer's statement plus one for a detached copy, the consumer's statement for a live view) and requires all places and all values to agree.
- **Guarantee availability scan with memo** (ccp:3001-3358). `scan` walks the live contexts for callee `ensures` facts; `admit` runs the use-independent checks; `StateGuarantees` remembers each admission per (statement, ordinal, fact, expression) for one state's check (ccp:3092-3213). No size limit.
- **Structural predicate matcher** (ccp:5198-5277). Compares two expression trees from two declarations node by node, mapping each leaf to a literal or to a place in the caller's namespace and through `captured_place`. It has a pending-pair list against cycles. It knows one logical step: a requirement may match either side of a guarantee's `&&`. It has no commutativity and no implication between different comparisons.
- **Arithmetic adapter** (ccp:1363-2635). Translates admitted expressions into `ScopedArithmeticExpression` with one binding per leaf occurrence, each leaf being an integer, a term, or an opaque atom named by a string. It gathers hypotheses from the caller's context facts, from guarantees available at the use, and from the contexts captured at each earlier store (ccp:1622-1722), then asks `validation::scoped_arithmetic_implication`. Value identity across copies is delegated to flow (`value_origin_at_call`, `value_origin_before_statement`). No budget in this file.
- **Constant propagation to a fixed point** (ccp:4398-4428). Repeats, at most once per binding plus one, a pass that derives constants at places from predicates, and stops when no new place gained a value; then asks `boolean_predicates::proves`. If it does not settle it returns false.
- **Induction gate** (ccp:3386-3445). Looks up the termination check's rank-arrival judgment and requires a strictly decreasing edge at exactly this call. It serves `terminates by`.
- **Static const actual resolution** (ccp:3453-4143). Follows template chains with a seen list, validates the application tuple, and resolves a const projection through struct literals, array literals, const declarations (decoding the canonical encoding) or type parameters (opaque atom).
- **Predicate lowering with a step budget** (ccp:4259-4268, 5032-5041). `lower_callable_scalar_contract_predicate` is called with `&mut 4096`. This is the only numeric budget in the file.
- **Stored-Boolean query batch** (ccp:5470-5624). Lazily prepared caches (`OnceCell`) of Boolean facts with their places and of retained predicates, shared by several field queries at one point.
- **Proposition unfolding** (ccp:6456-6554). Evaluates a chain of transparent proposition applications, passing scalar argument values down, with an `active` list against recursion.
- **Instruction-effect evidence search** (ccp:7730-7974) with **query frames** (ccp:7976-8149). The query is unfolded into a stack of proposition frames so that an argument can be traced back to the source expression (`source_projection`, `scoped_value`). The search walks context facts, matches direct events or call completions, recurses into every exit of the callee, and builds a receipt tree. `overlaps` (ccp:7689-7708) implements once-only spending.

## Accepts or skips without proof

- **"Any context" suffices.** Membership, byte predicates, Boolean expressions and labels are proven when one of the supplied contexts proves them (`contexts.iter().any`, ccp:156, 373, 5907, 6197, 6396). `installed_case` returns the first case found in any context (ccp:523-548) with no agreement check, unlike `scalar_at_path`, which demands agreement (ccp:742-755). Whether this is sound depends on whether a context list is a conjunction of fact sets; I cannot tell from this file.
- **Trusting recorded facts.** Every prover here takes a fact's presence in a live context as truth. The file states the dependency: "Mutation invalidation owns their lifetime; this consumer neither replays a body nor assumes zeros" (ccp:37-38). The flow stage is the other check; it is not in this slice.
- **Carry origin**: any `CarryOrigin` fact at the place satisfies a `CarryOrigin` requirement; the origin carried is not compared (ccp:6256-6261). I cannot see another check.
- **Stored Boolean from contract facts without admission.** `ordinary_boolean_value_from` treats every `ContractBooleanExpression` fact at the place as holding, whatever its kind or origin (ccp:5693-5697); for `CallEnsures` origin it only remaps the subject place (ccp:5706-5709). The `admit` checks (ownership, stable inputs, capture preserved, independent or strictly recursive call, ccp:3290-3358) are not run on this route. The arithmetic route explicitly skips `CallRequires`/`CallEnsures` facts (ccp:1800-1805). I cannot tell whether flow already guarantees the same conditions for a fact left in the context.
- **Field route "recognized but false" still falls through.** `field_actuals::proves` returns `Some(false)` on mismatch (ccp:5793-5795), which skips the per-context route, but the evaluator fallback is still tried (ccp:6131-6165). `field_actuals::proves` also returns `None` ("not recognized") through `?` at ccp:5821, 5822, 5839 after it has recognised the requirement, which reopens the per-context route.
- **Any integer-returning call is an arithmetic term** (ccp:2526-2529), with no test of what the call is. Its arguments are bound as terms if admitted and skipped if not (ccp:2420-2424). How the engine treats the call node is in `validation`; cannot tell.
- **Leaves skipped while binding.** An occurrence whose primitive does not accept an integer literal is left unbound (`continue`, ccp:2331-2335) and the expression is still returned. The `predicate`/`term` gate (ccp:2200-2205) should already exclude such leaves outside call arguments; inside call arguments, cannot tell.
- **`&&`/`||` have builtin meaning by shape** for requirement and proposition callables (ccp:2841-2848), without looking at operands. The caller decomposes and checks the operands separately (`has_builtin_meaning`, ccp:2890-2898); that caller is outside this slice.
- **Dropped hypotheses.** A context fact, guarantee or predicate that fails to translate is silently skipped (ccp:1816-1836, 1584-1600, 4256-4342). These are premises, so skipping makes proving harder, not easier.
- **Literal and static inputs are preserved by definition** (ccp:4615-4617, 4653-4659) and stable by definition (ccp:4988-4990).
- **Exclusive-reference parameters pass the write-overlap test** (ccp:4644-4647, 4685-4692): a guarantee about a place the callee may write through an exclusive reference is kept, on the reading that it describes the post-state. The comment at ccp:4697-4700 states this.
- **Remainder**: `builtin_unsigned_remainder` does not check division by zero: "This adapter does not establish that obligation: the callee's `requires` and the independent admitted remainder certificate do" (ccp:2551-2557). The other check is named but outside this slice.
- **Casts**: `value_preserving_integer_coercion` accepts any fixed-integer to fixed-integer non-recast cast as preserving the value: "Source formation independently proves any narrowing" (ccp:2593-2598). Outside this slice.
- **Fallback to the family definition**: `domain_definition_for_instance(symbol, instance).or_else(|| domain_definition(symbol))` (ccp:441-444); the literal and byte-predicate grants at ccp:448-455 run before the generic/indexed refusal at ccp:456.
- **Refusals by default.** Most failed lookups return `false`/`None` (for example ccp:78-82, 1417-1423, 3165-3172, 4479-4485, 6076-6089). `contract_membership_place_is_accessible` returns `true` for non-membership payloads and for points other than `CallRequires` (ccp:6292-6306), which is a pass-through, not an acceptance.

## Surprises

- **Property 1 holds here with one nuance.** There is no call to `proof_admission`, `ProofNode` or `verify_obligation`; the word "certificate" occurs only in two comments (ccp:2555, 2860), one of them saying availability is "never a certificate's assertion". Arithmetic is delegated to `validation::scoped_arithmetic_implication`, which returns a three-valued judgment and no proof object (ccp:1769-1770). The nuance: instruction-effect proofs produce a receipt tree that is published into the flow facts (`InstructionEffectEvidence::publish`, ccp:7660-7687), so one kind of acceptance does leave a record; nothing in this file re-checks it.
- **A linear resource discipline inside the contract prover.** Instruction-effect evidence can be "spent": a second requirement cannot reuse the same performed event (ccp:7689-7708, 7717, 7791). For helper calls the receipt has one child per callee exit, and two receipts overlap when some pair of children at the same exit overlap. I did not expect once-only accounting of hardware events in this stage.
- **The code distrusts its own fact tables.** `owns_guarantee` re-checks that an `ensures` fact belongs to the resolved callable (ccp:3360-3375); `call_result_atom` re-checks the flow call row against the typed call site and an `authored_source_custody_valid` flag (ccp:1985-2037); `static_operands::tuple` re-validates the static application bindings on each use (ccp:3842-3918); `invocation_fact` demands uniqueness (ccp:4170-4171). These are authentication checks on data produced by earlier parts of the same stage.
- **Recursion soundness is handled.** A machine may use its own `ensures` at a recursive call only through `strict_recursive_call` (ccp:3312-3320). The decision reads the termination check's output, including the test that a diagnostic string is empty (ccp:3414-3416).
- **Possible unbounded loop.** `prove_domain_by_extent_enumeration` substitutes the collection length only when the range is exactly `0..usize::MAX` (ccp:114); any other `FixedRange` is enumerated to its own `end` (ccp:133-141). A range with a non-zero start and `end == usize::MAX`, if flow ever produces one, would iterate until the first failing element. Nested ranges multiply, since each element proof re-enters the same function through `prove_domain_at_place` (ccp:242). Cannot tell whether such a segment can occur.
- **Empty ranges are refused**, not vacuously accepted (`start < end &&`, ccp:136).
- **Header comment narrower than code.** The header says the call-entry prover first tries "a caller's case at the place a case test's subject names" (ccp:10-12); the code uses `place_predicate`, which also covers byte-predicate calls (ccp:6091-6115, 946-950).
- **Comment and code differ on `field_actuals`.** The comment says a recognised place requirement "returns Some(false) on mismatch and cannot use labels" (ccp:5793-5795). The evaluator fallback still runs after `Some(false)` (ccp:6156-6165), and three `?` exits return `None` after recognition (ccp:5821, 5822, 5839).
- **Dead distinctions.** `store_matches` returns `Option<bool>` but its only caller collapses `None` and `Some(false)` (ccp:6722-6725). `scoped_value` has `unreachable!()` in a `let … else` over a two-variant enum (ccp:8048-8051). `Callable::resolve` matches a `Proposition` arm it can never have selected (ccp:2691-2695). In `ExitArithmetic::value`, a missing call row inside the loop aborts the whole lookup with `?` instead of moving to the next candidate (ccp:1513-1518).
- **Hypotheses collected as a side effect.** In `call_guarantees::proves` the arithmetic hypotheses are pushed inside the closure passed to `any_available`, which stops at the first structural match (ccp:4491-4511, 4549-4559). The list is complete only when no guarantee matched, which is the only case that uses it; the correctness depends on that coupling.
- **About 200 lines are stderr tracing** inside the prover (`trace_capture_refusal`, ccp:1135-1278, plus ccp:1035-1062 and 1083-1095), dumping operand rows, loan resources and borrow parents. It shows that failures of captured case/byte predicates were being debugged at the time of deletion, and that this module reaches into borrow facts (`facts.borrow.call_loan_resources`, ccp:1243-1274). The prover also calls the borrow check (`shared_reference_observation`, ccp:997-999), and the header says the borrow check calls back into `call_guarantees` (ccp:27).
- **Property 3 is weaker here than in the sampling.** Source placements have mostly been normalised to `CanonicalPlace` before this file. What repeats is the use point (call entry, pre-store, exit, statement entry) and the kind of leaf (result, literal, static const, formal); see the repetition section.
- **Property 2 is mixed.** The authors were removing text identity (three comments say so), yet the bridge to the arithmetic engine names every unknown by a formatted string, so equality of two values in an implication is string equality of `Debug` output (ccp:2092 and nine other sites). Captured and current observations get different string prefixes (`instruction-capture`, `instruction-current`, `call-guarantee`), so the same place under two prefixes is two unknowns unless the explicit capture loop joins them (ccp:7124-7186).
- **Several independent routes for one question.** `live_contexts_prove_boolean_expression` asks three separate evaluators in turn (ccp:5932-5968); the call-entry prover asks four (ccp:6091-6165); a call requirement from a guarantee asks two (ccp:4549-4559). Each route has its own vocabulary of admitted expressions, so whether a contract is provable depends on which route its shape happens to fit.
