## What this code is for

This file plans the cleanup that runs when an owned value dies: at a state's normal exit, after a call returns, when an assignment overwrites an old value, and when a temporary inside an expression is finished. It does not decide which values die. An earlier ownership pass has already recorded "contextual cleanup dispositions" (`facts.contextual_cleanup.dispositions`), each saying "this root and path dies at this source occurrence"; this file turns each disposition into an ordered list of executable actions (`Discard`, `InvokeNominal` for a `dropped by` hook, `RetireHome`) plus a partition tree that says which variant cases each action applies to (cleanup.rs:187-610). Around that one shared planner sit six drivers, one per place a death can occur: state exits (`normal_edges`, cleanup.rs:1820-2775), call continuations for anonymous argument owners (`anonymous`, cleanup.rs:994-1387), assignment replacement (`replacements`, cleanup.rs:2851-3288), retained owners released with a reference (`retained_owners`, cleanup.rs:3330-3473), nested value calls and scalar-call temporaries (`temporary_actions`, cleanup.rs:3474-4926) and borrowed descriptor temporaries (`temporary_descriptors`, cleanup.rs:4927-5040). A further part recognises one narrow machine shape, a single-state, empty-body, Unit machine whose parameters are affine or linear records with a cleanup hook, and checks that the caller's `requires` clauses state the boolean field facts that each hook's `requires` asks for (cleanup.rs:1556-1819, 5106-5245). The file's failures are almost all internal refusal strings (`&'static str` or `String`) raised when two independently built tables do not line up; only one user-facing `Diagnostic` is built here (cleanup.rs:1692-1712). Nothing in the file calls a proof kernel. Three unit tests pin `value_call_context` (cleanup.rs:3496-3626).

## Mechanisms

- **Disposition to actions (cleanup.rs:210-610).** Input: one disposition (root, path, exclusions, source occurrence). The function collects the moved sub-paths (exclusions that are reachable), the selected hooks, and extra split points from selection transfers, then asks `validation::reconstruct_case_selected_cleanup_partition` for a partition of the remaining region into regions with case conditions (cleanup.rs:539-560). Each region becomes an `InvokeNominal` if its path equals a hook path (binary search, cleanup.rs:587), otherwise a `Discard`. The budget argument is `usize::MAX` (cleanup.rs:546), so the search is unbounded here. Serves automatic cleanup of partially moved values and variant payloads.
- **Three-valued case reachability (cleanup.rs:253-254, 295-298, 337-350, 419-424, 547-558).** Each path is `Inactive`, `Selected` or `Runtime`. Inactive paths get no action; runtime paths keep a case condition evaluated at run time. The evidence comes from `flow::CleanupCaseEvidence`; this file only consumes it.
- **Partition tree retention (cleanup.rs:612-726).** Copies the partition nodes into arenas, pre-allocating node handles so children can be referenced by position, and checks with a `covered` bit vector that leaves and actions correspond one to one.
- **Result tree walk (cleanup.rs:2322-2483).** Recursive descent over the scalar computation that produces a state's returned value, in step with the tree of completed captures (`completed.nodes[cut].branches`). An `active` set of `(arena_index, generation)` detects cycles. Each non-dispatch leaf plans its own cleanup using that arm's completed storage (`completed_result`). Serves `match`-valued returns where each arm moves different things.
- **Declared-order merge (cleanup.rs:2785-2822).** Takes the actions belonging to one home, maps each action's lowered path back to source place segments (`checked_path_segments`), obtains a sort key from `flow::cleanup_path_order`, sorts, and writes the sorted actions back into the same positions. Used when a home has selected sub-regions (cleanup.rs:2650-2665, 3258-3271).
- **Select then install (cleanup.rs:3833-4014, 4235-4303).** `sequence_actions` walks an operation list, recursing into nested value calls' operand and completion sequences, and records `(position, actions)` pairs without mutating; `install_sequence` later writes them back by position. `OperationSequence` abstracts a plain slice and an arena-backed operand sequence (cleanup.rs:3738-3779).
- **Reverse completion ordering (cleanup.rs:1294-1296, 4727-4747, 5032).** Temporaries die in reverse order of the statement's authored completion order (or of binding ordinal for descriptors).
- **Owning machine walk (cleanup.rs:5070-5083).** Walks symbol parents until a `Machine` symbol is found; returns the state symbol itself if none is found.
- **Diagnostic graph dump (cleanup.rs:3633-3725).** Worklist traversal with a visited `Vec` over operand captures, copies, retentions and leaves, printing `Debug` forms. Only used when the trace flag is on (cleanup.rs:4565-4571).
- **Syntactic requirement matching (cleanup.rs:1750-1818, 1663-1678).** Reduces a `requires` expression to `(field, bool)` if it has one of five shapes, then tests set membership. No implication, no conjunction splitting, no solver.

- Refusal reasons are bare string literals (`&'static str`), and the tests match on the literal text: `Err("missing executable parameter catalog")` (cleanup.rs:3595), `Err("surviving bodies disagree on the value-call operand namespace")` (cleanup.rs:3623).
- `finalize_completion_actions` builds site labels from `program.symbols.name(machine)` and `name(state)` (cleanup.rs:4421-4425, 4429-4433, 4504-4510, 4835-4840) and `expressions(program).display_name(...)` (cleanup.rs:4721). These are for messages only.
- Trace phases are string labels, 17 of them in one function (cleanup.rs:1121-1383).
- No place in this slice decides meaning from a name or a string prefix. Values and storage are identified by symbol handles, expression handles, binding ordinals, `(statement_index, call_ordinal)` coordinates and segment lists. Comments say so explicitly: completing the roster "does not infer cleanup from a callee's name" (cleanup.rs:3480-3481), and "equal expressions or return types cannot identify a second evaluation" (cleanup.rs:2733-2735).
- One identity is by memory address: `std::ptr::eq(candidate, call)` finds which state a call row belongs to (cleanup.rs:4498-4503).

## Surprises

1. **No proof kernel, and the one "cannot prove" diagnostic involves no proof.** The message "cannot prove automatic cleanup requires ..." (cleanup.rs:1705-1711) is produced when a tuple `(parameter index, field identity, bool)` extracted from the hook's `requires` is not found among tuples extracted from the caller's `requires` (cleanup.rs:1663-1678). Extraction is purely syntactic (cleanup.rs:1750-1818). A caller that states the fact in any other form (a conjunction, a double negation, a fact implied by another) does not match. If any of the caller's `requires` is not one of the five shapes, `nominal_cleanup_caller_boolean_requirements` returns `None` (cleanup.rs:1631) and `build_nominal_affine_unit_cleanup_machine` returns `None` with no diagnostic (cleanup.rs:5194-5200). This supports sampled property 1.

2. **Property 2 mostly does not hold here.** This file identifies things by handles, ordinals and coordinates, and its comments warn against name-based or shape-based identity (cleanup.rs:765-769, 2733-2735, 3480-3481). The cost is a different one: the same value is known to five tables (contextual dispositions, flow control calls and operands, structural value roots, scalar computations, operation plans), and this file re-joins them by `(state, statement_index, call_ordinal)`, expression handle and binding ordinal, using linear scans with "exactly one match" checks. Most of the refusal strings in the Rules table are failures of those joins, not language errors.

3. **The refusal message in `finalize_completion_actions` can name the wrong site.** `refusal` is one mutable string, overwritten before some fallible steps (cleanup.rs:4383, 4421, 4429, 4462, 4511, 4553, 4562). Many exits are bare `?` or `return None` that do not set it: `shapes.add_type(...)?` (cleanup.rs:4467), the span lookup (cleanup.rs:4470), the type mismatch (cleanup.rs:4475), `source_call.statement()?` (cleanup.rs:4497), the state search (cleanup.rs:4503). When one of these fails the user sees whatever was written last, for example the last value call's "missing operand or completion cleanup correspondence" from a different machine and state, or the previous scalar call's site.

4. **State-graph and sequence bodies disagree on a dying parameter with no structural plan.** The sequence path returns `Some(None)` and skips the disposition (cleanup.rs:2158-2164, 2578-2580); the state-graph path returns `None`, which becomes "normal cleanup owner has no retained structural storage" (cleanup.rs:2687-2690, 2098, 2575-2576). The same program fact is skipped in one body form and refused in the other.

5. **`nominal_cleanup_target_matches` contradicts itself on access.** It requires the source receiver reference to be readable and exclusive (cleanup.rs:5297-5298) and then accepts a plan parameter with `WriteOnlyBorrow` access (cleanup.rs:5316-5320). It also accepts a plan with no structural parameter at all (`len() <= 1`, cleanup.rs:5313) although `nominal_cleanup_shape` requires exactly one source parameter (cleanup.rs:5267).

6. **The "nominal affine Unit cleanup machine" is a very narrow special case.** It must have exactly one state and an empty body (cleanup.rs:5114, 5125); every parameter must be a non-generic record with a hook. The diagnostic hard-codes "after statement 0" (cleanup.rs:1701) and `direct_boolean_field_requirement` resolves places at statement 0 (cleanup.rs:1798). The plan it returns holds only machine, state and caller requirements (cleanup.rs:5240-5244).

7. **Planning mutates earlier plans.** `normal_call_completion` clears the `discard_on_return` flag on producer operations it finds (cleanup.rs:1166-1172, 1345-1348). A later planning step therefore changes what an earlier step published.

8. **Dead branch.** At cleanup.rs:351-356 the `continue` cannot run: the guard at cleanup.rs:332-336 already ensured one path is a prefix of the other, so when `strip_prefix` fails the `if` at cleanup.rs:352 is always true and returns the error.

9. **Possible gap in "selected normal death".** The scalar-call block loops over dispositions matching statement and call ordinal with any target (`..`, cleanup.rs:4603-4611), then calls `selected_actions`, which also requires `target_symbol == call.target_symbol` (cleanup.rs:3368-3370). If the targets differ, `selected_actions` returns empty actions, the owner is still pushed (cleanup.rs:4677-4682), and the "has no selected normal death" check (cleanup.rs:4714-4725) passes because it tests only membership.

10. **An unrestricted reference temporary with no disposition is refused.** `descriptor_retirement` returns an empty list for unrestricted references (cleanup.rs:1534); the caller pushes an owner only when the list is non-empty (cleanup.rs:4700), so the operand then fails the "no selected normal death" check (cleanup.rs:4714-4725). A linear one exits through `?` (cleanup.rs:4699) with a stale message.

11. **Confusing alias.** `retained_owners` imports `disposition_actions as selected_regions` (cleanup.rs:3336) while a different function `actions::selected_region` exists (cleanup.rs:123). The call at cleanup.rs:3380 reads as a region query and is the full action planner.

12. **Debug output written straight to stderr from the checker.** Three `CHECKSITE` paths are gated by `validation::trace_flags::check_sites()` (cleanup.rs:1255-1269, 2627-2641, 4565-4571), and `normal_call_completion` records 17 string-labelled trace phases (cleanup.rs:1121-1383). This reads as instrumentation added while chasing hangs or mismatches.

13. **Costs.** Lookups are linear scans inside loops: all dispositions per value dependency (cleanup.rs:3410-3434), all states per scalar call node to find a call by pointer equality (cleanup.rs:4498-4503), all data definitions and members per requirement (cleanup.rs:1803-1810), repeated passes over operations per owner (cleanup.rs:1320-1363). `BTreeMap`/`BTreeSet` keyed by `(arena_index, generation)` appear at cleanup.rs:2217, 2291, 2373.

14. **Budget parameters are unlimited.** Both partition reconstruction calls pass `usize::MAX` (cleanup.rs:546, 2848).

15. **`machine_has_content_evidence` compares different field pairs for the two fact kinds**: `fact.machine_symbol/state_symbol` for reshuffles and `fact.plan.owner/plan.callable` for partition returns (cleanup.rs:1404-1415). The second treats the state symbol as the "callable".

16. **This file is a lowering planner living in the checker.** It decides executable action order, storage sources and partition trees for the emitter. A program is refused when this planner cannot rebuild a plan from the checker's tables, so the old checker's verdict depended on planner completeness as well as on the ownership rules themselves.
