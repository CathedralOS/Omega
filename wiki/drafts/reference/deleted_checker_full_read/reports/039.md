## What this code is for

This file is the old checker's operator-use check. Another stage has already chosen which operator declaration each `+`, `==`, `[]`, Match comparison or `Namespace::op(...)` call means and recorded that in `facts.operators`; this file reports on those choices and checks three things about them (header, 1-5). First, `check_operator_resolution` (2836-2881) turns the recorded "ambiguous" and "inadmissible" resolution issues into diagnostics and checks that a Match comparison has one selected two-operand Bool operator. Second, the `destinations` module (13-376) refuses a binary operator expression whose float result format (`f32` or `f64`) differs from the float format of the place it is delivered to. Third, the `requires` module (1157-2829) tries to prove each `requires` clause of the selected operator at each use, using the facts that hold at that invocation, and reports each clause it cannot prove. The `float_semantic` module (377-1152) is a helper for other checks: it turns a float predicate such as "is finite" into a resolved term tree so that an observed Boolean fact can establish a required float predicate by structural equality of terms, and it decides closed float predicates by evaluation or by an interval image over an integer type's range. The `requires::invocation` submodule (1230-1646) defines `InvocationContexts`, the selector that says which fact contexts describe the operands of one invocation; it is exported (2831-2834) and shared with ordinary call `requires` checking. The file contains no tests.

## Mechanisms

- **Float-format inference for an operator expression** (`result_primitive`, 281-365). Computes the float format an expression produces. For a binary node it looks up the recorded operator use for that expression, state and statement by a linear scan of all uses (302-304). A `Resolved` use gives the candidate's return type; `BuiltinFallback` and "no row found" fall through to a structural rule: for `+ - * / %`, equal operand formats give that format, and if only one side is known that side's format is used (326-330). No budget; recursion follows the expression tree. Serves the "landed float format" rule.
- **Float semantic terms** (377-1152). `semantic_term` (789-917) builds a `FloatSemanticTerm` from an operator's sealed semantic equation: applications of catalog operations, projections of source values, format constants, integer literals, integer sources, float literals. It substitutes operator formals with operands and then with the outer call's actuals (919-979), and composes through a nested selected operator's "raw" result equation (812-830). Every entry point starts a work budget of 1024 steps (544, 602, 722); each recursion and each cast-stripping step subtracts one and returns `None` at zero (631, 666, 799, 932, 944). Serves float predicates such as finiteness in `requires` clauses and conversions.
- **Closed evaluation of a term** (`closed_semantic_result`, 662-707). Evaluates a term whose leaves are literals by calling the catalog row's `kernel_discharge` and keeping only `.result`.
- **Interval image for integer-to-float conversion** (`ordered_meaning_image`, 627-660, used at 619-620). For a term `convert(format, integer)`, an integer literal gives a point interval; a symbolic integer source gives the full bounds of its carrier type (646-649). The catalog row maps the bounds to float meanings and a predicate is decided over the interval. Facts that narrow the integer are not used. Shares the 1024 budget with the closed evaluation that ran first (602-619).
- **Invocation context selection** (`InvocationContexts`, 1260-1613). Finds the one capture row for an invocation (operator, named operator, or ordinary call), then for a clause collects the formals it mentions and intersects the fact contexts captured for those operands (1497-1521). A clause that mentions no formal gets the invocation's entry-constraint contexts (1522-1526). No budget. Serves operator `requires` and, through the export at 2831-2834 and `from_call` (1280-1305), ordinary call `requires`.
- **Boolean decomposition with pluggable leaves** (2223-2284 for proof; `boolean_expression_has_polarity` called at 1758 for falsity). `and`/`or`/borrow structure, four leaf provers tried in order (2249-2273).
- **Closed-literal clause evaluator** (2488-2718). Substitutes operand expressions for formals, reduces to integer, float or Boolean literals, picks a float format (2608-2651: formal's declared type, else a literal's suffix, else `f64`), converts integers to that format with round-to-nearest-even (2705-2714), and compares with NaN-aware exact floats (2669-2689). No recursion budget.
- **Unique "finite" operator lookup** (`finite_float_semantic_term`, 742-767). Scans all operators for those whose catalog row is the `Finite` single predicate and returns a term only if exactly one exists.

## Surprises

1. **No proof-kernel call anywhere in the file.** A search of the file finds no `proof_admission`, `ProofNode`, `verify_obligation` or certificate. Every acceptance is one of: structural term equality (522-523), label string equality (1812-1813, 2352-2354), literal evaluation (2258, 2139-2144), a scan of context facts (2809-2827), or a yes from another checker module (1580, 2260, 2207, 2303). The one call with "kernel" in its name is `operation.kernel_discharge(&operands)` on a `numerics::float_semantics_catalog` row (699-701); the code keeps `.result` and drops the rest of the returned discharge.

2. **`operand_for_parameter` does not do what its comment says** (2569-2600). The comment says that without a captured receiver "operands count only the non-self formals". The code increments `positional_operand_index` for every parameter and never tests whether a parameter is `self`, so both branches return `operands.get(parameter_index)`. When the operand list is one shorter than the parameter list, each formal is bound to the operand one position off. The closed-literal evaluator (2562) and the float-format chooser (2637) use this binding, so a clause could be evaluated against the wrong operand's literal. `positional_operator_parameters` (170-179) in the same file does drop parameter 0 in that case, so the two helpers disagree. Cannot tell whether a shorter operand list reaches this function.

3. **`closed_scalar_value` can recurse without bound** (2548-2567). A formal's name is replaced by its operand and the function recurses on the operand with the same parameter list. The comment (2542-2547) says caller names never match a formal. If an operator's own body uses that operator with its own formals as operands, the operand is a `Name` whose symbol is a formal, and the recursion does not end. There is no work budget here, unlike the float-term code. Cannot tell whether such a self-use can reach this check.

4. **Statement-position named operator calls with `requires` are always refused** (1995-2028). The message says "no checked capture can prove" them. The same construct is still given a float-format check in the destination pass (47-63). This is a whole placement the checker could not handle and chose to reject.

5. **Parameterized domain memberships in an operator `requires` are never provable** (2147-2149). The fallback prover at 2113-2120 runs only for expression facts, so `requires value in Domain<args>` on an operator is reported at every use.

6. **`closed_operators_are_builtin` accepts by absence** (2732-2753): an expression with no recorded operator use passes. Together with the comment at 384-386 that proof-position operations have no use row, the guard on reflexive and literal acceptance may check nothing for contract expressions. Cannot tell.

7. **Two comments disagree about boundary operators.** 2424-2426 says a comparison that selected "a checked or boundary-operator meaning keeps the label/fact path". 2722-2723 and the code at 2763-2769 treat a `Resolved` selection of any `is_boundary` binding as builtin and let the literal evaluator apply the spelled operator's ordinary meaning. These may be two different notions ("boundary operator" versus "boundary machine"); the file does not say.

8. **Float literals are read with different accessors in the two evaluators.** The term builder uses `literal.value_f32()` for `f32` and `literal.landed_f64()` for `f64` (837-840). The clause evaluator uses `literal.value_f32()` and `literal.value_f64()` (2701-2704). Cannot tell whether `landed_f64` and `value_f64` differ for a literal with an `f32` suffix.

9. **The "is this known false" query matches text from two different renderers** (1798-1813): the required label is built from `render_proof_expression` operand labels, the fact side is `display_name`. Both soundness (two different values that render alike) and completeness (same value rendered differently) depend on those renderers.

10. **The Match-equality diagnostic says "floating"** (2864) but the test does not look at the type: any non-`Expression` occurrence without a candidate gets it, and any such occurrence that is not `Resolved` gets the second message (2868-2877). The code relies on the earlier stage creating these rows only for cases where that wording fits.
