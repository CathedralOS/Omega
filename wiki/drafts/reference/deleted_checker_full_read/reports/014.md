## What this code is for

This slice is not a proof checker. It is the part of pipeline stage 04 (typed trees to typed trees) that fills in types and resolves generic calls before any checking happens. `constructed_results.rs` computes the result type of every array literal, constructor, borrow, recast and call, children before parents, and stores it on the expression (`retain_constructed_result_types`, CR:762-852). `contextual_and_requirement_calls.rs` handles calls that pass a machine as a generic argument and calls to trait requirements: it works out which concrete machine or trait-member instance each call means, clones a specialized machine when none exists yet, and rewrites the call's target symbol and static arguments in place (CC:1834-2003, CC:2928-3137, CC:3859-4081). `data_and_product_operands.rs` has two halves: `data_applications` turns a generic data type applied to arguments (such as `List<T>` with a concrete `T`) into a concrete data definition by substituting into every field (DP:112-884); `product_operands` takes the operand graph that a build declaration supplies (a named boundary trait, a provider implementation, or a native-binding requirement) and translates it into typed-tree types, expressions and static applications (DP:886-3033). Almost every refusal in the slice is a structural one: an arity mismatch, an ambiguous or missing declaration, a conflict between two inferred arguments, or an internal table that "lost" a record. None of the three files calls the proof kernel, and none contains a test.

## Mechanisms

- **Child-before-parent result typing** (CR:594-677, 762-852). `occurrences` gathers every array literal, constructor, borrow, recast and call from machine contracts, state contracts, state statements and callable contract scopes, in post order (`visit_post_order`). The driver then computes one type per occurrence and stores it with `set_constructed_value_type_reference`. A parent reads its children's stored types through `validation::expression_result_type_reference`. No budget. Serves expression typing.
- **Constructor argument inference** (CR:935-1162). Proposals for each type or const parameter come from three sources: the constructor's authored application, "peers" (the other side of `==` or `!=` in a contract, or the declared argument type of a mathematical application, CR:372-438), and structural matching of field types against field value types (`infer_static_bindings`). All proposals for one parameter must share one `applied_type_identity`. Serves generic `data` construction.
- **Lifetime binding collection for calls** (CR:36-114). First binding wins; a later different binding sets a conflict flag. Serves reference-returning calls.
- **Dependent result substitution** (CR:287-345). If the return type mentions a parameter symbol (as a named type, inside a const expression, or as an array length), every parameter is replaced by a `ConstExpression` node holding the argument expression.
- **Provider closing** (CC:1436-1708). Given a machine passed for a machine-kinded parameter, it matches the provider's entry-state parameter and return types against the demanded signature to infer the provider's own type and const arguments, then either records the selection (no specialization parameters, or open operands), reuses an existing instance (`saved_calls::candidate_instance`), or clones a new specialized machine (`clone_specialized_machine`). No budget. Serves machine-kinded generics.
- **Open-operand analysis** (CC:1710-1825). Collects every symbol, type and expression reachable from a type or static argument, following data applications transitively, with visited lists.
- **Inference fixpoint for omitted static arguments** (CC:3344-3458). Loop: observe calls with fewer static arguments than parameters, infer the rest, record them, re-prepare applied signatures; stop when a pass changes nothing. No iteration limit.
- **Requirement instantiation** (CC:3859-4081). For each trait requirement in each applied trait scope: if the requirement's static signature family is finite (`finite_signature_family`), instantiate every tuple; otherwise instantiate only the tuples seen at call sites (`invocation_tuples`, CC:2710-2839). Then a second loop (CC:4046-4077) routes explicit requirement calls and re-prepares signatures until no signature is written. No iteration limit. Then `retarget` rewrites calls.
- **Template chain walk** (CC:2232-2241). Follows `executable_application_template` from a declaration back to the realization machine, with a visited list to stop cycles.
- **Recursive data elaboration** (DP:195-298). Walks from an applied data type into its field types, keeping a stack of ancestors so a recursive data type stops (DP:234-237); `contains_actual_type` prunes ancestors whose arguments contain the current type.
- **Structural type substitution** (DP:596-873). Substitutes type parameters and lifetimes through every type node kind, re-owns lifetimes ("foreign" owner rule, DP:607-623), and reuses an existing equal node found by a linear scan of the whole type table (DP:676-689, 720-733).
- **Product operand graph translation** (`Lower`, DP:2569-3032 with DP:1335-2178). Translates a `ProductStaticOperandGraph` (names, types, expressions, operands, applications) into typed-tree nodes. Memo tables (`types`, `expressions`, `subjects`) and four "active" stacks detect cycles. A static helper environment substitutes actuals for helper parameters, recursively through the chain of bindings (DP:1370-1451). It also records, for each static input, which authored source selection it came from (DP:2072-2177).

## Identity by text

- Constant values travel as type nodes whose name is the constant's text and whose symbol is invalid: the literal `"0"` is looked up by `name == "0"` and created with `Identifier::generated("0")` (CR:948-957); a const argument becomes `Named { symbol: invalid, name: spelling }` (CC:4130-4138); a `CanonicalConst` becomes `Named { symbol: invalid, name: value.atom() }` (DP:2921-2924).
- Those names are parsed back into numbers: `name.as_str().parse::<usize>()` gives an array length (DP:767-770); `spelling.parse::<i128>()` gives an integer literal (CC:4171-4177).
- A finite family tuple is a list of identity strings; `tuple_argument` turns each back into an argument through `const_identity_spelling` (CC:4164-4192), which strips the string prefixes `"named(integer-const("` and `"named(canonical-const(type("` (looked up at `monomorphization.rs:2609-2619`). A non-integer spelling becomes a path of one generated identifier with no symbol (CC:4188-4191).
- Two inferred types are compared as rendered text: `normalized_type_identity_text(previous) != normalized_type_identity_text(actual)` (CC:1583-1584).
- Lifetimes are names throughout: bound by `Identifier` equality (CR:94-99), matched by `name == parameter.as_str()` (CR:1067-1070), by `head == &binding.parameter` (CC:517), substituted by `*parameter == lifetime` (DP:881), and in helper environments matched by `source.source_id == occurrence.source_id && parameter.as_str() == named.text` (DP:1487).
- Type and const parameters are carried with their names as owned strings into `BindingContext` (CR:973, 980; CC:906, 913, 3576, 3587).
- Declarations in Product operands are found by path string: `path()` joins names with `"::"` (DP:2625-2635); the result is compared with `operand.path` (DP:1086) and passed to `resolve_product_path` (DP:1093-1098, 2216-2221, 2286-2291, 2374-2379) and `find_build_subject_declaration_from_source` (DP:1691-1696, 2753-2755). A trait member is found by building `format!("{}::{member_path}", display_path(owner, "::"))` and resolving that string (DP:2346-2355).
- A lexical static parameter is chosen by `parameter.name.as_str() == path` (DP:1352); the scope merge it uses treats parameters as the same when `left.name == right.name` (DP:1348).

## Surprises

1. **No proof kernel and no proof obligations at all.** None of `proof_admission`, `ProofNode`, `verify_obligation` or a certificate appears. This slice does not accept or reject proofs; it prepares types and call targets. Property 1 neither holds nor fails here in the sense of "the checker's own yes"; what does hold is that every decision is the code's own comparison or a call to a `TypedTrees`/`validation` method. Words such as "certified" (DP:2694, 2702, 2706) and "commitment"/"fingerprint" (CC:1686, CC:4093-4094) name identity tokens passed along, not kernel checks.

2. **One shared expression node is rewritten for all contexts, and disagreement is an error.** `retarget` keys prepared invocations by `(site, owning machine)` (CC:2930-2936) but keys the rewrite by expression handle alone (CC:3025-3034, 3068-3077). The same expression handle can therefore occur under more than one context. When two contexts resolve it to different requirement instances the compiler refuses with "one requirement expression occurs under disagreeing exact trait applications" (CC:3073). This is a limit of rewriting source-tree nodes in place: the node holds one `target_symbol`, so a body shared by two contexts cannot call two instances. Statement calls get no such check; the last write wins (CC:2992-2997, 3093-3097).

3. **Three different tests answer "do two inferred types agree", and three different outcomes follow a conflict.** Tests: rendered text (CC:1583-1584), `normalized_type_identity` (CC:3621-3622; CR:706-707), `applied_type_identity` (CR:1112-1115; DP:356-358). Outcomes: a provider conflict is silent and the provider stays unclosed (CC:1605-1612); a public-method conflict is a diagnostic (CC:3625-3628); a constructor conflict gives no type (CR:1113-1118). Lifetime conflicts are also split: an error for calls (CR:108-112), silence for constructors (CR:1060-1062).

4. **An explicit static argument is never checked against what inference finds.** In `providers::close` a supplied binding that disagrees with the inferred proposal falls into `Some(_) => {}` (CC:1581-1588, 1594-1602). In public-method inference, proposals for explicitly given positions are skipped (CC:3614-3616). I cannot see in this slice where a wrong explicit argument is refused.

5. **A library-specific rule sits inside generic constructor inference.** `unused_coordinate_widths` (looked up: it returns `Option<[bool; 3]>` and is tied to the `DllImport` external-binding vocabulary, `validation/src/lib.rs:1032-1043`) makes `retain_constructor_result_type` fill unused const parameters with a type node named `"0"` (CR:942-961, 1101-1110). The array is indexed by the parameter's position among const-or-value parameters (CR:1103-1106), so a matching type with more than three such parameters would index out of bounds; I cannot tell from this slice whether `validate_dll_import_shape` rules that out.

6. **Constants are represented as type names and parsed back from text** (see Identity by text). A const argument's value survives substitution only because `instantiate_type` can parse the node's name as `usize` (DP:767-770); if parsing fails the array length silently stays the unsubstituted parameter.

7. **Helper lifetimes match by file and name, not by declaration.** `lifetime_identifier` accepts a binding when the lifetime owner's source file id equals the name occurrence's file id and the texts are equal (DP:1487). Two machines in one file that both declare a lifetime with the same name, both present in the environment, would produce "static helper lifetime has multiple supplying frames" (DP:1489-1492), and a single binding for a different machine in the same file would be accepted. This looks like a bug or at least a much looser test than the span-exact tests used for type parameters (DP:1405-1415).

8. **Errors swallowed into an invalid handle.** `instantiate_type` returns `TypeReferenceHandle::invalid()` on four failures (DP:831, 853, 863, 870) and `elaborate_application` stores it as a field type without looking (DP:386-393, 399-405). `elaborate_application` also returns nothing on an arity mismatch (DP:341-345). Neither produces a diagnostic.

9. **Fifty-four diagnostic strings say the compiler "lost" something** (36 lines in CC, 18 in DP, counted by grep after reading). Messages such as "closed requirement demand lost its exact source invocation" (CC:102) report a broken internal table through the user diagnostic channel. Most carry no source span: `Diagnostic::error(message)` alone in CC, and `Lower::error` (DP:2611-2613). Only the `refuse` closures (DP:1024-1026, 2213-2214) and four other sites (CC:3960-3962; DP:1551, 2112, 2762) attach one.

10. **Capabilities I did not expect at this level.** (a) Target-machine families: one "portable" machine head with per-target member machines, each given the same provider selection (CC:417-553). (b) Installed interrupt operations with a "registrar" that must be a trait requirement (CC:559-874). (c) `Value`-kinded generic parameters bound to runtime values, which are appended to the call as extra runtime arguments (CC:3653-3788, 4116-4128). (d) Access-view plans that replace a `Template<Policy, Schema>` result type with a generated data type (CR:220-264). (e) Requirement instantiation that enumerates every tuple of a finite static signature family before any call is seen (CC:3916-3934). (f) A complete second expression and type converter for build-supplied Product operands, including match expressions with destructuring patterns and proof selectors (DP:1930-2037).

11. **Fixed choices inside the Product converter.** Every binary operation gets `ArithmeticDomain::Exact` (DP:1722). Every domain constraint gets the exposure `PrivateImplementation` (DP:3028). Field visibility is taken from the owning data type's `is_public` (DP:2644-2654).

12. **Dedup choices that can hide a second context.** `invocations::collect` keeps the first invocation per site regardless of owner (CC:1231-1236). `retarget` collects prepared invocations into a `HashMap` keyed by `(site, owner)`, so if one expression appears in two states of the same machine the later tuple replaces the earlier one (CC:2930-2936), although the tuple depends on state and statement position (CC:2312-2323).

13. **Unbounded loops.** `inference::prepare` (CC:3345-3457) and the routing loop in `instantiate_requirement_applications` (CC:4046-4077) have no iteration limit; termination rests on "no new signature was written".

14. **Cost.** `Lower::candidates` rebuilds a vector of every declaration, field, variant, payload field and trait signature in the program on each name resolution (DP:2636-2671, called from DP:1694, 2708, 2744). Finding an existing type node is a linear scan of the whole type table (CR:214-217, 753-756, 922-925; DP:676-689, 720-733).

15. **Property 3 evidence is strong here, but of a particular kind.** The repetition is mostly "call as statement" versus "call as expression" and "state body" versus "contract scope", not the local/field/parameter/return list. The slice does show two placement-only rules: the borrow lifetime taken only from a local initializer (CR:687-726) and the byte-string retyping only in a constructor field (CR:873-933).

16. **No dead code found**, with one no-op: `impl Extend<SymbolHandle> for SourceExpressions` discards its input (CC:3817-3819).
