## What this code is for
The file has two modules. `borrow_contracts` (7-3734) works out which borrowed inputs a returned view or a provider's writable output depends on. It does this by walking a type's reference/lifetime structure ("carried lifetimes"), and it checks that a callable or machine value refines a required callable contract (same regions, same returned-view sources). `reflection` (3736-5587) validates compile-time reflection products. It replays a semantic schema graph against the data declaration it claims to describe (3753). It builds and replays "selection snapshots" that pick a conformance or machine for each member of a data type (4227-5201). It builds and replays a "runtime visitation plan", a list of (field, operation) calls (5288-5575). The borrow half is a structural analysis over type references and lifetime names. The reflection half is a consistency checker. It recomputes what a stored product should say from the typed program and compares, then compares an FNV-style fingerprint. Nothing in the file calls a proof kernel, certificate or `ProofNode`. Every verdict is the code's own comparison or a call to another module.

## Mechanisms
- **Carried-lifetime frontier walk** (`collect_type`/`collect_data`/`collect_family`/`collect_frontier`, 1378-2170). It takes a type reference and produces a list of `CarriedLifetime` leaves: a reference or retained-custody carrier, its owner path (`Field`, `Case`, `FixedIndex`, `DynamicIndex`), access, region, and whether the source is the referent or stored. It is a recursive walk over `TypeReferenceNode` with a `visiting` stack for cycles. Modes are the six `LifetimeFrontier` values: `Value`, `Input`, `ReachableInput`, `InputStorage`, `BorrowedStorage`, `WriteOnlyAuthority`. A `TypeScope` chain carries substitutions, region names, application scopes and an outer link. A `TemplateFrontier` records whether an open type parameter was met (`dependent`). `Input` mode is walked a second time as `ReachableInput` (1398-1419). The walk expands fixed arrays per element index (1788-1804), so a large literal length yields one leaf per element and has no budget. Cycles with leaves return incomplete. It serves borrow tracking of views, provider outputs, owned carriers and callable refinement.
- **Return-source resolution** (3415-3548). Matches each output leaf with input leaves by region equality (or by the one elided candidate). It yields `Parameter`, `Fields`, `NotApplicable` or `Ambiguous`. A rule of access compatibility is applied.
- **Callable region inference** (`infer_inputs` 2964-3099, `InputRegionApplication` 3210-3327). It is a unification. It maps the actual callable's `Fresh(n)` regions to required regions through `constrain`, and elided input leaves to regions. Applications are kept as a list (`Vec<InputRegionApplication>`) that can branch, and exactly one distinct completed application must remain (3085). `finish` renumbers fresh regions to canonical invocation order and checks the required count. There is no explicit budget; it is bounded by the parameter count.
- **Region comparison through a trait** (`TypeRegionScope` impl 2778-2917). The scope object (`RegionScope`) implements `erased_identity`, `enter_operand`, `enter_lifetime`, `named_alias` so the generic walkers `type_reference_region_applications` and `type_reference_regions_match` (defined outside this slice) can compare two types.
- **Prepared refinement** (`PreparedCallableBorrowRefinement` 247-516). Splits refinement into `prepare` (infer input application) and `validate` (apply it to the actual frontier, then compare). `lifetime_frame` (272-359) exports a per-callable lifetime binding table.
- **Lifetime-region resolution** (`callable_regions::resolve` 822-937). It builds the name-to-region environment: captured lifetimes from lexical parents, application scopes, supplied bindings, and fresh regions for the callable's own lifetime parameters.
- **Reflection replay by recomputation** (3753-4037, 5044-5128, 5485-5528). Every product is rebuilt from the typed program with `describe_field`, `expected_members`, `expand_calls`, then compared whole. The fingerprint is a hash (`OFFSET_BASIS`, `byte`/`text`/`uint` folds; value 0 is mapped to 1: 4194, 5194, 5573).
- **Selection receiver state machine** (4822-4978): `new` -> `select`/`exclude` -> `freeze`, with a recorded-choice list and a uniqueness check.

## Surprises
- `check_conformance_refines` (4400-4438) verifies trait, application, and requirement realization and then unconditionally returns `Err` (4434). Everything before it is a diagnostic refinement of the error; no input makes the function succeed. The same holds for `Conformance` choices in `ScopedSelectionReceiver::select` and `replay_selection_snapshot`. Only `Machine` and `Excluded` choices can succeed.
- `prepare_callable_inputs` (217-223) reads `program.data_type_parameters.iter()` as a field with `(_, parameter)` tuples, while `collect_type` calls `program.data_type_parameters(definition)` as a method (1895). Both forms are used on `dyn CheckingInput`; I cannot tell from the slice whether both exist or one is a stale form.
- That same call collects every type parameter of every data definition in the program as "symbolic parameters" for each callable refinement (217-223). The cost grows with program size.
- `resolve_requester` (4191-4213) and `resolve_requirement`/`resolve_unique` (4251, 4300) scan all symbols/traits/conformances/machines and render an identity string for each one on every call.
- The `LifetimeFrontier::Input` mode is run twice and the second result replaces the first (`ReachableInput`, 1398-1419); the first result is only used if the second is incomplete or template-dependent.
- Fixed arrays are unrolled per element index with no cap (1788-1804).
- `input.access != output.access && input.access != Mutable` (3520, 3573): a `Mutable` input is accepted as source for any output access, including `WriteOnly`. A `WriteOnly` output from a `Shared` input is refused.
- `installed_context_lifetime_source` hard-codes `parameter_index: 0` and `source_type: context.acknowledgement` (3721-3731): an interrupt-context feature coupled into general view-return resolution.
- `resolve_applied_signature_view_return_source` (3356-3380) only handles custody entries whose `source.segments` and `result.segments` are both empty; others fall through to structural resolution.
- `region_correspondence::validate` computes `output_elisions` only when the actual frontier has exactly one input leaf (474-489); with several inputs the elided output regions simply find no match and are refused at comparison (3124-3129).
- In `RegionScope::named_alias`, `ReferenceStep::Stop` is returned when `operand == reference` (2891-2893), whereas the frontier walker's equivalent case returns `false` (1966-1968) or marks template-dependent (1962-1965). The two walkers treat a self-bound type parameter differently.
- `index > 1` in the orphan check (3991) encodes an unstated assumption that nodes 0 and 1 are reserved.
- `fingerprint` hashes (5136-5193, 5535-5573) include `qualified_type` text and identities but the plan hash omits `requirement.trait_application`, while the snapshot hash includes it (5160-5173 vs 5540-5541). The plan header equality check (5490-5495) does compare `requirement`, so the difference is covered by `replay_runtime_visitation_plan`, not by the fingerprint.
- `frontier_tests` is the only test and is nested inside `carried_lifetimes`; about 5,300 lines of validation logic here have no test in this file.
- No use of `proof_admission`, `ProofNode`, `verify_obligation` or certificates anywhere in the slice. Property 1 is borne out here, but the code does not decide value-level proof questions; it decides borrow/region structure and reflection-product consistency. Property 2 is borne out in `reflection` (all identities are strings) and partly in `borrow_contracts` (lifetime names). Property 3 appears as per-construct repetition inside the walker, not per source placement.
