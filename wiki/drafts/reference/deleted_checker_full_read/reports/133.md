## What this code is for
The file is a bundle of 17 inline modules (`pub mod ...`) that the header (VC:1-5) calls "value custody": the typed-tree checks about who owns a value and what must happen to it. The modules are: `activation_storage`, `atomic_fences`, `atomic_operations`, `byte_observations`, `claim_frontier`, `cleanup`, `cleanup_selection`, `const_expressions`, `constants`, `content_classes`, `data`, `destructure`, `dispatch_extraction`, `executable_value_occurrences`, `intrinsic_boundaries`, `locals`. Most of it recognizes special toolchain declarations (activation claims, atomic fence, console and process-exit intrinsics) by their sealed identity and exact shape. It also finds which parts of a type are linear (must be used exactly once) and so must be consumed, and checks `dropped by` cleanup selections. It checks const-generic argument carriers and constant eligibility, and data declarations (duplicate members, builtin shadowing, unbounded-integer fields, default-domain facts). It checks record-pattern exhaustiveness and local-name scoping, and it enumerates every executable expression with its origin. Almost everything reads the typed program through the `CheckingInput` trait (`program`); the only real "judgments" are returned as `bool`/`Option`/pushed `Diagnostic::error`. No proof-kernel call (`proof_admission`, `ProofNode`, `verify_obligation`, certificate) appears anywhere in the slice. The slice does call other modules for arithmetic and proof facts (`arithmetic_domains::validate_value_range_retaining_obligations`, `proof_contracts::...`), whose internals are not in this slice.

## Mechanisms
- **Linear claim frontier** (VC:1364-1631). Computes the list of paths (field/case/fixed-index segments) inside a type at which a linear value sits. Recursive walk with a `visiting` symbol stack against recursion, `substitutions` list for generic parameters (`enclosing_substitution` takes the latest binding and cuts the list at that position, VC:1660-1673). A `first_only` mode stops at the first claim (used by `type_carries_linear_obligation`). Fixed arrays of length n repeat the element claims n times (VC:1428-1441), so output size grows with array length (no budget). Results are memoized via `type_properties::memoized_claim_frontier` (defined elsewhere). `DeclaredClaimFrontier` (VC:1238-1270) adds a lazily built bucket index (`PlaceBucketIndex` over a hash of the path) so field lookups do not scan all claims; full path equality still decides membership (VC:1268).
- **Cleanup type answers** (VC:1871-1967). A sorted table of per-type-reference `OnceLock<bool>` answers, binary-searched by (arena index, generation); built on first use from `checking_memos`.
- **Nominal drop reachability** (VC:1969-2100). Depth-first search over the type graph with a visited set of identity strings and a substitution list; stops with false on cycles.
- **Nominal cleanup owner memo** (VC:2233-2250). A `Mutex`-guarded map keyed by symbol in frozen-program memos; `unwrap` is avoided (`if let Ok`) so a poisoned lock silently skips the cache.
- **Cleanup selection walk** (VC:2614-2704). Visits a type, its domain constraints, domain aliases and subject-membership facts, tracking visited `(domain, semantic id)` pairs, merging selections and refusing conflicts.
- **Establishment analysis** (VC:3994-4203). Recursive "can the zero value be used?" computation with a seen-stack for recursive types and a sorted memo (`computed`, binary-searched by `(decl arena, gen, application arena, gen)`). Recursion through a type already on the stack returns false (VC:4161-4163).
- **Fixed-point?** None. No budgets or iteration limits anywhere in the slice, apart from the recursion guards above.
- **Const-expression value category walk** (VC:3141-3222). Worklist DFS over subexpressions with a `visited` Vec (linear `contains`, quadratic in size).
- **Atomic operation recognizer** (VC:1077-1146). Pure pattern match that recovers an atomic operation from desugared arithmetic trees.

## Accepts or skips without proof
- `has_contents`-style predicates: `carries_activation_claim` returns false when a symbol has no data definition (VC:548-552, 582-587) and returns false on revisit (VC:545-547, 579-581). Cannot tell if another check catches an unknown carrier type.
- `append_linear_claim_frontier` silently returns (no claim) when a named or generic type has no data definition (VC:1470-1472, 1501-1505), when a `Reference`, `Slice`, `ConstExpression`, `DynamicTrait`, `Unit`, or non-literal-length `FixedArray` is met (VC:1531-1536; non-literal `FixedArrayLength` falls to the `FixedArray {..} => {}` arm), and when `visiting` already holds the definition (VC:1549-1551). Cannot tell what else catches a linear value hidden behind an unresolvable type.
- `frontier_type_multiplicity` defaults unknown names to `Affine` (VC:1712-1715, 1727-1730), which is the conservative direction. `type_multiplicity` for an invalid reference returns `Affine` too (VC:1638-1640, 1679-1681). But `Reference`, `ConstExpression`, `Unit` are `Unrestricted` (VC:1686-1688): a shared or exclusive reference is never treated as carrying a linear obligation.
- `type_graph_requires_nominal_drop` returns false for `Generic` when the base data definition is missing or argument count differs (VC:2031-2043), for revisited identities (VC:2007-2009), for `Reference`, `Slice`, `DynamicTrait`, `Unit`, `ConstExpression`. - `validate_cleanup_delivery` returns silently (no diagnostic) if the source type cannot be resolved or has no cleanup application (VC:2402-2413); also returns when the source and target types are identical.

## Surprises
- No call into the proof kernel, certificates or `verify_obligation` appears in this slice. Where proof-adjacent facts are needed (zero admission, integer ranges, domain membership), the code calls helpers (`integer_domain_membership` returning `StrictArithmeticImplicationJudgment::Proven`, `range_constraint_interval`, `domain_predicates_admit_zero`, `case_requires_field_intervals`) and uses their boolean/interval answer. In `exact_byte_read_result_type` (VC:5331-5337) an unbounded `value` is accepted as long as the helper returns `Some`.
- A built-in-sounding rule is hard-coded by machine name: `ConsoleNativeProvider::read_byte`/`write_byte`/`exit_process` and `ProcessExitNativeProvider::exit_process` are treated as compiler intrinsics by name plus `attached_data` name plus `Boundary` supply mode (VC:5254-5266, 5154), with no sealed-identity check like the toolchain declarations use. Same for the trait names `"Console"` and `"ProcessExit"` and requirement `"read_byte"` (VC:5219-5220).
- `Named` and `Generic` arms of `type_requires_establishment_inner` disagree on what a missing data definition means (permissive for `Named`, VC:4062; conservative for `Generic`, VC:4078).
- `eligible_type` for constants accepts a fixed list of builtin atoms and rejects `Reference`/`Slice` outright, but accepts `DynamicTrait` whenever the trait definition exists (VC:3492-3494).
- `state_value_root_is_known` treats any data variant name anywhere in the program as a known value root (VC:5677-5685), and any type/machine/trait name by text, so a bare name resolves by spelling when no symbol is attached.
- `has_value_category` accepts a name with no symbol if its text parses as an `i128` (VC:3199-3200): a number spelled as a name path.
- `atomic_operations::atomic_write_operands` recovers atomic operations by matching a desugared arithmetic shape (compare-exchange as `prior + (prior == expected) * (desired - prior)`, VC:1126-1139); the meaning lives in the tree shape, so any hand-written expression with that shape would be classified the same, provided it sits in an `ExpressionNode::Atomic` with matching ordering and result.
- `append_linear_claim_frontier` expands fixed arrays per index (VC:1428-1441), so claims and output grow with array length with no cap; a `[Linear; 1000000]` would create a million paths. Zero-length arrays are skipped (VC:1398-1400). The `first_only` mode takes index 0 only (VC:1401-1413).
- Dead or odd code: `data_member_name` helper is used only once (VC:4250, 4260-4265) while `validate_data_member_names` repeats a similar `match` inline (VC:4243-4246). `nominal_cleanup_owner` memo errors from a poisoned mutex are ignored. `ByteObservationCarrier` / `content_classes` are thin wrappers. `activation_claim_byte_carrier` scans all machines each call (VC:504-508), so `carries_activation_claim` (called per `Named` node) costs a machine scan each time, and each scan reruns `exact_toolchain_activation_storage_contract`, which itself scans machines for the roster (VC:119-128): quadratic-looking, mitigated by no memo seen in this slice.
- `validate_atomic_fence_declarations` and `validate_cleanup_machine_declarations` iterate the whole program per call and are `pub(crate)`; the lone `Diagnostic::error` for fences has no span.
- Comment vs code: the file header (VC:1-5) lists "structural identity" as a topic, but the slice has no module by that name; structural identity appears only as `expressions_structurally_equal` calls (VC:4576, 4670).
- Capability one might not expect: `cleanup_selection` supports `dropped by` on domains (including domain aliases and subject-membership facts, VC:2657-2704) and requires the carrier's owning package to authorize it by comparing package identity (VC:2786-2788).
- `record_pattern_coverage` and its tests show the authors deliberately moved record-pattern checking from spelling to symbols; by contrast, activation/intrinsic/atomic recognizers in the same file still decide by spelling plus sealed identity.
