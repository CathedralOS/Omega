# Omega Language Vision

Omega is a programming language centered around provable behavior, explicit state, and aggressive data-oriented execution.

This document is intentionally early and incomplete. It exists to capture the direction of the language while the syntax and implementation are still moving.

## Core goals

### 1. Extremely provable

Omega should make correctness a default part of the language experience rather than an afterthought.

Desired direction:

- Compile-time integration with TLA+ style checks
- Language constructs that map cleanly onto formal state-transition models
- Tooling that makes invariants, safety properties, and liveness properties explicit
- A bias toward designs that are easy to model check

The ideal outcome is that Omega programs are not only compiled, but also mechanically challenged for invalid state evolution before they run.

### 2. State machines as first-class citizens

State machines are not a library pattern in Omega. They are a core language abstraction.

A machine:

- Owns data
- Declares its states
- Declares transitions between those states
- Concentrates behavior around explicit state evolution

This should make control flow easier to reason about, easier to prove, and easier to optimize.

### 3. Extremely data oriented

Omega should assume that layout, ownership, and throughput matter.

Desired direction:

- Machines own and operate on their data directly
- Data layout should be visible and optimizable
- SIMD-friendly execution should be common rather than exotic
- Transformations over collections of data should prefer dense, predictable access patterns

The language should encourage code that looks high level while compiling toward low-level execution patterns that are cache-friendly and vectorizable.

### 4. Self-modifying code over branches

One experimental idea in Omega is to prefer patching executable control flow over carrying certain branches forever.

For some transitions, the runtime or generated code may be able to rewrite jump targets or patch instructions so the active control path becomes direct.

Desired benefits:

- Reduced branch overhead in hot paths
- Control flow that collapses toward the active state
- A closer mapping between state transition and machine execution

This is highly experimental and will need very careful constraints around safety, portability, debuggability, and proof semantics.

## Draft mental model

An Omega program is expected to revolve around machines that contain owned data and explicit states.

Very early sketch:

```omega
machine main {
    contains log: Logger;

    state Main {
        log.Flush();

        -> self;
    }
}
```

This example suggests a few important ideas:

- `machine` is a top-level construct
- `contains` declares owned machine data
- `state` declares executable machine states
- `state Main` is the implicit entry point for a machine named `main`
- trailing `-> Target` lines declare control-flow edges out of a state

## Early semantic direction

The design currently appears to want the following:

- State is explicit, not implicit in scattered booleans or enum checks
- Behavior lives inside states, commands, and queries
- Transitions are graph edges, not function bodies
- Data ownership belongs to the machine that evolves it
- Transitions are natural proof boundaries
- The compiler has enough structure to derive formal models from source

## Proof-oriented compilation

One possible long-term pipeline:

1. Parse Omega source into an IR centered on machines, states, data, and transitions.
2. Derive a formal transition-system representation from that IR.
3. Check invariants and temporal properties using integrated formal tooling.
4. Reject programs whose declared properties cannot be satisfied.
5. Lower verified machine behavior into optimized executable code.

Open question:

How much TLA+ should be surfaced directly in Omega syntax versus generated by the compiler?

## Open design questions

- How are invariants declared on machines and states?
- How are liveness properties expressed?
- Are transitions single-step atomic operations, or can they yield?
- What distinguishes a `state` from a more traditional coroutine or actor mode?
- How does self-modifying control flow interact with formal proofs?
- How portable is the patching model across operating systems and architectures?
- What syntax should express SIMD-first data transforms without becoming unreadable?
- How much manual control over memory layout should users have?
