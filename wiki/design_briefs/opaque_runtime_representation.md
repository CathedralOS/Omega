# Design Brief: Opaque Runtime Representation

Current as of 2026-07-25. Status: semantic architecture settled; source
spelling and exact compiler-generated implementation hooks remain owner
questions.

## Problem

`boundary data` currently has no structural constructor or source-visible
fields. That is correct for externally supplied or provider-minted values, but
the compiler also gives every such declaration no runtime layout. Erasure works
for proof-only values such as `Real`; it cannot represent an `Extent`,
`TaskRuntime`, interrupt guard, acknowledgement, or other opaque value that
must occupy storage and cross calls.

Opacity, representation, introduction, qualification, and authority are
independent:

- opacity determines whether ordinary source can inspect or construct a value;
- representation determines how runtime bits are stored and passed;
- introduction determines which operations may establish a value;
- qualification establishes semantic domain facts; and
- authority is supplied by the introduction operation's inputs and contract.

No one axis substitutes for another.

## Closed representation property

Representation is a compiler-defined declaration property, not an open
user-authored `plan()` machine:

```text
Erased
Runtime::Inline(LayoutPlan)
Runtime::SealedHandle(HandlePlan)
```

Omission means `Erased` and fails closed when the value reaches runtime.
`Inline` cites the ordinary authored layout machinery for carrier geometry;
that does not make representation itself an authored policy family.
`SealedHandle` names provider-owned backing state through a compiler-validated
handle plan.

The type owner pins the representation. A provider may own backing state and
mint values through declared introductions, but it cannot select a different
carrier ABI for the same type.

An empty inline carrier normalizes to a runtime zero-sized result. Zero-sized
is not a separately asserted source class. Structural emptiness proves only
that no bits are present; the type owner and provider remain responsible for
showing behavior does not need hidden instance state. Zero-filled storage does
not establish a live zero-sized value: establishment remains path-sensitive.

Native pointers and descriptors are ordinary inline layouts unless they
require distinct validation semantics. The compiler must not infer
representation from type names or silently assign every opaque value one
pointer-sized word.

## Carrier and implementation scope

An inline opaque type cites an unpublished ordinary carrier declaration:

```text
unpublished Carrier declaration
    + normalized LayoutPlan
    + opaque public declaration
```

The toolchain knows the carrier layout for storage, calling classification,
linking, and compatibility. Ordinary consumers cannot name, construct, pattern
match, or project the carrier.

The compiler generates two implementation hooks:

- `pack(carrier) -> Opaque`, callable only inside declared introduction
  implementations; and
- an immutable projection from `&Opaque` to `&Carrier`, callable only in the
  declaration's representation-implementation scope.

`pack` takes no authority parameter. Its lexical/semantic scope prevents
ordinary calls; the enclosing introduction's signature supplies the actual
entitlement. Immutable projection is implementation access, not semantic
authority.

Mutable carrier projection is not generated by default. It would allow
representation mutation to bypass the small set of introduction and
transformation contracts. A type may opt in only with an explicit customer and
acceptance tests covering every invariant such mutation can affect.

Generated packing and projection carry contracts connecting carrier values to
published observations. A prover must be able to establish, for example, that
packing an Extent carrier with one base and length makes `range(result)` return
that same geometry.

## Introduction and entitlement

The type owner declares the operations allowed to introduce values. Providers
call those operations; providers do not receive raw `pack`.

Each introduction names its own entitlement through ordinary inputs and
contracts:

- root establishment consumes an admitted provider-neutral root grant;
- split consumes a parent authority and proves exact conservation;
- a storage-backed loan carries the source borrow;
- mapping consumes or borrows its source and consumes destination authority;
  and
- handle creation atomically registers provider backing before packing the
  carrier.

Linearity bounds consumption, not production. Conservation therefore comes
from ordinary public postconditions over published observations. A split must
prove its children are disjoint and exactly partition the old range; a loan
must prove its range lies within the source borrow. Facts not provable from
checked code, such as firmware having transferred a physical range, enter
through ordinary provider admission and receipts.

Construction and qualification are separate mechanisms but compose before an
authority-bearing value escapes. A provider may construct an Extent carrier and
establish `Physical` and `Writable` through different internal gates; no bare
unqualified Extent becomes an ordinary public result between them.

Provider-specific evidence is normalized to a type-owner-understood grant.
Core code need not name every future `UefiGrant`, device-tree receipt, or
hypervisor token. The admitted provider converts those facts to the
provider-neutral input consumed by the type-owned introduction.

Domain `MintAuthority<D>` remains the authority for introducing a semantic
qualification. It is not the opaque representation `pack` operation and must
not be reused as a universal carrier-construction token.

## No structural leakage

Opaque runtime types derive no carrier-based:

- equality or ordering;
- hashing;
- display or debug formatting;
- serialization;
- structural reflection or pattern matching; or
- cloning beyond independently established multiplicity rules.

Carrier equality is not necessarily semantic identity. Two handles can name one
resource, and equal handle words from different provider eras can mean
different things. The type owner publishes only meaningful observations and
operations, such as `Extent::range()`, and explicitly defines comparison or
serialization where the abstraction has such a contract.

## Which facts need runtime bits?

A fact needs runtime representation when:

1. runtime code must branch on it;
2. an untrusted boundary must validate it from a caller;
3. it identifies provider-owned backing; or
4. it must survive a storage/component crossing where static provenance is no
   longer available.

Otherwise it remains a qualification, checked provenance fact, admission
receipt, or audit fact. For `Extent`, base and `u64` length are the likely
inline payload. Address space, rights, and provenance normally remain sealed
facts. Authority lineage gains runtime backing only if compiler-tracked origin
identity cannot survive the required flows.

Generation checks substitute for a static alias guarantee the checker cannot
make. Linear, uncopyable values with no foreign retention and reuse only after
consumption need no generation lookup. Shared handles, foreign retention,
independently dying backing, and asynchronous revocation may require one.

## Identity and package admission

The normalized representation and published introduction contracts enter
contract/component compatibility identity. Private implementation bodies and
proof evidence remain behind the evidence firewall; changing them alters
artifact content identity, not the public contract identity.

Artifacts retain a complete machine-readable manifest containing runtime opaque
types, normalized carrier plans, published introductions, backing/provider
requirements, admitted claims, representation mutation, and reachable
authority. Human package diffs are severity-ranked:

- a checked local inline token is summarized quietly;
- new mutable carrier access, sealed-handle backing, generation/revocation,
  admitted foreign providers, or system authority is elevated; and
- transitive expansion to root memory, DMA/IOMMU, executable installation,
  interrupt publication, or equivalent authority blocks without explicit
  policy approval.

Admission operates over the transitive reachable-authority set of the final
resolved artifact, not only direct dependencies. The manifest should report the
dependency path that introduced a new authority.

Package policy is an admission gate, not a behavior gate. It decides which
package may receive authority; checked contracts constrain how admitted code
uses it. Neither substitutes for the other.

## Encapsulation is not a customer

Runtime `boundary data` is not replacement field privacy. Ordinary
implementation records remain transparent when published; correctness belongs
in invariants and sealed qualifications. Confidentiality belongs in custody
behind a real provider boundary.

Tooling should warn when runtime opaque data has no external realization,
provider-owned backing, sealed introduction, authority-bearing input, or other
semantic justification. The warning remains policy-configurable because
library-issued sessions and reservations can be legitimate authority values
without hardware or OS backing.

## Acceptance

- an inline linear Extent crosses a checked call without a public constructor;
- an ordinary package cannot call `pack` or project the carrier;
- every introduction proves its public postcondition or presents an admitted
  receipt;
- two packs from one consumed Extent cannot satisfy split conservation;
- an empty mask guard fails the behavioral nested-mask/restore canary unless
  prior state is preserved through admitted backing;
- no structural equality, display, serialization, or reflection appears
  implicitly;
- changing inline to sealed-handle changes contract identity;
- a transitive authority expansion is visible and policy-gated; and
- representation-only implementation refactoring preserves contract identity.

## Remaining owner decisions

- exact representation-clause spelling;
- exact spelling/designation of introduction implementations;
- exact names and compiler scoping for generated pack and immutable projection;
- the normalized `HandlePlan` vocabulary;
- whether Extent lineage survives statically through every required crossing;
  and
- the first staging point for `SealedHandle` implementation.
