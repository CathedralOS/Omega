Foundation should keep generic building blocks, and native compilation should expose its work as representation-to-representation stages. The six rulings set that direction. This plan proposes the contracts and order of the moves; its package names, stage boundaries and answers to open questions are judgment, not additional owner rulings.

At source revision 3f9ce43f0c9d179048911d18faa91ba93f60176d, the two foundation folders contain 96,223 Rust lines in 26 crates, and the backend contains 223,507 in 29 crates. Counts include tests. Generated counts are the authority for sizes; they do not measure complexity or the amount of code a move can delete.

Part A separates primitive bytes and storage from language vocabulary and program facts. Part B gives native preparation, encoding, layout, objects and images explicit owners. Provider settlement belongs in this account too: it closes over reached requirements before native lowering, but installation binding also needs facts produced much later. The Omega map traces those operations before proposing a new order.

The migration must preserve accepted programs, refusals, artifact identities and output bytes. This documentation update has not implemented or tested that migration. Each implementation PR must prove its own part before deleting the old route.

0. Method and how much to trust it

This review reads source at 3f9ce43f0c9d179048911d18faa91ba93f60176d. The evidence manifest records the source revision, scanner versions and exclusions. Reproduction commands live in the atlas README.

  • Crate edges: cargo metadata --format-version 1 --no-deps reports 139 workspace packages and 1,479 workspace path dependency declarations: 1,318 normal, 1 build and 160 dev. A manifest edge establishes permission to use a crate; it does not prove a production function call.
  • Module uses: modscan.py and modscan_be.py scan non-test Rust paths. They are evidence of observed references, not a Rust resolver. Re-exports, macros, glob imports and conditional compilation limit their conclusions.
  • Counts: all_rs_lines includes all Git-tracked Rust files under a crate; src_rs_lines counts those under src/ only. Backend totals are respectively 223,507 and 221,538. The former plan mixed an all-files total with a src/-only scanner. It also compared source from 6de27da2a36d86f6c3883cb89527d0d44dea646a with later code. Historical measurements are not fresh verification. Module sizes and proposed split sizes retained below from the original 6de27da… inventory are historical estimates, unverified at the reviewed source; generated package totals are identified separately.
  • Ownership: trace the function that creates a value, its containing representation, and the consumer. A type's defining crate alone proves neither a side channel nor where its computation belongs.

Part A: Foundation keeps only primitives

1. The rule and what decides each destination

What the 2026-11-17 ruling says

Foundation keeps only primitives. A primitive is a generic building block with no Omega-language or compiler meaning: arenas, handles and dense ID tables, the record codec, wire bytes and digest encoding, plain diagnostics carriers, source text positions, and big-integer arithmetic.

Foundation has no language layer. A language table (intrinsic catalogs, spellings, the scalar and proposition term language, numeric and float rules, the optimization catalog, access and layout rules) moves into the first pipeline stage or representation that needs it. Later stages then carry it forward. A crate that no pipeline stage uses leaves for its actual owner, even if that splits the crate.

The four verdicts

Verdict Test Text that decides it
primitive (stays in psi/foundation/) Generic building block with no language or compiler meaning, used by the pipeline The ruling
move into <stage or representation> A language table, or a table, handle, plan or summary that a stage fills from the program. Goes to the first representation that needs it; a private helper used by one stage stays there; a value handed to its neighbor belongs to their representation contract. The ruling. Also AGENTS.md "Representation-to-representation pipeline: … Carry needed semantic facts in that representation; do not bypass the pipeline with sidecars".
move to <non-pipeline owner> No pipeline user The ruling. Also pipeline.md table: "Build-time execution inputs and accounting → Psi compilation/build-time-evaluation/"; "Source acquisition and package storage primitives → Omega packages/".
delete Unused, duplicated, or re-exported AGENTS.md rule 6: no second copy of a data structure

Proposed representation packages

  1. psi/compilation/representations/terminal-psi/vocabulary - What it is: the "carried vocabulary" of Terminal Psi, abbreviated TPV below. - Why it is needed: many tables are first used by a source-side form (syntax-trees, symbol-resolved-trees, typed-trees) but are also read by Terminal Psi, Omega, realization or the interpreter. The firewall (boundary.rs:352-358, PERMITTED_OWNERS) forbids those readers from reaching source-side forms, so such a table cannot live in the source-side form that first needs it. - Judgment: put shared definitions in the carried representation under the Terminal Psi family. The source-side forms depend on it, and the Terminal and Omega sides already may reach it, because terminal-psi/* is in PERMITTED_OWNERS. - It follows the existing precedent of native-vocabulary: "owns the leaf types every native form carries unchanged". - It should be split by subject into nested packages (judgment): identities, scalars (term language and numeric rules), declarations, resources (access and extents), layout. The original rough module estimate was 40–45k lines; an exact post-split total is unverified. Keeping subjects separate makes their permitted dependencies and constructors reviewable.
  2. psi/compilation/representations/build-requests - What it is: a proposed carrier for Build evaluation requests and results consumed during source preparation: selection requests, executed results, product targets and operands, and compiler-evaluation requests. Q-B recommends projecting only required facts into later forms, not granting Terminal and native consumers access to the whole Build input. - Why it is a Psi package: build-time-evaluation (Psi) produces it, and the firewall forbids Psi from depending on Omega.
  3. psi/compilation/representations/source-files (judgment) - What it is: the input of stage 00, which is already named source-files-to-tokens. It holds LoadedSource(s), SourceContents, the captured source tree and snapshot (capture.rs), read_accounting, SourceCatalogue, and loading-specific identity/custody. Split the small consumed-source identity vocabulary needed by Terminal readers into a shared leaf; Q-B does not grant them access to loaded files or source acquisition. - Why it is not foundation: these carry package and source-loading meaning, not plain text positions.

The firewall still decides two things

Psi never depends on Omega (boundary.rs:228-233). So:

  • A Psi-side table used mainly by Omega still goes to a Psi representation.
  • An item with no pipeline user goes to an Omega owner only when no Psi crate uses it.

Text the ruling supersedes

The implementation sequence rewrites applicable instruction text with the corresponding move (AGENTS.md "Scope and escalation"):

  • pipeline.md:1057-1063: "Shared foundations … stay independent libraries. Do not fold them into a producing stage". Superseded for foundation; the rule against merging stages stays.
  • pipeline.md:1086-1089, 1110, 1440-1447 and 1604-1614: the foundation rows and the flow-effects, optimization and function-identity placements.
  • psi/compilation/representations/README.md: "Shared vocabulary belongs in language-semantics", and the flow-effects and optimization paragraph.
  • omega/foundation/README.md and psi/foundation/*/README.md for every crate that moves.
  • numerics/README.md: it becomes the bignum README.

5. Ordered PR sequence (contracts before moves)

These are proposed implementation PRs, not completed work. Each move deletes its old module and updates the instructions that name it. Run check-boundary and check-rules, lint touched Rust crates, and test the moved operation and its direct consumers. Compiler contract changes also need a focused accepted and refused program; a path-only move needs byte/codec equivalence where that is the contract. Do not equate a docs build with these checks.

Step Depends on Change and deletion Proof specific to the move
A0 none Record reviewed source and complete scan coverage; distinguish definitions, value storage and producers. Add boundary expectations with explicit temporary allowances for current paths. Scanner covers the real backend/target; graph and counts reproduce.
A1 A0 Remove only individually confirmed unobserved dependencies. There is no promised count of deletions. Feature/target checks cover each removed edge.
A2 A0 Move source-audit and mutation-matrix to test support; retire the old re-export and feature only after migrating their actual tests. Existing source guards and image mutation tests still run.
A3 A0 Extract generic wire helpers, fnv1a, ID tables and generic hashing. Keep semantic type/path encoders with semantic definitions until A11. Existing codec bytes and digest identities agree.
A4 A3 Move function-identity into a leaf native vocabulary; delete the old crate. No reverse edge from vocabulary to a program form.

Part B: Backend dissolves (owner ruling 2026-11-17)

The ruling: omega-rust/omega/compilation/backend/ should not exist, because native compilation is one linear pipeline.

Today the backend is 223,507 lines in 29 crates: all .rs lines, counted the same way as §2. Every Omega stage except O01 depends on backend crates directly, and so do 6 of the 7 native representation families (all except native-vocabulary). After Omega 09, the native driver keeps working outside the numbered pipeline: it calls machine-emission, object-file and image-emission, which turn the program into an object and an image.

The plan:

  • Give that work numbered stages (O10–O14) with their own representations.
  • Fold encoding into Omega 07.
  • Turn the selected target's description into an input representation that Omega 00 receives and the native forms carry. This is the Omega-side analogue of build-requests, and it answers Q-E.
  • Carry program-derived provider plans in the output of explicit settlement and admission phases; bind later installation facts when their inputs exist.
  • Move the rest to products, realization, the interpreter or tests.

B5. Provider settlement, admission and later installation binding

The five realization crates contain 36,409 Rust lines at the reviewed source. They do not form one operation that can all be moved before O00. The current route has four materially different points:

  1. The compiler closes provider demand. It discovers reached requirements using already chosen exact bodies, prepares calling-policy inputs when that set changes, chooses providers, and repeats until the bindings stop changing. It refuses a change to an already chosen exact body. Retained available code does not itself become an invocation root.
  2. Policy preparation receives checked source custody, accepted publication, Build bindings and target. The proposed input must retain an admitted catalog of policy artifacts and selection authority; “Terminal Psi + target” alone does not describe this current API.
  3. O00 and native preparation admit the selected providers, entry and application evidence. The native proposal constructor already performs task realization and provider checks despite living in a representation crate. Move those producers explicitly.
  4. The root pauses after O02. Installed handlers may run through their own native pipelines first. Their emitted objects determine numeric stack requirements, which admission binds before root O03. The callback coordinator rejects cyclic installer/handler resource dependencies and reuses each produced object. Source

Recommendation for Q-G (judgment): make early provider closure and native admission explicit numbered transitions, and give later installation binding its own transition when its measurements exist. Carry selected declarations, call plans, trust and task facts in the corresponding output. Keep constructors that issue sealed authority with their checking producer, while runtimes depend only on the resulting carrier interfaces. SelectedExecution::settle is not the sole constructor: from_realization is public.

A global linear pipeline needs more than an O02/O03 insertion. Today's handler measurement runs later child stages while the root is paused. Proposed contract work: carry a complete reachable body roster and symbolic installation demands through selection and frame planning; derive stack facts from that current form and bind them before their first numeric encoding use. Inventory O03's numeric consumers first. If a choice cannot be deferred without repeating selection, split that choice into a later stage. Do not hide recursive calls to earlier stages inside a newly named binding stage. The precise split and preservation of current cycle refusals are unverified and block the whole-program linearity claim, not the independent late-emission moves.

7. Owner questions

The six recorded rulings settle the direction: primitives only, program facts carried by representations, little shared code, and no backend layer. They do not ratify specific package names, a host-support exception, source-input access or a complete installation-stage design. TPV, build-requests, target-description, provider-plans and O10–O14 are this plan's proposed implementation names.

The question page records Q-A, Q-B, Q-C, Q-D, Q-F and Q-G with current code evidence, options and recommendations. In brief, the recommended choices are:

Question Recommendation — judgment, not adopted
Q-A: shared process runner Give non-compiler host support an explicit narrow owner and runtime rule. Do not place it in packages then waive an unexplained runtime edge.
Q-B: Build/source access Carry admitted semantic facts and provenance in the current representation. Split them from source-loading state and whole Build results.
Q-C: source/evaluation sequencing One source sequencer owns continuation and evaluator requests; an artifact-only executor runs checked programs. Remove evaluator stage calls before reversing any dependency: source-compiler already depends on build-time-evaluation.
Q-D: earlier types versus earlier programs Allow leaf identity/vocabulary definitions across forms; prohibit undeclared access to an earlier whole program. Re-export chains are not a substitute for data flow.
Q-F: encoding after O07 Carry encoding alternatives plus complete fixup rules, including callback materializations and frame-induced displacement changes. Prove the representation before relocating all encoders.
Q-G: realization Number early closure/admission and later binding where their facts exist. Replace the root/child interleaving explicitly before claiming a single whole-program pipeline.
