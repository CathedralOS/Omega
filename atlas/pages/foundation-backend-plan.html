This plan replaces the foundation and backend architecture in one coordinated change set with one cutover. It does not propose a sequence of small migration PRs. Source settlement, provider selection, generated code, physical resources, representations, runtimes and validators must agree before the new route replaces the old one. Internal work has dependencies and can be divided among agents; partial routes are not separately rolled out.

The current task is plan first. No compiler migration is implemented by this document. The six owner rulings remain authoritative and unchanged. The destination below is a concrete recommendation applying them. Proposed boundaries and names are judgment; feasibility obligations are unverified until the named evidence is supplied. Those obligations must be settled in this plan before implementation starts. A new folder name is not evidence that a contract is possible.

Reading the map? Start with the extra-arrow repair list and the handler detour. The remaining sections give the contracts and evidence for the same coordinated migration.

1. Scope, evidence and the single cutover

The change covers the Rust compiler from source input through accepted Psi, native planning, code generation, object/image construction and publication, including the consumers affected by dissolving foundation and backend. It also updates their documentation, boundary rules, tests, recovery codecs and public facades together. Package acquisition, live interpreter execution and filesystem publication remain real owners outside the transformation pipeline; they may supply inputs or consume outputs, not perform hidden compiler stages.

The Omega-written compiler and bootstrap chain are separate implementations. This plan does not claim to rewrite them incidentally. Their dependencies, commands and artifact contracts must still work after the Rust compiler cutover.

A single cutover means all production entry points switch to the completed new contracts together, old paths and temporary adapters are deleted in that change set, and the full boundary checks are enabled when it lands. Development commits and parallel branches are permitted working material; none is an independently shipped migration milestone. If final validation fails, the old released route remains in place. This is not a runtime fallback between two compilers.

3. Recommended destination and stage contracts

Proposed · unverified contracts. This figure states the intended whole-program handoffs for one coordinated cutover. The table below supplies their invariants; §8 names the feasibility work that must finish before implementation.

Each arrow carries the complete next input, including records destined for later stages. Compiler evaluation stays inside its requesting stage. Runtime execution starts from a finished product; it is not a compiler stage or a side helper.

00–10 are proposed ordering numbers, not current crate numbers or a claim that these contracts are implemented. Current Psi/Omega numbers still locate existing code. Feasibility work in §8 may revise the proposed boundaries.

Every representation carries the current program, its identity, needed provenance, unconsumed requests and established facts. Stage 00 admits external inputs; facts first computed later enter that producer's output. A later stage consumes these records from its immediate predecessor. It never asks an earlier owner to recover a fact or perform more work. A retained earlier executable graph, source lookup, mutable Build context or producer callback is not a carried record.

This is a compilation record, not a proposal to put native configuration into portable Psi. The Psi-owned program and source operations remain target-neutral; they see only the neutral projection of carried requests. Native target/ABI data has an Omega-owned type. The exact acyclic record/type arrangement is an open gate, including how untouched inputs pass through Psi work without Psi importing Omega. Passing a callback or opaque source owner fails that gate.

4. Source settlement, evaluation and provider-body closure

Keep the operations visible

The canvas unfolds each proposed owner into its operations and intermediate forms by default. A shared owner does not erase lexing, parsing, resolution, typing, preparation, lowering or checking. Decimal labels identify operations inside a proposed stage; they are not current crate numbers.

Proposed owner Visible operations, in dependency order
00 Inputs Record source custody; admit compilation requests and budgets.
01 Source Lex → tokens; parse → syntax; resolve → bound names; type → typed trees; prepare applications and required values → prepared trees; lower → lowered Psi; check → accepted Psi; selected Psi optimizations → transformed Psi; check transformed Psi → accepted result.
02 Portable publication Encode accepted Psi; seal identities, evidence and carried requests.
03 Native planning Join Build selections to checked bodies; compute and validate calling policies; lower to abstract operations; optimize abstract operations; lower to target operations; select instructions; optimize selected instructions; close retained body demand and generated recipes.

This order shows dependencies, not a promise of one visit per operation. Source resolution, typing and preparation have demand-driven worklists. Required value evaluation privately prepares, lowers, checks and admits the exact invocation, then executes it and returns a value plus receipts to preparation. Display that sequence inside the preparation operation. Final program checking remains visible after lowering. Selected Psi passes run only after that check; the same checker runs again only for a nonempty selection. Native planning likewise closes its worklist before releasing its output. These iterations must remain visible in the map; hiding them would misrepresent the proposed design.

The mapping preserves the operations documented by the compiler route and the optimization ordering. Their proposed grouping and exact private scheduling remain subject to §8, including generated body constraints and optimization-related reach. A diagram is not evidence that those ordering gates have closed.

Why the old source stage boundaries change

The recommendation is to replace the externally sequenced Psi 00–06 source route with one source-settlement transition. Source acquisition remains outside it; canonical publication and all native work remain after it. Its private operations retain useful names and tests: lexical/syntax preparation, name and body resolution, typing, application preparation, structural lowering, obligation generation, proof search and independent certificate admission. The lowered-form checker remains the sole semantic verdict. Combining ownership does not merge proof search with its checking authority or weaken a refusal.

Lexing/parsing must be demand-aware too. Settlement starts with admitted bytes, not an eagerly parsed forest of all available files. It activates a unit only under a recorded root/dependency request, lazily prepares its syntax and retains that result in its private state. This avoids both a callback into an earlier numbered parser and new errors from unused files. The exact activation/error order is a compatibility obligation, not an opportunity to parse more input.

The private state owns admitted source custody, active scope/bindings, syntax, resolved and typed rows, prepared applications, pending evaluation jobs, accepted invocation artifacts and charging records. A work item names its inputs, requester and unresolved dependency. Completing it publishes a new immutable result for dependants; it does not mutate an already admitted answer. Equivalent preparation requests may share immutable code and established facts. Invocation deduplication is allowed only where the proved request identity and existing accounting contract permit it. Distinct deployments, sponsors and actual invocations retain their required execution and receipts; the current invocation accounting is not blanket memoization. A dependency cycle or exhausted budget follows the existing refusal semantics; there is no guessed constant, default provider or ambient host observation.

The old numbered source crates cease being callable stages. Their useful algorithms move into this owner or independent checking packages. Keeping the same stage calls inside a new settle() wrapper is specifically not completion. The scope is bounded by one target-neutral source result; package acquisition, process execution, native lowering and file publication are not absorbed into an all-purpose compiler stage.

Evaluation is an explicit operation on accepted code

The source compiler currently requests values while preparing a program; the evaluator also prepares and checks invocations. Source preparation, invocation preparation show the mixed ownership. The spec requires checked, hermetic evaluation, not an external executor interface.

01 owns source evaluation; 03 owns calling-policy computation. In 01, private operations construct, lower and check the exact invocation, bind its caller, arguments, target/supplies, permitted observations and work account, execute it, and use the result to finish source preparation. Preserve termination, empty runtime-service reach, suspension/trap restrictions, executable dependencies and all other invocation admission rules. Each invocation uses fresh owned value storage; only permitted value snapshots and bound receipts leave it. No host/compiler reference escapes into a computed value.

03 evaluates carried, accepted calling-policy code over the carried signature, target facts and admission record, then checks the returned ABI plan. The current CallingPolicyEvaluator callback is a path to retire, not a proposed shared service. A private evaluator interprets the stage's accepted input; it cannot request source preparation or choose a different logical body.

The current source-job preparation, retained-product preparation and invocation execution must be assigned to these owners together. The reverse dependency already exists; reversing one import is not the repair. Language execution is compiler-semantic work, not a generic primitive. Sharing an interpreter-shaped compiler service outside the stages would preserve the rejected topology. Any shared algorithm must actually be language-independent; otherwise assign it to the stage or revise the stage boundary. Keep runtime interpretation of finished Psi a separate product consumer, outside compilation.

Close logical providers without violating the firewall

Available declarations are not roots. Settlement receives admitted Build selection/binding descriptions in Psi-neutral data: exact declaration IDs, source scope, target keys and language-level requirements. It owns discovery and preparation of the required checked candidate bodies and their transitive source dependencies. The output contains the checked catalog, neutral selection records and their acceptance/provenance. Nothing later can request another source file, activate a declaration or rejoin a source SymbolTable.

The Psi product contract keeps exact checked candidates portable; Omega joins the target's Build row to that catalog. Source settlement must not take over target-specific provider choice. Omega then evaluates and validates physical ABI plans over those closed identities. Failure cannot trigger an alternative logical provider or reopen settlement. The current closure loop and calling-policy inputs must therefore be split by meaning, not moved wholesale before a renamed O00. Calling-policy code needed later must already be an admitted immutable artifact.

Unverified planning obligation: demonstrate that logical provider choice can be separated from target ABI realization with the same choices and refusals. Where a choice requires a target observation, state the neutral admitted input and its owner explicitly. Passing an Omega ABI object into Psi, hiding a call behind a trait, or preparing all candidate source bodies is not an answer. If this separation cannot preserve behavior, revise the phase contract before implementation; do not ship a backedge or quietly accept fewer programs.

5. Whole-program reach, generated code and resources

Three body sets, with different obligations

Set Meaning What membership does not imply
Available Admitted source or accepted code that a valid request could select. Source availability and native code availability are separate catalogs. It does not demand typing, proof, ABI realization, native support or emission merely by existing.
Demanded A recorded semantic/native dependency of a selected root, with the requester and selected binding. It does not guarantee the body survives allowed optimization, nor permit a different source selection.
Retained A body/reference still required after the relevant optimization and closure step. It does not let later phases invent another body or erase its obligations.

Source settlement closes the source decisions. Native planning closes the native retained set over accepted code. An accepted body can be available for native planning without yet requiring target lowering; this is necessary to preserve current pruning. The current callback walk uses emitted object references, so “all bodies up front” is not a sufficient design.

Native planning must derive explicit reference edges from the current program and keep their relationship to optimization. Each newly retained native body is processed within that phase's worklist. Changes to an already settled logical binding refuse. Work/identity records distinguish shared processing from repeated execution. At phase exit, a certificate or independently checkable invariant identifies the closed native body/reference set.

Unverified: prove that all later encoding/layout references are a projection of this set. If an existing optimization changes whether a callback is needed, its demand-changing part belongs before closure, or the planning boundary must move. It may not survive as an image-time discovery followed by a recursive compiler invocation. Preserve harmless unavailable target support in bodies that the old route prunes; a larger conservative native roster can change acceptance even when its final bytes omit those bodies.

Generated bodies join the program before encoding

Entries, foreign adapters, callback transports, interrupt entries, stack-switch helpers, floating-control/hosted sequences and any live post-handoff writers must have explicit identities, inputs, effects, calls and resource contracts. Native planning declares their recipes; physical planning instantiates them using carried ABI plans and actual body effects. Fixed target byte templates are allowed only as fully described encoding inputs, with effects and fixups; they cannot hide an instruction-selection algorithm in target description.

This replaces entry generation from a completed object. Today its request obtains body effects, then the bridge chooses scratch registers and frame/encoding details. Those dependencies must be exposed in the physical program. Image construction may resolve addresses or format relocations, but may not call these generators. The old suggestion to place their whole implementations in an O14 writer is withdrawn.

The post-handoff plan already distinguishes address-free transfer steps from invocation relocations. Classify actual callers before claiming a production route: an exported library function or its tests alone do not prove that image construction uses it. Where required, its transfer program follows the common encoding route; otherwise retire or retain it only with an evidenced non-production owner.

Binding uses a complete resource summary

The current stack requirement contains body demand, bridge bytes, call-stack bias, alignment, entry plan and fault premises. Transitive demand includes called/private bodies; fault analysis reads physical instruction correspondence. The replacement record must name the same program, target, entry, installation and body version and preserve all these dimensions. It must distinguish a finite admitted bound from unknown/unbounded demand; “missing” is never zero.

Physical planning establishes register/effect and frame facts for ordinary and generated bodies. Resource analysis then combines the whole retained call graph, entry/bridge costs, arrival nesting and fault premises. Installation binding checks that summary against admitted cohorts, environment assumptions and placement requirements and publishes one bound physical program.

Today O03 constructs numeric stack guards before this point. The recommendation is to represent those requirements as symbolic operands with reserved constraints until binding. Binding must not change body membership, register pressure, clobbers, control-flow shape or frame demand. Encoding may choose a carried width alternative after the value is known.

Unverified: prove this stability for every current numeric consumer. A late literal patch is insufficient if the value chooses a different instruction sequence, creates a helper or alters its own stack bound. The plan must either move that decision into physical planning with a proved finite dependency order, or revise the boundary. It cannot claim a global pass while secretly compiling handlers through later stages and returning to the installer.

Encoding and layout have a closed executable input

Common encoding owns ordinary instructions and all generated executable fragments, including frame prologues/epilogues. It emits legal alternatives and fixup data: bases, signed ranges, alignment, bitfield geometry, external symbols, callback/image addresses and identity bindings. Layout chooses carried encoding alternatives and patches their fixups. O08's callback-byte comparison is validation, not a demonstrated callback producer; preserve it. The confirmed late instruction rewriting in frame application needs carried alternatives instead.

Preserve the present reason for body-first relaxation before frame insertion. The layout phase can perform those internal placement steps using already encoded frame fragments; moving frame encoding earlier need not force a new relaxation algorithm. Exact bytes, branch choices and failures must be compared. The object and image phases then consume closed encoded content and explicit relocations. No stage after encoding may create a new executable body.

6. Data ownership, runtimes and independent checks

Classify every export before assigning a home

Kind Permitted owner Test for the distinction
Generic primitive Foundation No language, program, target or source-authority meaning.
Definition Narrow representation vocabulary Names a stable semantic or target concept; holds no live source/body lookup.
Carried record The first complete program form that establishes it Includes identities/provenance needed to interpret it, not an earlier program used as a database.
Producer The phase whose complete input permits the calculation Creates a plan, offset, choice, commitment, body or authority-bound result. “Pure” does not make it data.
Checker Admission boundary or explicit independent verifier Checks evidence against a stated input contract; it does not choose missing semantics.
Live host operation Packages, runtime, products or host support Performs acquisition, execution or publication, not a compiler transformation.

terminal-psi/vocabulary (TPV) is a proposed family of small definition/carrier leaves, not a destination for 40k lines of mixed semantic code. Split identities, scalar/path definitions, declarations, access/resources and layout by their actual dependencies. The old 40–45k figure was an inventory estimate, not an approved API or a size target.

RetainedDeclaration contains SourceFile; SourceFile contains text and ownership/scope data; rejoining consults the source symbol table. Those capabilities stay inside source settlement. Publish only necessary IDs, selected declaration summaries and immutable error provenance. Likewise, application preparation and access-plan commitment construction are producers. Layout defaults are realizations, not automatically language promises. Moving these modules unchanged into TPV would reproduce the problem.

Generic byte cursors, record encoding and digest bytes may become wire. Scalar identity encoding and field/case path encoding assign semantic tags and stay with their representation codecs. A SymbolHandle-keyed alias stays with symbol vocabulary even if its generic hasher moves to foundation.

Carry what emission actually reads

The focused audit found ordinary publication reading abstract_program to derive physical evidence scope, and emission construction reading the earlier program's entry/identity and admitted cohorts. Publication, construction These checks protect real contracts. Move their required records into the current form; do not delete the checks or carry the entire earlier executable graph under a new field name.

For every EmissionFacts consumer, record the field read, meaning, producer, first available phase, version/identity and final consumer. Replace access to whole abstract/Terminal programs with those current-form records. Current immutable structural declarations may be shared by content identity where unchanged; executable graphs and source owners may not be retained as lookup shortcuts. The deletion condition is that consumers no longer recover facts from an earlier program, not that the struct or Arc changed its name.

Runtimes consume products and admitted provision records

Keep sealed admitted carrier definitions separate from their issuing producer; terminal-runtime already names an admission type. The runtime must not import a producing stage merely to read it. Native/Psi execution provisions carry exact program/target/binding identities and the necessary host plans; only the corresponding admission phase may issue them.

The Psi execution route does not automatically require a native version of the main program. It may require generated foreign adapters: current capture emits one. Model those as explicit auxiliary native roots with their own completed pipeline results. They use the common planning/encoding route, then join the provision output. Do not revive a private adapter compiler inside a runtime carrier constructor, and do not reject a valid Psi program because an unused native main body lacks support. Independent components remain separately admitted products; the migration does not merge their address spaces or change their isolation/ABI contracts.

Verification has explicit inputs and independent authority

Retain producer admission at trust boundaries and object/image consistency checks. Keep explicit correspondence/rewrite replay separate from ordinary production. Its request identifies which originals must be retained; absence refuses that audit. Moving a validator beside a representation does not remove its dependency on a producing stage or make it independent.

The verifier route receives current data and retained evidence directly through its declared phase/product boundary. Its input and report are explicit records; its checking logic retains independent authority. Program representations hold no callback into the native driver or an earlier stage. Separate shared vocabulary/codecs from independent checking logic; do not deduplicate a verifier into the producer whose error it must catch. Proof search, certificate admission, source acceptance, canonical decoding and host execution authorization remain distinct contracts.

8. Planning completion gates — before implementation

These are not deferred cleanup tasks. They are the remaining proof/design work needed to turn the recommendation into an implementation-ready contract. Each must end with a concrete field/API model, source-backed consumer inventory and an ordering argument; a diagram alone does not close it.

Gate Required result What would make the proposed boundary fail
Numbered input custody Map every request/fact from admission or producer through each 00–10 handoff to its final consumer, with an acyclic type-ownership model preserving the Psi/Omega firewall. A mid-pipeline external input, side service, retained earlier program, callback or hidden compilation in a carrier.
Evaluation ownership Assign source evaluation to 01 and target-policy computation to 03; inventory the private algorithms, admission/accounting/result records and deleted executor/callback APIs. Language execution relabeled as a primitive, stage work still dispatched outside the chain, or changed values/refusals/charging.
Source activation and closure Exact lazy source activation, extension, evaluation and charging state transitions; preserve error order and checker verdicts. Show that private operations replace, rather than call, the old source stages. Eager errors from unused files; dynamic source discovered after portable publication; a callback to an old stage.
Logical provider separation Map every provider-selection input to neutral admitted Build/source data or later ABI admission. Close selected source bodies and calling-policy code before source publication. A later target decision needs another source body, an ABI object enters Psi, or moving checks changes provider choice/refusal.
Native demand closure Show available/demanded/retained membership and every generated reference; prove later encoding/layout cannot discover new bodies. Preserve optimization-pruned unavailable targets. A conservative roster introduces new native obligations, or object symbols remain the authoritative source of reach.
Generated physical program Model entries/adapters/handlers/hosted/writer code, their body-effect inputs and caller constraints in one physical form. Prove ordinary body effects remain valid after adding helpers. Late scratch/frame choices, missing helper clobbers or image-time code generation.
Resource/binding stability Inventory every numeric consumer; model transitive demand, bridge/bias/arrival costs, fault premises and identity joins. Encoding/layout closure Complete alternative/fixup schema for both ISAs, callbacks, frames, entries and formats; account for exact old relaxation decisions. A layout phase must invoke an encoder or the new order changes bytes/refusals without authorization.
Carried-fact and authority interfaces Finish per-export/per-field classification, including EmissionFacts and source custody; specify allowed constructors and runtime/verifier inputs. A representation exposes an earlier graph, source lookup, producing stage or driver callback.
Extra-arrow closure Account for every mechanism in §2 with its actual producer/consumer, replacement handoff, deleted API/path and behavior check. Distinguish production, host execution and independent verification. A detour is merely renamed, hidden by a coordinator or removed from the picture while its code survives.

A gate may require changing the proposed boundary. Resolve that change in the plan and its consumer contracts before coding. Do not hide the conflict with an extra shared library, blanket allowance, speculative new acceptance rule or a “temporary” runtime branch intended to survive cutover.

10. Validation and exact done criteria

This is the validation plan for implementation, not a report of tests already run. Establish the baseline on the chosen source and run the replacement on the same inputs, targets, optimization settings, permissions and budgets. Existing focused tests stay with their operations; add only tests that prove changed contracts or previously untested failure modes.

Boundary Required evidence for the cutover
Source and evaluation Same selected source activation, values, work charging, diagnostic provenance and accepted/rejected/incomplete results; unused invalid/unavailable source remains governed by the same demand rules. Exact-budget and one-unit-short behavior survives.
Source acceptance and proof authority Positive/negative twins preserve the sole lowered-form verdict and independent certificate checks. Wire decoding, proof search or a native request cannot substitute for acceptance.
Logical and native provider demand Same exact providers/bodies/calling-policy outputs; previously selected choices cannot change. Unused or optimization-pruned target-unsupported callbacks do not become new errors; reached equivalents still refuse.

Object/image/products Byte-for-byte canonical artifacts and native outputs, identity/digest/relocation/signature contracts and publication receipts remain stable for identical deterministic inputs. Preserve failure atomicity and component isolation. Any proposed intentional format/byte change requires an explicit separate design decision, not an unexplained comparison waiver.

Independent validators Tampered facts/identities/bytes refuse; valid retained evidence passes; missing requested originals refuse. Production has no hidden replay/driver callback and does not lose required trust-boundary checks.
Architecture and deletion Check complete dependency graph, per-export ownership and all public entrances; no old backend/non-primitive foundation path, bypass, adapter, duplicate route or unexplained allowance remains. Text matching alone is not proof of behavior.

Use repository-required mbx commands for actual Rust builds/tests and the shared host budget. The exact changed crates and programs determine the focused validation set; the integrated cutover also exercises every affected public route: compile/check, native and Psi execution, component production/import, explicit validators and publication. A passing library test is not evidence that an untested public route migrated.

The migration is done only when all planning gates have closed, every inventory row and retirement item is accounted for, all producers and consumers use the same final contracts, the exact combined change passes its behavior/identity and architecture checks, and the old route is deleted at the single cutover. A page build, a smaller crate count, a renamed stage or a partially connected native example does not establish that outcome.
