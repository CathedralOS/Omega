Foundation and backend plan

Omega is one linear pipeline, yet about 318,000 lines sit beside it: 96,000 in foundation/ and 222,000 in omega/compilation/backend/. This plan moves nearly all of it into the pipeline. Foundation keeps about 14,800 lines of primitives. 0. Method and how much to trust it

  • Crate edges: cargo metadata --no-deps from a fresh run. It matches the cached meta.json exactly (1478 path edges). Only production edges count (normal and build); dev-dependencies are listed separately.
  • Module and type usage: scratchpad scripts fdn/modscan.py, fdn/report.py and fdn/sub.py, with output in fdn/usage.json. They scan non-test .rs files and skip tests/ directories, tests.rs, *_tests.rs, source_guards.rs and brace-matched #[cfg(test)] items. They record crate::Seg, crate::{..} and crate::mod::{..} paths. A path counts only when the user crate declares that crate as a dependency, which removes local modules with the same name (for example optimization:: inside Omega 06).
  • Limits (unverified):
  • The scan uses regular expressions, not a Rust resolver.
  • A glob (use x::*) or a path inside a macro body can be missed.
  • A type reached through a re-export is credited to the re-exporting crate.
  • The defining file shown for an item is the first pub definition the script finds, so it is occasionally wrong. Example: ScalarType shows as closed_integers.rs::tests, but it is defined in scalar_terms.rs:711.
  • "Declared but unused" means the scan found no non-test reference. Confirm each case with a type check before deleting the dependency.
  • Positions: a position is a Psi stage NN, an Omega stage NN, a representation (psi-repr X, omega-repr X), or a non-pipeline owner: backend, realization, products, compiler, packages, build, cli, interpreter, tools.

Part A: Foundation keeps only primitives

1. The rule and what decides each destination

What the 2026-11-17 ruling says

Foundation keeps only primitives. A primitive is a generic building block with no Omega-language or compiler meaning: arenas, handles and dense ID tables, the record codec, wire bytes and digest encoding, plain diagnostics carriers, source text positions, and big-integer arithmetic.

Foundation has no language layer. A language table (intrinsic catalogs, spellings, the scalar and proposition term language, numeric and float rules, the optimization catalog, access and layout rules) moves into the first pipeline stage or representation that needs it. Later stages then carry it forward. A crate that no pipeline stage uses leaves for its actual owner, even if that splits the crate.

The four verdicts

Verdict Test Text that decides it
primitive (stays in psi/foundation/) Generic building block with no language or compiler meaning, used by the pipeline The ruling
move into <stage or representation> A language table, or a table, handle, plan or summary that a stage fills from the program. Goes to the first representation that needs it; a type used by one stage (plus its neighbor) goes to that stage. The ruling. Also AGENTS.md "Representation-to-representation pipeline: … Carry needed semantic facts in that representation; do not bypass the pipeline with sidecars".
move to <non-pipeline owner> No pipeline user The ruling. Also pipeline.md table: "Build-time execution inputs and accounting → Psi compilation/build-time-evaluation/"; "Source acquisition and package storage primitives → Omega packages/".
delete Unused, duplicated, or re-exported AGENTS.md rule 6: no second copy of a data structure

Two new representation packages the ruling implies

  1. psi/compilation/representations/terminal-psi/vocabulary - What it is: the "carried vocabulary" of Terminal Psi, abbreviated TPV below. - Why it is needed: many tables are first used by a source-side form (syntax-trees, symbol-resolved-trees, typed-trees) but are also read by Terminal Psi, Omega, realization or the interpreter. The firewall (boundary.rs:352-358, PERMITTED_OWNERS) forbids those readers from reaching source-side forms, so such a table cannot live in the source-side form that first needs it. - The owner's answer: such a table lives in the carried representation under the Terminal Psi family. The source-side forms depend on it, and the Terminal and Omega sides already may reach it, because terminal-psi/* is in PERMITTED_OWNERS. - It follows the existing precedent of native-vocabulary: "owns the leaf types every native form carries unchanged". - It should be split by subject into nested packages (judgment): identities, scalars (term language and numeric rules), declarations, resources (access and extents), layout. At an estimated 40–45k lines it would otherwise be the largest crate in the workspace, which is OWNER_CODE_CONCERNS category 5, "Too big to read".
  2. psi/compilation/representations/build-requests - What it is: the input representation for Build. It holds what Build evaluation computes and stages 02–05 read: Build selection requests, executed results, product targets and operands, layout target facts, and compiler-evaluation requests. - Why it is a Psi package: build-time-evaluation (Psi) produces it, and the firewall forbids Psi from depending on Omega.
  3. psi/compilation/representations/source-files (judgment) - What it is: the input of stage 00, which is already named source-files-to-tokens. It holds LoadedSource(s), SourceContents, the captured source tree and snapshot (capture.rs), read_accounting, SourceCatalogue, and the consumed-source identity (source_identity, PackageKeyIdentity, DependencyScope, SourceOrigin, SourceResolutionStratum). - Why it is not foundation: these carry package and source-loading meaning, not plain text positions.

The firewall still decides two things

Psi never depends on Omega (boundary.rs:228-233). So:

  • A Psi-side table used mainly by Omega still goes to a Psi representation.
  • An item with no pipeline user goes to an Omega owner only when no Psi crate uses it.

Text the ruling supersedes

Part B: Backend dissolves (owner ruling 2026-11-17)

The ruling: omega-rust/omega/compilation/backend/ should not exist, because native compilation is one linear pipeline.

Today the backend is 221,793 lines in 29 crates: all .rs lines, counted the same way as §2. Every Omega stage except O01 depends on backend crates directly, and so do 6 of the 7 native representation families (all except native-vocabulary). After Omega 09, the native driver keeps working outside the numbered pipeline: it calls machine-emission, object-file and image-emission, which turn the program into an object and an image.

The plan:

  • Give that work numbered stages (O10–O14) with their own representations.
  • Fold encoding into Omega 07.
  • Turn the selected target's description into an input representation that Omega 00 receives and the native forms carry. This is the Omega-side analogue of build-requests, and it answers Q-E.
  • Carry the program-derived provider plans in a second input representation.
  • Move the rest to products, realization, the interpreter or tests.

B4. The target description becomes an input representation

New package omega/compilation/representations/target-description.

  • Who builds it: Build, once per selected target. This matches the board item BUILD-OWNED-TARGET-SELECTION (TASKS.md:83: "Retire target-prefixed machines for target-keyed Build rows").
  • Who receives it: Omega 00, as an input. Every native form may depend on it (rule B-R2).
  • Why it fits the existing rules: Psi never uses it, so the firewall is satisfied. The runtimes may depend on representations (PERMITTED_OWNERS[1..]), so terminal-runtime and native-provider-runtime keep their ABI geometry.
  • One expected side effect (unverified): register-environment today caches "one validated instance per target process-wide". As an input representation it would be built once by the driver and passed down, which removes that process-wide cache (tools/ratchets/cache_state.txt territory).

Are ISA encoding tables part of the input, or the encoding stage? Decision: split them

The module scan of non-test users supports a split:

  • The encoders are stage work and go to the encoding stage, O07.
  • The files: selected_form_encoding.rs (x86 24,017; AArch64 18,243), frame_protocol.rs, encoded-scalar-plan, normalized-foreign-call-plan. About 46k lines including those plan crates.
  • O07's own doc says it "Routes each instruction kind to its target ISA encoder (x86-64 or AArch64)".
  • The main encoder callers are O07 itself: encode_*_selected_form, memory, scalar-call, foreign-call templates, system and table calls.
  • encoded-scalar-plan and normalized-foreign-call-plan have no users except the two ISA crates.
  • The register and effect catalogs are target description.
  • The files: register_model.rs, machine_effects.rs, preservation_storage.rs.
  • Their users are register-environment and selected-instruction-analyses. Those are read at O03–O06, before anything is encoded, so they cannot belong to O07.
  • Image-time sequences go to O14: generated_entry.rs, hosted_kernel.rs / hosted_sequences.rs, ieee_float.rs, floating_control.rs and the lib.rs byte constants. Their users are image-emission, native-artifact and machine-emission (the bridges).
  • Post-handoff writers go to O14 (judgment): post_handoff_writer.rs together with post-handoff-writer-plan, whose README says the plan "derives writer programs" and the "ISA crates encode those fragments".
  • The leftover small crates:
  • x86_64-encoding (78 lines): its users are isa-x86_64 and native-artifact. It moves into O07's x86 encoder module, and the native-artifact use moves with the image-stage code that calls it.
  • isa-conformance (579 lines) is a dev-only test suite of both ISA crates. It moves beside O07's tests or to tools/test-support.

What does not fit cleanly. O08 and O09 re-encode branches after O07 (branch_forms, jump; x86 short-branch relaxation in O09), and so does O11 (frame insertion re-encodes stretched branches). If the encoders live in O07, these are stage-to-stage calls, which boundary.rs forbids. That is open question Q-F.

  • Q-A. Where does the shared process runner go?
  • Who uses it: the native-provider runtime, package resolvers (resolver-execution, source-acquisition), the CLI and three dev tools all start child processes through bounded-process. None of them is the compiler pipeline.
  • Why the obvious home fails: the runtime's dependency check only lets it use compiler crates, so it cannot use a crate under packages/.
  • The options:
    • (a) The interpreter owns the runner, and packages depend on an interpreter crate.
    • (b) Packages own it, and the runtime check gains one exception.
    • (c) A small shared host area outside the compiler, for example omega/host/.
  • Q-B. May Terminal Psi and the native compiler read Build inputs and loaded source data directly?
  • What reads them today: Terminal Psi uses CompositionMode and the layout target facts from Build. terminal-semantics uses the consumed-source identity.
  • The options:
    • (a) The native side may depend on the new build-requests and source-files packages. They contain no source trees.
    • (b) Terminal Psi copies the few fields it needs into its own vocabulary, and the native side never reaches the input packages.
  • Q-C. Is Build-time evaluation a second front-end driver? It calls stages 02–04 directly instead of going through the Psi facade (source-compiler). Allow it as a driver, or route it through the facade?
  • Q-D. "Only its predecessor": immediate or any earlier form? Every native representation (all 13 crates, checked in metadata) uses Terminal Psi identities directly. A strict immediate-predecessor rule would force each form to re-export the previous form's identities.
  • Q-F. Who encodes branches after stage 07?
  • The problem: stage 07 encodes instructions. Stages 08 and 09 lay out and relax branches, and the new frame-insertion stage (O11) re-encodes branches that an inserted epilogue stretched. All three call the ISA branch encoders today (branch_forms, jump). If the encoders live in stage 07, these become stage-to-stage calls, which boundary.rs forbids.
  • The options:
    • (a) Stage 07 writes every branch's possible encodings (short and long forms, byte templates) into its output, so later stages only choose and patch. This changes how the output is laid out, but not which programs compile.
    • (b) Branch encoding stays a small target library that stages 07–11 may call. That is an exception to "no crate outside a stage owns stage work".
    • (c) Fold stages 08, 09 and frame insertion into one layout stage that owns branch encoding. That reverses the reasons their docs give for keeping them separate.
  • Q-G. Where does realization sit in the linear pipeline?
  • What it does: provider planning, selection and admission (the crates under omega/compilation/realization/) compute the provider plans, installation facts, task plans and boundary applications. Omega 00, 02 and 03 read those.
  • What this plan does meanwhile: treats them as an input representation, provider-plans, beside the target description.
  • The options:
    • (a) Realization stays a separate producer of that input, like Build.
    • (b) Realization becomes a numbered step before Omega 00, and its output is Omega 00's input representation.

8. Side findings (for OWNER_CODE_CONCERNS.md; no extra PRs)

  • Duplicated wire helpers. psi optimization and optimization-core each define DomainDigestEncoder, Cursor/TakeError, push_encoded and structural_variant_accessor!. Step 3 fixes this.
  • Duplicate opaque-representation records. language-semantics::opaque_representations duplicates the owner that pipeline.md names, typed-trees::opaque_representations.

  • A very large carried vocabulary. terminal-psi/vocabulary would hold an estimated 40–45k lines. Split it by subject (step 11) so it does not become one unreadable crate.
  • The native driver copies stage 02 output past stages 03–09. native-compiler/src/pipeline.rs:265 (emission_facts) hands stage 02's lowering facts and abstract program straight to emission, around the pipeline. Step B7 removes it.
  • A process-wide cache in register-environment. It caches "one validated instance per target process-wide". Building the target description once per compile (step B3) may remove it (unverified).
  • emit_fragment_object lives in native-artifact. It runs four emission steps plus object building, so a product crate is driving pipeline work. Step B12 deletes it.
