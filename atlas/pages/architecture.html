Proposed contracts and open questions

Proposed phase boundaries are judgment, not implemented or verified behavior. Open planning gates.

00 Admit inputs

Record acquired source/package custody, scoped roots, Build/configuration requests, target/component/provider/loader/output inputs, selections, budgets and staged receipts. Values requiring evaluation are produced in 01.

Open contract: Specify complete input fields and authority without activating unused source.

Read proposal · Recorded plan
Admitted inputs

Source inputs and the requests needed later, carried in one compilation record.

Read proposal · Recorded plan
01 Compile source + values

Own lazy syntax, resolution, typing, preparation, lowering and hermetic evaluation. The lowered-form checker gives the sole semantic verdict. Preserve independent certificate admission and the specified optimization/checker order.

Open contract: Prove activation/error order, invocation admission, value isolation and charging. Replace old APIs with private operations, not a wrapper.

Read proposal · Recorded plan
Accepted program + values

Checked candidate bodies, computed values, neutral selection records, invocation receipts and provenance, with downstream requests.

Read proposal · Recorded plan
02 Seal portable program

Publish canonical target-neutral Psi from accepted code. Forward remaining inputs in their declared compilation record; native configuration does not become portable language semantics.

Open contract: Define acyclic type ownership: Psi sees only neutral projections and never imports Omega target/ABI types.

Read proposal · Recorded plan
Psi + carried inputs

Canonical checked code and its catalog, evidence and summaries, with the records needed downstream. No source owner or lookup callback.

Read proposal · Recorded plan
03 Plan native code

Join carried Build selections to the checked catalog. Compute and validate calling policies inside this stage. Close retained native demand, call/ABI plans and generated-body recipes without source lookup.

Open contract: Prove body-demand closure and exact policy admission/results, preserving optimization-pruned unsupported targets.

Read proposal · Recorded plan
Selected native program

Retained bodies, ABI plans, obligations and generated-body recipes; carry target, installation and output records forward.

Read proposal · Recorded plan
04 Build physical program

Represent ordinary and generated bodies together, including handlers, entries and adapters. Own register choices, frames, effects and symbolic resource uses.

Open contract: Prove complete generated-body effects, caller constraints and finite resource ordering.

Read proposal · Recorded plan
Complete physical program

All executable bodies, register/effect/frame records and resource dependencies. Handler analysis needs no object-emission detour.

Read proposal · Recorded plan
05 Bind resources

Use complete physical resource summaries and carried installation limits. Check transitive stack, bridge storage, call bias, alignment, fault premises and placement identities.

Open contract: Binding must not change allocation, effects, frames or body membership.

Read proposal · Recorded plan
Bound physical program

Complete physical code with bound resources and installation identities; preserve encoding, format, loader and output requests.

Read proposal · Recorded plan
06 Encode all code

Encode ordinary and generated bodies, including frames. Publish legal alternatives and complete fixups; imported encoded components remain admitted data.

Open contract: Complete alternatives/fixups for both ISAs and all formats. No later executable-body producer.

Read proposal · Recorded plan
Encoded code + fixups

Body/frame fragments, alternatives, fixups and attribution, with placement/output facts. No earlier executable graph.

Read proposal · Recorded plan
07 Lay out code

Place fragments, choose carried alternatives and patch references. Preserve body/frame relaxation, ranges and alignment without an encoder callback.

Read proposal · Recorded plan
Laid-out program

Resolved content, symbols and placement records with remaining object/image/output requests.

Read proposal · Recorded plan
08 Build objects

Construct object containers from laid-out content and carried symbols/format requests. No source/ABI rediscovery or private helper generation.

Read proposal · Recorded plan
Objects + image inputs

Objects, attribution, entry/evidence records and carried container, loader and binding inputs.

Read proposal · Recorded plan
09 Build image

Place objects and produce relocations, signatures and container/loader metadata from carried inputs. Executable code is already encoded.

Read proposal · Recorded plan
Completed image

Final image, regions, symbols, relocation evidence and provision records, plus the publication request.

Read proposal · Recorded plan
10 Publish products

Install completed artifacts using the carried output request and return receipts. Publication performs no compiler transformations.

Read proposal · Recorded plan
Published products

Finished executable/component/Psi products and receipts. Runtime execution consumes finished products after compilation; it is not a pipeline helper.

Provider selection

↑ Back to the whole compiler

Provider closure

Settlement follows reached exact bodies and Build bindings. When reach changes, it prepares policy inputs from the retained accepted publication and checked source custody, then realizes target supplies. It repeats until bindings stabilize; this loop does not restart source compilation. Available, demanded and retained code are different sets.

Read subsystem · Pinned source
Prepare provider · policy inputs

Publishes the retained accepted closure and admits its source-selection packet. Reached requirements and Build bindings determine which calling policies to evaluate. The resulting calling plans return to settlement; publication does not re-lex or re-type the source.

Psi runtime

Runtime · admission

The Psi product route admits target/provider and entry provisions without emitting a native image. Provider choice alone does not confer host authority.

Read subsystem · Pinned source
Omega runtime · & host adapters

Target-aware host ownership joins code identity, runtime provisions and external capabilities. It requests execution from the target-neutral Psi engine.

Read subsystem · Pinned source
Psi interpreter

Loads or borrows code, admits supplies, binds imports and invokes/resumes the instance under a work meter. It never invokes the source compiler.

Read subsystem · Pinned source
Native-provider · worker

A private native provider process serves host-adapted external calls. It is distinct from running the user's emitted native executable.

Read subsystem · Pinned source
Compile-time execution

↑ Back to the whole compiler

Source evaluator

The source compiler requests a compile-time value. This owner prepares and admits its own checked invocation, runs it in the Psi interpreter, and returns the value and work usage to the source caller. The interpreter never calls source stages.

Read subsystem · Pinned source
Calling-policy · evaluator

Build settings prepares and admits a calling-policy invocation, invokes the Psi interpreter, validates the returned ABI calling plan, and accounts for work. This is a different caller from source compile-time evaluation.

Omega-written · compiler

source/psi and source/omega implement the product compiler in Omega, outside the bootstrap variants. The supported compiler subset does not yet establish complete self-rebuild.

Bootstrap peers

Interpreted, compiled-VM and independent native construction routes are peers. Proof experiments have their own scope. Constructing the complete product compiler and its self-rebuild remains an unfinished objective.

Foundation crates

Supporting ownership, not a processing stage. Current foundation includes primitives and semantic/planning code. The proposed migration retains only justified generic primitives.
