The omega executable parses a complete request, selects its owner and turns the result into console output and a process status. Build compilation belongs to orchestration; execution and inspection still have substantial application code. Calling the entire application “only a router” hides those operations. main.rs is the router; execution/ and inspection/ are complete workflows below it.

Startup and the actual command surface

The Cargo package and binary are omega, under omega-rust/omega/application/. Startup first checks the internal native provider-worker protocol. A child launched for a foreign call can enter that worker before normal command parsing. Ordinary startup then removes the global --verbose flag, parses an Invocation, obtains one host execution budget, and dispatches on a compiler worker. Failure to parse exits 64; failure to start the worker budget reports an error. Startup

The parser selects packages, psi, source or run from the first token. Otherwise it puts the token back and parses the default compile invocation. The current default is omega <root.omg> or omega --check <root.omg>; the top-level dispatch has no separate build subcommand. Flat install, update, audit and inspect-terminal are explicitly retired. Invocation and parsing are the source of truth when a README uses an older spelling.

Surface Owner called from the console adapter Result boundary
omega [--check] ... <root.omg> commands::compile constructs orchestration::BuildRequest Ordered target reports or compilation refusals; native products are published unless checking. Source
omega run ... <root.omg> commands::run calls execution::run_project or run_project_cases Compiled product plus host/Psi outcome, captured output and optional comparison. Source
omega psi inspect --machine ... <root.omg> inspection::inspect_terminal calls the shared Build operation Requested machine's checked artifact; no native image. Source

The graph shows operation ownership, not simultaneous execution. Package commands use their review coordinator, which can request compiler work; their edge to output does not imply they are parser-only operations.

Compile requests preserve target and product intent

commands::compile::run translates parsed arguments into a BuildRequest. No target names means BuildTargets::Host; one name becomes Single; several names become an explicit target set. --check chooses ProjectProduct::Check; the ordinary case chooses a published native product. Requested validators, optimization rollback, restricted-action verification and caller-named Build input capture travel in that same request. Translation

The adapter formats single or batch outcomes and optional reports; it does not invoke Psi or Omega stages. Compilation status is distinct from CLI usage: the request contract uses 0 for complete, 1 for rejected, 2 for incomplete because private provisions ran out, and 3 for an internal failure. For a batch, an internal failure outranks rejection, and rejection outranks incompleteness. A report-write failure must also be handled by the console adapter. Compile status policy, usage status

Explicit validators are not ordinary compilation checks. The current registry has TargetOperationCorrespondence, FixedFrameCorrespondence and SelectedInstructionRewriteReplay. Their requests make the producer retain the earlier inputs needed for independent validation. They run before published native output is written; default compilation runs none. A named validator that cannot apply is refused; --every-validator enumerates the registry and reports inapplicable entries. Registry, publication boundary

This also differs from --verify: that request rechecks under retained pins without exercising accepted restricted Build grants. It is not shorthand for the independent stage-validator roster. The distinctions are declared on BuildRequest and enforced by package product admission.

Run uses the exact product compilation produced

The parser chooses native by default, psi for an explicit engine, or the two-engine comparison for --both. --engine and --both cannot be combined. Case inputs require an output directory, cannot use a target override, and currently refuse Psi-only execution. A Psi work budget is allowed only when Psi will actually execute. Argument constraints

run_project allocates a temporary directory and calls the same orchestration::build as compilation. Native and comparison requests ask for NativeDestination::Retained; Psi-only requests ask for RuntimeAdmission. The compilation adapter requires exactly one target outcome and returns its CompileReport. Build request

For a comparison, interpret_product obtains the Psi artifact from that report's retained native program. For Psi-only execution, it obtains the artifact directly from the report. It refuses if the report has lost its artifact. The runtime request receives the same runtime provisions, target, work budget and private entry data produced by compilation; it does not recompile source or rerun Build. Artifact and runtime request

The application explicitly delegates a host filesystem namespace, matching-host native services, a host clock, target-specific x86 flags when applicable, a private sequential memory-ordering environment and an isolated domain exit. It also supplies a command for the native provider helper. Those are actual host capabilities in the request, not authority inferred from entry selection. Their eventual admission is the runtime's responsibility. The atlas must not repeat the older application README's broad “isolated hosted root” description as a statement of this current caller's filesystem delegation. Runtime request fields

Run selection Behavior in the application source
Native, no target override Publish the retained executable, validate component process inputs, launch it with inherited stdin, capture its output and observe its process status.
Native with --target Compile and publish for that target; return TargetOnly without launching the image or reading stdin.
--both, host execution Interpret the report's Psi artifact before publication consumes the native payload, then publish/run native and compare the outcomes.
--both --target ... Follow the target-only path; no host or Psi run is performed. The parser separately refuses a Psi work budget for this non-executing case.
--engine psi Request runtime admission, interpret directly with caller stdin, and return a Psi outcome without emitting or launching a native image.

The control flow is in run_project and run_terminal. Psi-only execution still uses native runtime admission for the selected target's entry/providers; “no emitted image” does not mean “skip target and provider admission.”

When --both first reports a missing standard-input provision, the application captures stdin to a finite replay file, invokes Psi again with it, and later gives those same bytes to native. If Psi completes without a stdin request, the native child receives null stdin; ordinary native-only execution inherits the caller's input. The replay and publication order are explicit in run_project. Multi-case execution compiles once and uses one retained report for its inputs.

Comparison checks the host presentation of termination, including recognized crash causes, and separately checks private-entry backing observations when present. It does not generally compare stdout/stderr or full effect traces. Exhausted work, a pending host effect, unavailable host capability or a Psi exit argument that the host truncates can produce a declined comparison. A native exit of zero does not convert that decline into agreement. Comparison, private entry comparison

commands::run forwards stdout/stderr as raw bytes before its own diagnostics and flushes both streams. Its reserved harness/Psi statuses include 200 for execution/compilation or forwarding failure, 201 for divergence, 202 for incomplete compilation, 203 for a Psi guest crash and 204 for a declined single-run comparison. Case reporting has its own batch handling. These statuses are command-specific; package audit's status 3 is not the compiler request's internal-failure verdict. Run status handling, output forwarding, package audit handling

A concrete CLI trace and its test

The integration test both_exit_status_comparison.rs launches the real binary as omega run --both main.omg in omega-rust/tests/fixtures/run/cli/both_comparison_verdict. Its positive case expects native/Psi agreement. Its twin adds a small --psi-work-budget, expects the native program to exit zero, and still expects the command to report DECLINED and status 204.

The traced route is:

  1. arguments::parse produces Invocation::Run; main selects commands::run.
  2. commands::run constructs RunRequest, preserving the engine choice, target, captured-input request and work budget.
  3. execution::compilation::compile asks Build for a retained native product. Build resolves source/package input, performs compiler and provider admission, completes native work and returns the report. The Build page follows those operations.
  4. interpret_product passes the report's artifact and provisions to the Psi runtime. Native publication and execution then use that same report. Run lifecycle
  5. compare_interpretation keeps “no completed Psi result” distinct from a matching exit. The console adapter maps the decline to
  6. Status branch

Inspection and package commands have different effects

Source inspection requests one named machine through Build with verify: true and an empty stage-validator request. Encoded-artifact inspection instead calls CanonicalTerminalArtifact::from_bytes. Decoding and validation do not run the guest or establish source package acceptance. These two routes should remain separate in the atlas even though one public command selects them. Inspection implementations

The source form can write the checked artifact to the caller's --output path. The encoded-artifact form only reads and summarizes; its parser refuses source, target, machine or output arguments, and its reader enforces a byte limit before decoding. Console adapter, argument separation

The package command adapter creates one retained BuildSession and passes it through the complete review operation. When the user explicitly requests --dangerously-accept-all, the adapter edits pending decisions and resumes for a bounded number of rounds, reporting that the decisions were accepted unread. Ordinary commands do not choose that flag for the user. Discard is a package-file operation; it does not run compilation. Package adapter

Project package audit returns a report and indicates whether review remains necessary; source audit opens acquisition storage and reports the selected local/Git source. Neither is a compiler-stage validator. The project audit coordinator can run Build and checks, but verifies unchanged project/lock identity before it finishes. Audit adapter, source audit, read-only coordinator

What the atlas should change

Judgment: show the console adapter, execution coordinator and source/artifact inspection as distinct boxes within the application boundary. Keep compiler sequencing in the shared Build/compiler route. This makes the intended small CLI router visible without claiming the entire application crate is already that small.

Judgment: show four separate kinds of checks: source semantic acceptance, package policy review, artifact admission and explicitly requested independent stage validation. They have different inputs, effects and failure meanings. Combining them under an “audit” arrow would conceal both ordinary behavior and the work only an explicit request enables.

The runtime's source is the authority for available host adapters. The application request and a selected provider do not prove every operation is executable; the runtime can refuse missing provisions and decline comparison.
