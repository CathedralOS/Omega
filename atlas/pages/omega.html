Omega turns a checked portable program into code for one target. It selects and admits outside providers, lowers the program to instructions, assigns registers, encodes and lays out bytes, builds objects and images, then hands a retained product to publication. Today several of these operations sit outside the numbered stages. The map below shows that current route before the proposed linear pipeline.

Evidence: source revision 3f9ce43f0c9d179048911d18faa91ba93f60176d; pinned source links below and the generated counts and dependency graph. This is a source review, not a fresh native execution test. Stage destination names and migration recommendations are judgment. The six owner rulings are unchanged.

The input boundary

The native facade accepts RetainedTerminalArtifact and NativeCompileRequest; Build has supplied completed scalar applications. prepare joins the retained proposal, installation assumptions, component inputs and private-entry memory recipes, then checks the required scalar values are present. Its errors preserve the image request alongside diagnostics so the caller retains the failed request's context.

This facade is source-free, but the entire path to it is not. The compiler's provider settlement still works with accepted source publication and policy preparation still takes checked source custody. The Psi/Omega firewall must be assessed at both boundaries, not inferred from the facade's signature alone.

An outside call has several kinds of identity: which program requested it, which declaration/body was chosen, and which target plan implements it. The selected execution checks target agreement; later installation binding checks program, target, entry and admitted placement. Moving these records must preserve their checked construction, not just their fields.

Current route: order within one native body

Solid arrows below show the main transformations. The handler branch matters: the root can pause after O02 while another native body is compiled. This is a per-body route with a driver coordinating dependent bodies, not one whole-program pass through every box.

The native pipeline driver orders O01–O09. The object coordinator prepares handlers, binds installations, emits the root, then lowers remaining referenced callback thunks and composes private objects. The fragment wrapper orders the transformations after O09. Image realization returns the retained artifact; products owns the call that writes it.

The total is 36,409 lines, including tests. These are ownership units, not five successive stages.

The closure loop starts from the actual entry's reached requirements and explicit Build selections. Chosen bodies can introduce more requirements. The loop reruns policy-input preparation when the reached set changes, realizes supply, and joins the resulting exact bodies. It terminates when the binding set is unchanged and refuses replacement of a prior choice. Available but unused code does not independently demand a provider.

Calling policies are executable programs: Build supplies their evaluator, and preparation retains the program artifacts and selection authority. The native proposal constructor also closes provider specializations, realizes task activations and checks selected provider ownership. These are producers despite the constructor living under representations/.

Admission is not finished at early provider selection. O00 realization admits native providers and the executable entry and captures provisions for Psi execution. Later, installed handlers are emitted before their installer needs a numeric stack guard. The coordinator caches those objects for this compilation, rejects cyclic executable resource dependencies, and derives requirements from the emitted objects. Binding joins them to the admitted cohort and current program before instruction selection.

SelectedExecution::settle is a convenience route, not the only constructor. The compiler uses public from_realization after it closes demand.

A concrete boundary: Console on Linux x86-64

The library's Build declaration selects LinuxX86Console for Console, then binds LinuxX86ConsoleIo::write to Syscall { number: 1 }. The provider methods call console helpers; the raw implementation reaches the I/O boundary. Terminal Psi keeps the program's required operations; provider settlement connects reached requirements to this target selection and calling plans. Native lowering uses the admitted realization to produce target operations.

This trace establishes who declares and chooses the binding. It does not assert that every Console method is one syscall, that all available Console code is reached, or that this review executed a Console sample.

Current bypass: EmissionFacts

The driver extracts EmissionFacts from O02's result. It keeps admitted lowering facts, a shared whole optimized abstract program, and projection/Terminal/final-unit identities. Emission later receives those beside the resolved machine program and installation authority. That is a genuine bypass around the representations between selection and emission.

Judgment: inventory every emission consumer and materialize the needed records in the current forms. Moving the same Arc into machine-code would change packaging without removing earlier-program access. Exact fields and retention cost remain unverified until the inventory and implementation are complete; this review claims no memory or performance improvement.

The declaration-selection ledger in Psi is different: its definition is misplaced in foundation but the value already travels through typed trees. Definition location, stored value and producer must be mapped separately.

Explicit verification is a separate route

When retain_native_stage_inputs is false, the driver drops the original target, allocation, encoding and layout inputs as they become unnecessary. When requested, it retains those originals for correspondence audits. Retention logic This does not remove the ordinary EmissionFacts bypass described above.

Target-operation verification requires the retained target input and calls the preparation verifier plus a borrowed-storage reconstruction routine. Fixed-frame verification compares current output with retained allocation, machine, encoding and baseline layout. These functions refuse when required custody is missing. They are not evidence that every default compile replays O02/O03.

Production still performs checks at admission, foreign/import boundaries and object/image handoffs. Distinguishing explicit replay from ordinary production does not mean ordinary production performs no validation.

Judgment: move explicit validators beside the representation they check, with independent checking APIs and an explicit retained-evidence input. Merely moving a file preserves its dependency on producer stages. Remove each stage-call allowance only after that call is gone; preserve independent checks rather than sharing the producer's logic by default.

Runtime use is another consumer

admit_runtime shares native provider/entry admission and returns provisions for Psi execution. The runtime-admission route also performs abstract optimization and captures borrowed-storage layouts, then stops before machine emission. It is not equivalent to compiling and running a native image.

The native runtimes read admitted carriers and image/provision records. Some carrier definitions currently live in a producing crate, for example the admitted intrinsic type used by terminal-runtime. A move of admission into numbered stages must split that interface so runtimes do not start importing or executing a stage merely to read a record.

Proposed route and migration dependencies

The complete migration plan contains the proposed contract figure and phase table. Judgment: close source and logical providers before native planning, then carry demanded bodies through physical planning, resource binding and one encoding boundary. Image construction must consume completed executable bodies. This differs from today's per-body route and late bridge production shown above.

The planning gates must establish the unresolved ordering. O03 currently needs bound installation facts, while those facts depend on compiled handlers. Numeric consumers must be classified, generated body effects made explicit and resource binding shown to preserve prior register/frame choices. Cyclic resource demand must still be refused. The current code does not prove that this proposed separation works.

The integrated execution plan orders one coordinated cutover, including semantic encoder ownership, carried ABI plans, O07/O08 encoding alternatives, emission facts, runtimes, independent checks and deletion of replaced paths. These are coupled obligations, not a set of separately adopted package moves. Questions retain the recommendations that still need a ruling.
