Build and packages

How package custody and Build evaluation become a compilation request and provider choices.

Build decides which sources, entries, providers and settings a product uses. Packages establish which source bytes and accepted decisions those choices may refer to. The coordinator alternates between those owners and the compiler; the native compiler receives the resulting program, target and completed inputs. This is more than a configuration reader, and it is not a second native pipeline. The complete project operation makes that division visible.

Evidence revision: 3f9ce43f0c9d179048911d18faa91ba93f60176d. This page follows production source at that revision. Existing tests below are evidence of intended assertions; their current execution results are unverified. Proposed ownership changes are marked judgment. The Psi page, Omega page, interpreter page and CLI page cover the adjoining owners.

The operation a caller actually requests

orchestration::build(BuildRequest) returns Result<Vec<TargetBuildOutcome>, BuildError>. The request names a root path, host/single/batch targets, a product, output directory, source-capture request, optimization selections, timings, offline/verification options and explicit stage validators. Each ordered target outcome contains either its own refusal or a compiler output, timing data, optional published executable path and validator rows. A failure before target work can start is the outer error. These are actual request and result fields.

Requested product Where this route stops
Check Produces a checked report; the coordinator uses a disposable workspace.
Terminal Retains the canonical Psi artifact for a caller. This project operation does not automatically write a .psi file.
Inspection { machine } Returns the requested machine's inspection artifact; requires one exact target and uses a disposable workspace.
Native { destination: Published } Completes native work, runs requested validators, then writes the product.
Native { destination: Retained } Keeps the native product in memory, allowing the CLI to interpret its exact Psi artifact before publication.
Native { destination: RuntimeAdmission } Completes the runtime admission needed by run --engine psi without emitting machine code.

The product and destination enums are declared together. Publication branches on those values; it does not infer the stop point from whichever files happen to exist.

This is the package-project route in build.rs and project_compilation.rs. A standalone source request uses the same begin/execute/complete protocol through compile_sources, check_source or produce_source. The standalone execution loop can answer retained product queries, but explicitly refuses provider-readiness or dependency-preparation pauses that require the package scheduler. It does not silently turn into a package resolver. See execute_build.

The coordinator's BuildSession is a deliberate join between independently owned compiler and package state. A source request can stop while Build asks for a dependency, then resume after the compiler prepares that dependency. The coordinator explains this dependency direction; putting acquisition inside a numbered compiler stage would erase it.

Build's execution profile and the requested product target are separate inputs. Source discovery uses its explicit execution profile or the supported host; the resulting Build choices can bind several product targets. The caller's source inventory also constrains acquisition itself: a scoped capture request selects the root before Product discovery or Build filesystem reads consume it. Source discovery entrance

Follow a concrete source request

The provider-readiness sample registers local package backing for Build use, suspends on Build::await_provider<ProgramImage, backing::TestImage>, then calls ProgramImage::retained_suffix_start(). It binds the product entry only when the result is 64. Its backing source defines a public TestImage returning 64, another public provider returning 128, and a private provider. These are ordinary Omega declarations, not names recognized by the CLI.

  1. build discovers the project and opens a retained Build session. Source discovery returns the closed source graph and the returned Build invocations. Project entrance
  2. The readiness scheduler retains the paused activation. For an InstallProvider work item it settles the dependency graph, prepares the dependency product for DependencyPurpose::Build, asks produce_package_build_provider for the exact declaration, installs that provider into the paused activation, and schedules the same Build to run again. Scheduler
  3. On normal return, the activation extracts settings and takes committed entry, declaration, native-binding and exclusion effects from its binding host. It returns source requests, demanded sources, filesystem effects and the artifact's custody identity with those choices. A parked or failed activation cannot call this successful completion path. Return
  4. Product compilation settles the returned Builds without rerunning them, admits the per-target requests through package policy, compiles them together, and reconciles completion with the package session. Target compilation
  5. The compiler settles product providers against actual reached requirements. It recomputes reach when newly selected bodies expose more requirements, reuses execution inputs when the reached set is unchanged, and refuses a change to an already selected exact body. Product settlement

The same mechanism handles Build::prepare_dependency: the scheduler prepares the dependency for the Build purpose and rejects an alias that names two different prepared packages. Preparation branch Build dependencies and Product dependencies are distinct purposes; a helper that executed during source discovery is not automatically a Product import. The input representation keeps separate dependency maps.

The integration test build_provider_readiness.rs checks the positive provider, changes only the provider name to expose the wrong result, and refuses private or absent implementations. It uses the maintained fixture under omega-rust/tests/fixtures/pass/build/, not the sample directory. Unverified: this atlas review inspected those assertions and source paths; it did not run the sample or tests.

Where the program-derived values live

A crate dependency is not a data-flow diagram. The concrete storage and joins are these. Here, custody means retained evidence and ownership that tie an input to its exact source or invocation:

Value Producer and storage Consumer and invariant
Exact source bytes, roots and requester-relative aliases Acquisition establishes the snapshot; PackageCompilationSourceInputs stores the source filesystem and per-package roots, captured trees, metadata, Product aliases and Build aliases behind an Arc. Source Target forks share that source input. Rejoining target attachments validates the input contract; a target attachment is not a new source identity.
Target-specific dependency output and accepted semantic bindings PackageCompilationTargetInputs stores the purpose, dependency PackageBuildHandoffs, accepted semantic bindings and component descriptions. Source The compiler consumes the package input for that purpose and target. A handoff carries both target and Build execution profile, not one interchangeable target string. Handoff
Executed Build selections TerminalBuildBindingHost keeps a mutex-protected state for one activation, authenticates the original structural receiver, and consumes exact prepare/commit tickets. The completed selections leave only after normal return. Host, return Product resolution and admission must resolve them to actual declarations. A committed choice alone grants no runtime authority.
Complete evaluated Build result PreparedBuildExecution::complete creates ComputedBuildConfig from the validated return, retaining its accepted Build source, executed request vectors, project declaration, observations and generated sources. Producer, fields The compiler uses the returned configuration and its custody during source completion, entry/provider selection and reporting. This is actual retention of a source judgment, not merely a type imported from another crate.
Source-consumption identity BuildSourceCustody::seal derives CheckedSourceCustody from frozen typed source, package input and generated-source custody; it records exact toolchain source digests and accepted semantic bindings. Producer require_owner rejects a different frozen source owner. The consumption record does not itself prove semantic acceptance.
Runtime permission acceptance Package policy selects the root Product occurrence for the exact package and target from accepted lock state. Selection TerminalPermissionAcceptance::validate compares exact canonical runtime permission, assumed-binding and component-assumption rows; mismatches require review. Comparison
Calling-policy execution input prepare_provider_execution_inputs joins retained Psi, reached boundaries, normalized Build supplies, target and declaration-selection authority. It stores the artifact and evaluator in a CallingProgram. Producer The evaluator executes a checked Psi policy for the exact signature and target. The returned register/stack plan still passes provider validation. Execution
Native work PendingNativeProduct stores retained Psi, selected independent components, accepted permissions and a native request. Fields Orchestration completes scalar values and passes them in NativeCompileRequest; the native compiler receives no Build interpreter callback on this route. Consumer

Source acquisition also retains filesystem authority, not just path strings. SourceResolver selects host Git outside package-controlled roots and holds the storage lanes; local snapshot resolution verifies its lane before and after capture/publication. If that final identity check fails, the operation returns that failure even if capture completed. The source identity and the user's acceptance of its policy remain separate facts. Ordinary compilation, review and explicit validation

Ordinary package compilation checks source/compiler identity against retained acceptance and selects the exact occurrence's inputs. An absent lock supplies no accepted semantic bindings or restricted checkpoints; it does not trigger an inline audit or write a new lock. This does not mean every unlocked program is refused: the existing unlocked standard-entry test expects an ordinary default entry to run without a lock. Permission-bearing cases still have their own admission requirements. Admission code, occurrence selection

Install, update and resume use execute_package_command. Package policy owns the transaction and proposed decisions; orchestration runs source discovery and dependency-first review passes, then hands all results back for publication or pending review. Read-only package audit uses inspect_packages. It can execute Build and compiler review work, but its final transaction verifies that project/lock files stayed unchanged. A failed source-discovery result is reported for each target; it does not prevent the remaining target reports from being assembled. Read-only does not mean no temporary or cache work.

Independent stage validators are a different operation again. At this revision the registry contains TargetOperationCorrespondence, FixedFrameCorrespondence and SelectedInstructionRewriteReplay. Default compilation runs none. An explicit request retains the inputs its validator needs and validates before native publication; a named validator for a product that never produces its stage is refused. --every-validator reports inapplicable validators as such. The source registry is newer than the orchestration README's one-validator description.

The publisher consumes only publishable retained output, refuses an already published report, and records the resulting publication in the report. Generated Build output is published through the same final operation. Product publication

Q-B: narrow input facts and retained source are different issues

Observed. Provider preparation currently receives CheckedSourceCustody and a ProductTerminalPublication. It verifies the accepted source owner, publishes through a retained result, maps native Build supplies through the accepted source's elaboration, and borrows dependency-closure authority to admit declaration selections. Provider input construction and retained publication show this real source-side join. The word “Terminal” in a module name does not make it source-free.

Observed. Later native completion already has a narrower boundary. It takes PendingNativeProduct, completes component/root scalar demands, and constructs NativeCompileRequest from the resulting Psi, permissions, components, target-dependent data and values. It calls either compile or admit_runtime. It does not give the native compiler PackageCompilationInputs or a live Build activation. Complete operation

Judgment: Q-B should inventory the required fields at each crossing, then carry their identities and acceptance evidence in the declared next input. Moving all Build state into Terminal Psi would preserve the broad coupling under another name. Equally, deleting source custody before the join would discard the evidence used to reject a selection from the wrong package or source owner. The migration must name when each association becomes settled and who is responsible for carrying it forward. The owner’s linear-pipeline ruling supplies the goal; it does not decide those field-level contracts.

Q-C: compilation ownership must be separated from execution service

Observed. source-compiler already depends on build-time-evaluation. The evaluator's manifest declares Psi 02, 03 and 04 dependencies, but that is not proof of three production stage invocations. At this revision:

  • Production source_jobs.rs prepares typed source through Psi 04, then calls AcceptedTerminalSource::judge for the requested invocation closure. It verifies the returned entry names the actual caller. Source
  • Production retained-provider reconstruction calls Psi 04's prepare_retained_product_application. Source
  • BuildTimeSources holds Psi 03's SeededTypingBase type. Field
  • The direct Psi 02 resolution and Psi 03 lowering calls inspected in source_jobs.rs are under #[cfg(test)]; the separate real-library test loader is also declared under that attribute. Test boundary, test modules

Thus the existing question “calls Psi stages 02–04 directly” overstates the production evidence. The real concern is that source-job compilation and preparation coexist with evaluation services. Simply making the evaluator call source-compiler adds the reverse of an existing dependency and creates a cycle. Source-compiler manifest, evaluator manifest

Judgment: give one driver ownership of source preparation and checking, with a lower-level execution service that accepts the checked invocation and returns a value, effects and accounting. The exact interfaces and placement remain a design decision. This direction must also serve constant evaluation, fixed layouts, provider applications and calling policies; naming it “the Build script runner” would omit real consumers. The existing calling-policy executor already demonstrates a checked-artifact input and a fresh interpreter instance without re-entering source compilation. Calling-policy source

This diagram is a judgment about ownership, not an implemented route or a new owner ruling. The loop is an explicit request/result exchange for source computation, not permission for a later native stage to reread earlier source.

Existing checks that exercise these boundaries

Existing check What its assertions distinguish
Build provider readiness The named dependency provider is installed before the resumed call; wrong, private and missing choices are refused.
Build native bindings One native supply per requirement/target; a different place on another target is allowed; missing requirements and demanded dependency supplies are checked.
Shared compilation session A changed dependency contract is rechecked; failure can recover; an equal body hash with different dependency context is refused.
Package command transaction Update/resume retains the application session and leaves the accepted lock unchanged while review is pending.
Package inspection transaction Inspection checks its receipt roster and final file identity.
Source snapshot custody Snapshot writes and publication remain bound to the open stage; replacement and nested symlink substitution are refused.
Explicit stage validator requests Requested validators run, default compilation runs none, unknown/inapplicable names refuse, and the full roster distinguishes inapplicable work.
