Psi gives source its target-neutral meaning and publishes the portable program Omega consumes. In the Rust reference compiler, the important boundary is acceptance: typed trees describe a program; only the lowered-form checking route can accept it. Native provider choice, register placement and image emission belong to Omega, while execution belongs to the interpreter. Source: domain contract

What crosses each stage

The diagram names transformations of one prepared source request. It is not a claim that the current coordinator performs one uninterrupted pass: source activation and compile-time evaluation interrupt that larger workflow, as described below. Nor does a box imply that every language construct works.

Stage Actual entrance and values Work and limit of its authority
00, source files to tokens lex_sources(LoadedSources) -> Result<LexedSources, Vec<Diagnostic>> Lexes retained source text and keeps its source identity and metadata. Lexical failures carry the original location. Code
01, tokens to syntax trees parse_sources(LexedSources, &mut SyntaxTrees) -> Result<ParsedSources, Vec<Diagnostic>> Writes syntax nodes and returns the source/root associations. Parsing identifies authored structure; it does not prove contracts. Code
02, syntax to resolved trees resolve(ResolutionRequest) -> Result<SymbolResolvedTrees, Vec<Diagnostic>> Resolves names against source scope, top-level bindings and an optional retained base. The request explicitly carries source custody; source-free test forests have different visibility inputs. Deferred and extension entrances support staged source activation. Code
03, resolved to typed trees lower_symbol_resolved_trees(&SymbolResolvedTrees) -> Result<TypedTrees, Diagnostic> Validates resolved semantics, constructs typed declarations and expressions, and carries semantic records forward. The production facade also uses SeededTypingBase to extend the exact retained predecessor. Lowering; facade
04, typed preparation prepare_typed_trees(TypedTrees, &PreparationRequest) -> Result<(FrozenTypedTrees, TypedPreparation), Vec<Diagnostic>> Runs specialization, domain applications and record patterns in that order, then freezes the result. TypedPreparation is request metadata, with no judgment receipt. Deferred layouts, opaque representation selections and wire demands without a serving pass refuse explicitly. Pass list; entrance and refusals
05, structural lowering prepare_compilation(&TypedTrees, Compilation, TerminalPublication) -> PreparedSource Emits TerminalCompilation plus SourceCorrespondence. It gathers the entry closure, generic forms, selected conformance witnesses and their relationships while typed source is available. Formation failures remain data for stage 06 to judge. Code
06, lowered-form checking judge_compilation(TerminalCompilation) -> Vec<Result<RouteVerdict, CompilationRefusal>> Checks the prepared forms and witnesses without consulting typed source or invoking an earlier stage. Accepted closures contain elaboration, discharge and obligation evidence seals. Other outcomes publish no accepted artifact. Entrance; verdict types

The public parsing facade also fuses 00 and 01 per source: it calls Lexer, retains source backing, calls parse, and recycles token scratch. It preserves lexical-error priority across the batch. Thus a diagram of the representations does not imply that every program materializes an entire separate LexedSources batch. Fused source ingress and tests

Who sequences the work today

source-compiler owns the source entrances: SourceInput, SourceCompilationRequest, SourceContinuation, CompletedSource and SourcePreparationRequest. A continuation retains a seeded typed base, pending resolved bodies and pending evaluations. Completing selected source bodies alternates the deferred resolution and typing operations until none of those bodies remains. That is existing orchestration to account for in a linearization plan, not an already linear whole-program implementation. Request and retained state; completion loop

Preparation currently evaluates fixed-layout applications, domain access plans, const arguments and constant initializers before invoking Psi 04. It checks materialization receipts, then returns FrozenSource with frozen trees, accounting and demanded constants. A failed preparation keeps usage accounting with its diagnostics. Preparation sequence

terminal-production owns the next sequence. AcceptedTerminalSource::judge retains the exact Arc<FrozenTypedTrees>, asks 05 to prepare the compilation, then asks 06 for verdicts. It refuses missing correspondence between accepted forms and their source. produce publishes either portable canonical code or invocation code, keeps evidence, and attaches source selections, provenance and Build companions to that same owner. The checker consumes the program half of 05's output; the publication owner retains the source half. This is the current data route, including the correspondence retained outside the checker. Judgment; publication

The two publication forms matter. A compile-time invocation can publish code for one checked dependency closure; that does not claim a whole package was checked or that portable output was requested. The source-job producer fixes the actual requesting caller before preparation and checks that acceptance returned that same caller. Invocation preparation

Trace a selected call through the representations

For a call with an authored declaration-selection occurrence, the selection ledger already travels through typed trees. The shared location of its type definition is a different ownership question from the location of its values.

  1. SymbolResolvedTrees owns AuthoredDeclarationSelections and recording methods associate source occurrences with selected declarations. Storage and recording
  2. Psi 03 calls retain_authored_declaration_selections with that ledger. TypedTreeTables contains the field, whose type is currently defined in language_semantics::declaration_selection. Transfer; typed storage
  3. Psi 05 reads self.typed.authored_declaration_selections().get(occurrence). It refuses a missing ledger row or a selection resolved to another declaration; it also explicitly refuses the intrinsic and late-bound cases in this call-reading path. Consumer and errors

Judgment. Moving this vocabulary out of foundation must preserve the occurrence identities, ledger transfer and consumer checks. Drawing an arrow from foundation that skips typed trees would misdescribe the present code and suggest a data-flow repair that has already happened.

Checking, proof admission and publication are different jobs

Stage 06's prover searches for certificates from the hypotheses and semantic axioms at an obligation. Its output is checked; search success alone is not acceptance. proof-admission::accept_certificate validates the goal and premises, walks the supplied proof, checks that its conclusion matches the goal and records mathematical-core admission. Proof admission runs no search of its own. Prover; certificate admission; admission contract

There is a useful concrete test of that boundary. The stage-06 test helper constructs a machine adding two u32 formals. With each operand constrained to at most 100, the test expects one safety obligation and checks its kernel evidence. The adjacent tests remove those premises, or add u32::MAX and 1, and expect the addition to remain unproved. This tests proof requirements; it is not a runtime overflow experiment. Unverified: these tests were inspected, not executed for this atlas update. All three test definitions

The result preserves distinct failure meanings:

  • Rejected records unproved supported obligations, invalid formations, violations, unestablished storage, conflicting loans or exceeded service reach.
  • Incomplete records a goal form for which the prover has no rule.
  • FallBack is an old variant name for unsupported constructs. The source explicitly says no fallback checker runs.
  • CompilationRefusal reports defects such as failed identity relationships.

None is an accepted closure. Failure to find proof is not a proof that the proposition is false. Verdict contract

Current limit. The bounded certificate checker and the mathematical-core translation have different coverage. accept_certificate may return an acceptance whose core decision is Refused(family) when that translation does not cover a rule family; a covered but invalid translation errors. The map must not describe every accepted bounded certificate as already translated and judged by the mathematical core. Exact distinction

Canonical sealing is another boundary. ClosedTerminalModule keeps a module, closed types, bytes and identity together; its definition expressly says this does not establish checker acceptance or producer trust. terminal-wire owns canonical encoding and structural closure, while terminal-codec owns the sealed module and envelope. The digest identifies bytes; it does not authorize execution. Closed module; codec contract

Compile-time evaluation and the plan's dependency problem

Build-time evaluation is compilation work that uses the interpreter. The interpreter never calls the source workflow. A source job prepares and checks an invocation, publishes its code, admits its exact target and supplies, executes it, and converts its returned value into BuildTimeValue for the compiler. Missing imports, providers, external completions or unavailable target observations refuse at admission. Preparation; admission; execution

The following is a current dependency/call diagram, not stage order:

source-compiler already depends on build-time-evaluation, so making the whole evaluator depend on that facade would create a crate cycle. In production, the evaluator directly invokes Psi 04 for an invocation and prepares retained Product applications through another Psi 04 entrance. It also stores the Psi 03 SeededTypingBase type. Direct Psi 02 resolution and Psi 03 lowering calls found in this audit are in tests, even though the crates appear in ordinary manifest dependencies. A manifest edge, a retained type and a call into a stage are three different kinds of evidence. Facade manifest; evaluator manifest; production invocation; Product preparation; retained type; test boundary

Judgment for Q-C. Give one sequencing owner the source continuation and the task of preparing each requested evaluation program. Pass admitted code, arguments, supplies and accounting to an executor that cannot call a source stage. Return a result tied to that invocation before continuing compilation. Extract the source-stage calls and relocate SeededTypingBase custody before reversing any dependency. Preserve the existing exact-caller, source-consent, target and accounting checks; a common facade name alone would not resolve them. This is a migration proposal, not another owner ruling.

Coverage and review checks

Source evidence supports the route above, but not a claim of full language or product support. Source preparation explicitly refuses source-selection authority it cannot admit and opaque representation requests; Psi 04 refuses unserved layout, representation and wire requests. Other constructs can reach 05 or 06 and then be refused. An accepted small example cannot remove those boundaries. Preparation limits; Psi 04 limits

Useful existing checks, all runtime-unverified in this review, are the fused-ingress source-order/error-priority tests, the resolved-tree ledger ownership test, Psi 05's left-to-right operand/call-argument test, and the three arithmetic obligation tests above. These are test definitions, not fresh passing results. Ingress; ledger ownership; operand order; arithmetic
