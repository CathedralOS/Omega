# Bound support members

This directory authors, once and readably, the exact Gamma text the Delta
compiler copies into generated programs:

| Member | Role |
| --- | --- |
| `bytes.gamma` | Byte-rope runtime (`$dbe`, `$dbs`, `$dbl`, `$dbc`, `$dbg`, `$dbgi`): empty, singleton, length, checked concatenation, and bounds-checked indexing over `(pair length (pair tag payload))` ropes. |
| `conformance.gamma` | `ConformanceBytesV1` runtime (`$pbg`, `$pbgi`, `$pbi`, `$pbw`): the same rope contract plus tag-3 sealed-input views and the output writer. |
| `adapter.gamma` | The generated `main` adapter for `ConformanceBytesV1`: input/output extent guards and the `__d_main` call. |

`support.gamma.sources` is the ordered member manifest. Its packed bytes are
the bound support section: every sealed compiler input ends with exactly
those bytes, and `implementation/emission/support.gamma` binds each member's
extent, frame offset, and byte sum. The canonical `DCREQ` entry admits only
inputs whose support section is present and complete; compilation then
verifies each member's contents and emits members by sealed-input copy during
publication, after counting every support and generated byte.

The `$db*`/`$pb*` names are the private lowering/runtime boundary; generated
programs reference them and nothing else from this directory.

## Source-owned copying versus byte-only materialization

The board item asked to compare the two custody shapes before selecting:

- **Source-owned copying** keeps runtime text inside compiler source as
  emitter data - the retired `implementation/emission/bytes.gamma`, which
  wrote ~1.3 KB of runtime through hundreds of grouped character-literal
  calls. Its costs: a ~13.5 KB emitter member whose text duplicates the
  runtime it describes, no independently readable runtime source, and a
  receipt whose support bytes exist only as emitter outputs. Its sole saving
  is that the compiler needs no sealed-input extension.
- **Byte-only materialization** (selected) authors each runtime member once
  as ordinary Gamma, packs it through the generic `source_closure.py`
  manifest mechanism - ordered identities, exact lengths, per-member digests,
  inventory equality, atomic destination - and carries the packed section in
  the sealed input. The compiler validates member extents and byte sums
  against an embedded table before compiling and copies bytes verbatim during
  publication.

Cost accounting for the selected shape:

- *Evaluator*: unchanged. The support section is sealed input read with the
  ordinary `read`/`input` primitives; no evaluator facility or profile entry
  was added.
- *Compiler*: `emission/support.gamma` (3.7 KB: bound table, member
  validation, counted copy loop) replaces `emission/bytes.gamma`
  (13.5 KB of writers) - a ~9.8 KB member swap - while the entry and
  request-admission members grew ~ +1.2 KB for the support trailer, so the
  packed closure is ~8.6 KB smaller overall. Emission adds one ~3 KB
  sealed-input pass (member sums) and a 3 KB verbatim copy.
- *Tooling*: one extra bound manifest plus `materialize_delta_support`; the
  composed record gains the packed support identity under `GammaComposedV2`.
- *Proof*: DCOUT gains coordinate space 5 with two codes; exact-limit and
  adjacent-refusal counting is structurally unchanged (member extents flow
  through the same `emit_advance` accounting). Conformance coverage -
  empty/NUL/high bytes, concat, indexing, exact traps, logical-length
  overflow, adapter input/output limits - is exercised by the same gates.

Rejected alternatives: no host semantic parser (the materializer and the
compiler treat members as bytes, never as parsed Gamma), no output patcher
(receipts are written once, in order, never edited), no filename discovery or
ambient file access (only the pinned manifest selects members), and no
unbound dependency (the composed record pins the packed section and the
compiler's table pins each member within it).
