# Settle and lock one V2 layer

Work through the V2 junction in the assigned worktree. Start with the layer’s lock status in [PLAN.md](../../../PLAN.md), the relevant [shared Omega spec](../../../../wiki/spec/), and the layer’s own contract. Treat a design question as a discussion. Begin editing when the user asks for implementation.

1. **Define the open layer’s job.** For a concrete program, identify what the layer receives, what decision must be made, and what the next layer needs. Ask “What information is required to make this decision?” and “Which layer owns that information?” Name the field or other part of the output that carries the answer. Read the producer and its consumers to check that account. Name the crates the downstream consumer should depend on and who supplies any fresh input the consumer needs. Before editing, choose a program that makes a consumer decide something using the carried fact. Predict the outcome and how it changes when one deciding input changes.
2. **Make the architectural changes before testing.** Change the representation, APIs, and ownership together where the design requires it. Remove the consumer code that reconstructs a decision the producer now supplies. During this phase, read existing tests for context and defer test runs. Move to testing when you can trace the decision from its inputs through one owner to its consumers, with the responsibilities of adjacent locked layers intact.
3. **Test the handoff.** Once ownership is settled, run that program first through the ordinary entry point that reaches the consumer. For example, returning a computed-width array as a fixed-width array makes typing compare the widths. Check that equal widths pass and unequal widths fail at the return. If computing the width itself fails, check that the error points to the computation. Then run the three independent reviews below. Reproduce their cases through the V2 stage entry points. Run the focused regressions and the open layer’s relevant suite. If a failure exposes an ownership mistake, return to design. If it exposes an implementation bug, fix it and rerun the affected checks.
4. **Lock, commit, then advance.** For each sign-off claim, name the deciding input and point to the assertion that checks the claimed result. A presence check supports a presence claim. An identity claim needs an assertion comparing the selected identity with the expected one. For the consumer dependency check, cite the consumer manifest and the operation exercised. State what remains unverified, including downstream behavior exercised only through a test consumer. Before calling the layer locked, check that the owner’s sign-off covers this handoff. Record the signed-off responsibility in `PLAN.md`, align the layer contract, and state which changes would require reopening it. Commit the agreed implementation, contract, and tests, then advance.

## Measuring whether samples improve

For a sample-quality pass, choose one spec rule and name the public decision the sample must distinguish. Before editing assertions, pin the baseline revision and write down a small set of plausible wrong outputs, a valid control, and the expected outcomes. When using an independent reviewer, have them reserve one additional challenge from that revision. Keep it private until the revised assertions are frozen. Run it once before adapting the tests to anything it reveals.

Give the old and revised assertions the same valid output and the same independently altered copies, including any checks their shared helpers perform. Verify that each alteration actually changed the product. Record which changes each version rejects for the expected reason. Count each distinct wrong decision once across spellings and call forms. Report the reserved result separately, including misses and zero gain. Record an unrepresentable alteration as unscored and label any later challenge as a separate experiment. Credit a compiler defect only when an ordinary source input produces the wrong output.

Strengthen an existing sample when its program already expresses the distinction. Retire a weaker sample when its replacement catches its faults at the same boundary and preserves useful failure localization. To check whether a gain repeats, select another rule before examining its failures and keep its denominator separate.

## How to review the handoff

Before sending the review prompts, have the coordinator set aside a plausible violation and a nearby lawful case for this handoff. Derive both from the contract and what the producer can emit. Write down the expected public results and keep the cases out of the prompts. Once the reviewers submit, run both through the consumer and record which failure, if any, the reviewers found independently. Keep these checks with the handoff they exercise.

Give three GPT-6.2 Sol reviewers the same contract and the distinct questions from the [parallel handoff review](../../../PLAN.md#handoff-review).

| Reviewer | Question to answer |
| --- | --- |
| Producer | Where do the deciding facts first exist? Which other candidate could the producer plausibly choose, and which assertion distinguishes them at the public output? |
| Consumer | Could the program still pass this stage if the producer omitted a fact or attached it to the wrong occurrence? Exercise the public result with the consumer’s intended dependencies and show how it retrieves that exact fact. Change one deciding input and check the affected occurrence and its neighbor when both are present. |
| Equivalent inputs | Which selections should agree, or which refusal and source site should both forms produce? Check those exact results. For example, a callback forwarded through a checked library should retain the same crash guard and invocation operands as one typed jointly with the client. |

Have the consumer reviewer list the facts the consumer relies on for the decision under review. For each fact, record the producer field or context that supplies it, a valid control, one change that would make the evidence wrong, and the expected public result. Include relationships between fields and who supplied the evidence. For example, a byte column can be positive and still be impossible at its byte offset. A diagnostic record can be valid yet belong to a different test or a previous run of the same target. To test attribution, keep the record intact and change only its surrounding context.

Run every proposed mutation and its control through the same consumer. Restore the valid input between mutations. Record the expected and observed result for each pair, including which fact lost credit and whether unaffected facts kept theirs. If the input cannot reveal the answer, name the independent evidence needed. For example, detecting a missing diagnostic record requires some independent indication that the producer returned a refusal. Leave that claim unverified until the evidence exists.

Keep an independent open review alongside the inventory. Give the equivalent-input reviewer the contract and producer output, and let them choose their own cases before sharing the inventory or other findings. At sign-off, combine the reproduced failures from both reviews and group them by the decision that needs repair. Use the ranked findings to order repairs after replaying the full inventory. Distinguish newly exposed defects, correctly rejected mutations, and cases the available evidence could not settle. A count of probes alone cannot establish coverage.

After a repair, rerun the original failing input and the nearest lawful edge case through the repaired consumer. Assert the required outcome for each. For example, an L5 diagnostic reader should reject a dependency record that claims a local source position. A local record for a zero-length span has a valid line and column and an empty excerpt. Require the reader to preserve that location and credit the valid record. A rule that requires every local excerpt to contain text would lose it.

For a broad sweep, split the open layer into distinct decisions. When the owner requests Pi, use the requested model and effort (the L5 sweep used Opus 5.5 on high). Give each reviewer one decision, the same layer contract, and the relevant canonical spec excerpt. Supply the excerpt from the authorized spec when reviewers are confined to the V2 junction. Ask each reviewer for the files inspected, the smallest witness and its nearest passing control, and the predicted output field or diagnostic. A reviewer who finds no defect should say which paths they examined.

Reproduce a lead through the ordinary stage commands and inspect the disputed handoff before assigning a repair. If the failure differs from the prediction, remove the suspected feature and run the control. A plain nested helper exposed a refusal before the callback inside it. If the published product already preserves the required distinction, close the lead with that evidence. For example, Psi retains an affine sum’s declared multiplicity and the linear field’s carrier on its occupied case. The empty case has no such field. The checker can use the active case to determine what the value owes. [Sum handoff test](../../../layers/05_prepared-trees-to-terminal-psi/tests/declarations.rs)

Follow the same value through the forms the spec says should agree. Compare a direct call with the same machine passed as a callback under two enclosing applications. For an owned byte-array result, compare a quoted literal with a named constant containing the same bytes. Inspect element order, type and returned array in Psi. L3 already published the decoded bytes, so the direct-literal repair belonged in L5. [Byte-array handoff tests](../../../layers/05_prepared-trees-to-terminal-psi/tests/array_values.rs)

When a construct affects both evaluation and lowering, write a witness that forces each consumer to act. A runtime machine containing `_ = leaf(x);` can pass preparation without L4 executing its body. Calling that machine from a constant initializer exercises L4. Make the discarded call’s precondition fail and check the refusal at that call. In L5, inspect the order of operations and the requirement attached to the call whose result is discarded. [L4 evaluation](../../../layers/04_typed-trees-to-prepared-trees/tests/boolean_calls.rs) · [L5 lowering](../../../layers/05_prepared-trees-to-terminal-psi/tests/calls.rs)

Build and run the handoff case in the downstream crate with its intended dependencies. If that crate does not exist yet, use a small test consumer with its own manifest. Keep upstream setup in the producer harness. Exercise the operation a real consumer needs, including any fresh input, and inspect its public signature for earlier-layer types exposed through re-exports. For example, dropping L4’s prepared trees proves that L5 owns the saved target observation. The original replay test supplied a fresh L4 `TargetSemantics`, which hid a public dependency on preparation. The repaired test builds the receiver from portable Psi subjects in a client that depends only on the product. Identify who owns the receiving target facts and check whether replay can obtain them through the intended contract.

For each decision that matters to the lock, ask “Could this test pass if the compiler made the wrong decision?” When two choices could satisfy a weak assertion, inject the plausible wrong choice into a temporary copy of the producer. For example, substitute a neighboring generic binder or attach a precondition to an identically spelled call. Observe which assertion fails and why. If the test stays green, strengthen it at the public handoff and repeat. Verify it passes against the actual producer before reporting the result. When testing several reasons to refuse one receipt, restore the accepted receipt between cases. For evidence tied to a generic constructor, hold the occurrence, fields and typing pass fixed and change only the closed application. [Construction evidence tests](../../../layers/04_typed-trees-to-prepared-trees/src/evaluation/owned_values/tests.rs)

Try swapping two valid identities while preserving their count and distinctness. Check which declaration belongs to each defining file or call. When the identities are opaque, obtain the expected one from a small control program that explicitly names the intended declaration and has no competitor. If the product publishes the same decision in two places, change one while leaving the other correct. For a nested operator, inspect both the machine and operator visibility in Psi. [Imported declarations](../../../layers/02_syntax-trees-to-symbol-resolved-trees/tests/signature_origins.rs) · [Operator visibility](../../../layers/05_prepared-trees-to-terminal-psi/tests/operators.rs)

When a handoff carries generic arguments, run the same source occurrence at two closed applications in one package. Swap the enclosing and local arguments and assert distinguishable answers. Exercise the value through a helper as well as directly. In L4 a direct layout query succeeded while a generic helper lost its caller’s type argument. [Nested layout regression](../../../layers/04_typed-trees-to-prepared-trees/tests/target_layout.rs)

Make the field or result named in the claim depend on the argument being varied. Two swapped operands can still produce the same set of result domains. Use an overload that selects just one operand and assert the defining file. A generic record can still have a fixed-type omitted field. Omit a field of type `[u8; N]` and check the prepared array at two concrete lengths. First run the new case with the unmodified compiler. A refusal at an earlier contract leaves the intended decision untested. [Result-domain selection](../../../layers/03_symbol-resolved-trees-to-typed-trees/tests/calls/result_domain_selection.rs) · [Omitted field](../../../layers/04_typed-trees-to-prepared-trees/tests/owned_records.rs)

For a refusal, name the earliest layer whose contract requires it and assert the diagnostic at that layer’s public entry point. A later layer can catch the same invalid program and hide the missed decision. Pair the refusal with a valid program where a plausible shortcut would confuse two identities. Follow the owner’s published field into the production consumer and assert which identity it selects. In the L2 overload repair, the generic binder `T` and the nominal member in `Io::T` share a spelling. Renaming only the binder must still produce a duplicate at L2. Changing the nominal member must give L3 two distinct candidates and the expected selection at each call. [Resolver assertion](../../../layers/02_syntax-trees-to-symbol-resolved-trees/tests/stage.rs) · [Typing assertion](../../../layers/03_symbol-resolved-trees-to-typed-trees/tests/calls/generic_applications.rs)

When a rule requires preserving which input a value depends on, choose two different inputs that yield the same value. Follow each reference from its consumer to the exact input in the public output. Then swap which input each consumer uses. For example, size and alignment can both yield 8. The array shapes, set of observations and whole-package replay can all agree even if both constants point to alignment. The assertion that distinguishes the programs reads the projection attached to each constant.

## When a later layer reaches back

If a declaration owns a fact, test a legal declaration that never uses it. For example, `domain i32::Empty requires false;` still has a signed carrier even though its predicate never reads `self`. Pair it with the same predicate on `u32` and read each carrier from its own lowered declaration. This exposes a handoff that only works when a use happens to reveal the missing fact.

Start at the open layer. Name the exact fact its consumer needs for one program and inspect the input the consumer actually receives. If the fact is present for the right occurrence and usable through the intended dependencies, fix the consumer and stop tracing backward. For example, L5 could read the typed Boolean in `data Never requires false {}` through L4. The repair was to retain it on L5’s data schema.

If the fact is missing or wrong, walk backward one handoff at a time. For each intervening layer, compare what enters with what its public output lets the next consumer read. Record the first point where the fact should exist and the point where it becomes unavailable or changes identity. If a prerequisite never enters the ordinary pipeline, name its supplier. Mark any boundary you could not exercise as unverified.

Run the complete program through the ordinary entry point. If the producer demands a value before it releases the facts its consumer needs to compute that value, show where the program stops. Compare it with a literal-value control. If a test supplies results up front, first inspect the pending requests from a run without those results. Assert the exact occurrence and argument tuples the evaluator must receive. In a fault-injection test, L3 accepted both supplied widths after its pending output lost one request. Then run the consumer on the original program. [Pending width requests](../../../layers/03_symbol-resolved-trees-to-typed-trees/tests/calls/generic_applications.rs)

| What the case shows | Who acts |
| --- | --- |
| The handoff supplies the information through the intended dependencies. | Fix the consumer to use it. |
| Using the handoff requires a type or service from an earlier implementation crate. | Name the public field or method that requires it. Decide who owns the information, then correct the public contract or document why that dependency belongs to the consumer. |
| The locked contract promises the information, but the producer loses or misstates it. | Fix the producer under its existing lock and test the handoff. |
| The requested information falls outside the locked contract. | Decide whether the open layer can derive it from facts it owns. If the evidence points to the earlier layer, bring the case forward for an explicit decision to reopen. |

One valid program can demonstrate information loss. Repeated workarounds can reveal a pattern, but repetition alone cannot establish ownership. For each proposed reopening, show what breaks, where the deciding facts first exist, which contract would change, and what its consumer would do with the revised output. When one producer gains a fact, check whether the next layer’s existing output already exposes it before proposing a second contract change. For example, if L3 publishes an assembly instruction’s implicit writes, the question for L4 is whether L5 can read those writes from the prepared package for that instruction. After an explicit reopening decision, apply the same design and test sequence to the revised boundary before locking it again.
