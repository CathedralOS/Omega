# Repair a layer decision

Work through the V2 junction in the assigned worktree. Start with the layer’s lock status in [PLAN.md](../../../PLAN.md), the relevant [shared Omega spec](../../../../wiki/spec/), and the layer’s own contract. Treat a design question as a discussion. Begin editing when the user asks for implementation.

1. **Define the open layer’s job.** For a concrete program, identify what the layer receives, what decision must be made, and what the next layer needs. Ask “What information is required to make this decision?” and “Which layer owns that information?” Name the field or other part of the output that carries the answer. Read the producer and its consumers to check that account. Name the crates the downstream consumer should depend on and who supplies any fresh input the consumer needs. Before editing, choose a program that makes a consumer decide something using the carried fact. Predict the outcome and how it changes when one deciding input changes.
2. **Make the architectural changes before testing.** Change the representation, APIs, and ownership together where the design requires it. Remove the consumer code that reconstructs a decision the producer now supplies. During this phase, read existing tests for context and defer test runs. Move to testing when you can trace the decision from its inputs through one owner to its consumers, with the responsibilities of adjacent locked layers intact.
3. **Test the handoff.** Once ownership is settled, run that program first through the ordinary entry point that reaches the consumer. For example, returning a computed-width array as a fixed-width array makes typing compare the widths. Check that equal widths pass and unequal widths fail at the return. If computing the width itself fails, check that the error points to the computation. Before sign-off, run the three independent reviews specified in the plan. Reproduce their cases through the V2 stage entry points. Run the focused regressions and the open layer’s relevant suite. If a failure exposes an ownership mistake, return to design. If it exposes an implementation bug, fix it and rerun the affected checks.

## Handoff review

Give three GPT-6.2 Sol reviewers the same contract and the distinct questions from the [parallel handoff review](../../../PLAN.md#handoff-review).

| Reviewer | Question to answer |
| --- | --- |
| Producer | Where do the deciding facts first exist? Which other candidate could the producer plausibly choose, and which assertion distinguishes them at the public output? |
| Consumer | Could the program still pass this stage if the producer omitted a fact or attached it to the wrong occurrence? Exercise the public result with the consumer’s intended dependencies and show how it retrieves that exact fact. Change one deciding input and check the affected occurrence and its neighbor when both are present. |
| Equivalent inputs | Which selections should agree, or which refusal and source site should both forms produce? Check those exact results. For example, a callback forwarded through a checked library should retain the same crash guard and invocation operands as one typed jointly with the client. |

Reproduce a lead through the ordinary stage commands and inspect the disputed handoff before assigning a repair. If the failure differs from the prediction, remove the suspected feature and run the control. A plain nested helper exposed a refusal before the callback inside it. If the published product already preserves the required distinction, close the lead with that evidence. For example, Psi retains an affine sum’s declared multiplicity and the linear field’s carrier on its occupied case. The empty case has no such field. The checker can use the active case to determine what the value owes. [Sum handoff test](../../../layers/05_prepared-trees-to-terminal-psi/tests/declarations.rs)

Follow the same value through the forms the spec says should agree. Compare a direct call with the same machine passed as a callback under two enclosing applications. For an owned byte-array result, compare a quoted literal with a named constant containing the same bytes. Inspect element order, type and returned array in Psi. L3 already published the decoded bytes, so the direct-literal repair belonged in L5. [Byte-array handoff tests](../../../layers/05_prepared-trees-to-terminal-psi/tests/array_values.rs)

When a construct affects both evaluation and lowering, write a witness that forces each consumer to act. A runtime machine containing `_ = leaf(x);` can pass preparation without L4 executing its body. Calling that machine from a constant initializer exercises L4. Make the discarded call’s precondition fail and check the refusal at that call. In L5, inspect the order of operations and the requirement attached to the call whose result is discarded. [L4 evaluation](../../../layers/04_typed-trees-to-prepared-trees/tests/boolean_calls.rs) · [L5 lowering](../../../layers/05_prepared-trees-to-terminal-psi/tests/calls.rs)

Build and run the handoff case in the downstream crate with its intended dependencies. If that crate does not exist yet, use a small test consumer with its own manifest. Keep upstream setup in the producer harness. Exercise the operation a real consumer needs, including any fresh input, and inspect its public signature for earlier-layer types exposed through re-exports. For example, dropping L4’s prepared trees proves that L5 owns the saved target observation. The original replay test supplied a fresh L4 `TargetSemantics`, which hid a public dependency on preparation. The repaired test builds the receiver from portable Psi subjects in a client that depends only on the product. Identify who owns the receiving target facts and check whether replay can obtain them through the intended contract.

For a refusal, name the earliest layer whose contract requires it and assert the diagnostic at that layer’s public entry point. A later layer can catch the same invalid program and hide the missed decision. Pair the refusal with a valid program where a plausible shortcut would confuse two identities. Follow the owner’s published field into the production consumer and assert which identity it selects. In the L2 overload repair, the generic binder `T` and the nominal member in `Io::T` share a spelling. Renaming only the binder must still produce a duplicate at L2. Changing the nominal member must give L3 two distinct candidates and the expected selection at each call. [Resolver assertion](../../../layers/02_syntax-trees-to-symbol-resolved-trees/tests/stage.rs) · [Typing assertion](../../../layers/03_symbol-resolved-trees-to-typed-trees/tests/calls/generic_applications.rs)

If a declaration owns a fact, test a legal declaration that never uses it. For example, `domain i32::Empty requires false;` still has a signed carrier even though its predicate never reads `self`. Pair it with the same predicate on `u32` and read each carrier from its own lowered declaration. This exposes a handoff that only works when a use happens to reveal the missing fact.

## When a later layer reaches back

Start at the open layer. Name the exact fact its consumer needs for one program and inspect the input the consumer actually receives. If the fact is present for the right occurrence and usable through the intended dependencies, fix the consumer and stop tracing backward. For example, L5 could read the typed Boolean in `data Never requires false {}` through L4. The repair was to retain it on L5’s data schema.

If the fact is missing or wrong, walk backward one handoff at a time. For each intervening layer, compare what enters with what its public output lets the next consumer read. Record the first point where the fact should exist and the point where it becomes unavailable or changes identity. If a prerequisite never enters the ordinary pipeline, name its supplier. Mark any boundary you could not exercise as unverified.

Run the complete program through the ordinary entry point. If the producer demands a value before it releases the facts its consumer needs to compute that value, show where the program stops. Compare it with a literal-value control. If a test supplies results up front, first inspect the pending requests from a run without those results. Assert the exact occurrence and argument tuples the evaluator must receive. In a fault-injection test, L3 accepted both supplied widths after its pending output lost one request. Then run the consumer on the original program. [Pending width requests](../../../layers/03_symbol-resolved-trees-to-typed-trees/tests/calls/generic_applications.rs)

| What the case shows | Who acts |
| --- | --- |
| The handoff supplies the information through the intended dependencies. | Fix the consumer to use it. |
| Using the handoff requires a type or service from an earlier implementation crate. | Name the public field or method that requires it. Decide who owns the information, then correct the public contract or document why that dependency belongs to the consumer. |
| The locked contract promises the information, but the producer loses or misstates it. | Fix the producer under its existing lock and test the handoff. |
| The requested information falls outside the locked contract. | Decide whether the open layer can derive it from facts it owns. If the evidence points to the earlier layer, bring the case forward for an explicit decision to reopen. |

One valid program can demonstrate information loss. Repeated workarounds can reveal a pattern, but repetition alone cannot establish ownership. For each proposed reopening, show what breaks, where the deciding facts first exist, which contract would change, and what its consumer would do with the revised output. When one producer gains a fact, check whether the next layer’s existing output already exposes it before proposing a second contract change. For example, if L3 publishes an assembly instruction’s implicit writes, the question for L4 is whether L5 can read those writes from the prepared package for that instruction. After an explicit reopening decision, apply the same design and test sequence to the revised boundary before locking it again.

## Sign-off

Apply the [layer-lock criteria](../../../PLAN.md#what-solid-means) to each disputed handoff. Start from the canonical spec clause and identify where the deciding information becomes available. In the sign-off, point to the producer and consumer assertions for a real use, an unrelated use, and a plausible substitution. Existing fixtures count when their assertions distinguish the cases. If the spec leaves ownership open, record the owner question. If an assertion is missing or contradicts the proposed ownership, record the open case before requesting a lock.

For each sign-off claim, name the deciding input and point to the assertion that checks the claimed result. A presence check supports a presence claim. An identity claim needs an assertion comparing the selected identity with the expected one. For the consumer dependency check, cite the consumer manifest and the operation exercised. State what remains unverified, including downstream behavior exercised only through a test consumer. Before calling the layer locked, check that the owner’s sign-off covers this handoff. Record the signed-off responsibility in `PLAN.md`, align the layer contract, and state which changes would require reopening it. Commit the agreed implementation, contract, and tests, then advance within the authorized scope.
