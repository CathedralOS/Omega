# Measure a layer decision

Start from a saved readiness report for the scoped layers. Record the revision, source fingerprint, case IDs and first stops. If the workspace differs from the baseline, retain the source and executable needed to replay the earlier result. Run the readiness command from the V2 junction on the integrated candidate. Compare the report directories using the existing tools.

```powershell
uv run --no-project python -B tools/spec-corpus/check_layer_readiness.py
uv run --no-project python -B tools/spec-corpus/compare_readiness.py BEFORE AFTER --verbose
```

Use the actual directories for BEFORE and AFTER. The readiness command returns a blocked verdict while known gaps remain. Read the suite exits, measurement errors, case results and outstanding sign-off obligations separately. Resolve incomplete measurements before crediting closures. The comparison command reports differences and can exit successfully even if the compiler regressed.

Match original case IDs across reports. For a claimed repair, replay the same source, dependencies and configuration. Check the original failure on the baseline and the required handoff or specified rejection on the candidate. For an additional blocking case, run its source on the baseline too. Record whether it already failed, regressed, or still lacks a comparable baseline. A disappearing case, a renamed test, a new control and a changed compiler result have different meanings. When the comparator confuses them, preserve the pair that exposed the mistake, fix the measurement and replay both reports.

For example, adding three selector fixtures increased the recorded set of byte spans. Replaying the four original sources confirmed the same refusal at each original span. A reporter can distinguish an added control by matching the source package, entry point, diagnostic and location for every original fixture. Cover both an added source and a changed location on the same source in the reporter test.

## Measuring whether samples improve

For a sample-quality pass, choose one spec rule and name the public decision the sample must distinguish. Before editing assertions, pin the baseline revision and write down a small set of plausible wrong outputs, a valid control, and the expected outcomes. When using an independent reviewer, have them reserve one additional challenge from that revision. Keep it private until the revised assertions are frozen. Run it once before adapting the tests to anything it reveals.

Give the old and revised assertions the same valid output and the same independently altered copies, including any checks their shared helpers perform. Verify that each alteration actually changed the product. Record which changes each version rejects for the expected reason. Count each distinct wrong decision once across spellings and call forms. Report the reserved result separately, including misses and zero gain. Record an unrepresentable alteration as unscored and label any later challenge as a separate experiment. Credit a compiler defect only when an ordinary source input produces the wrong output.

Strengthen an existing sample when its program already expresses the distinction. Retire a weaker sample when its replacement catches its faults at the same boundary and preserves useful failure localization. To check whether a gain repeats, select another rule before examining its failures and keep its denominator separate.

## Designing a discriminating check

Before sending the review prompts, have the coordinator set aside a plausible violation and a nearby lawful case for this handoff. Derive both from the contract and what the producer can emit. Write down the expected public results and keep the cases out of the prompts. Once the reviewers submit, run both through the consumer and record which failure, if any, the reviewers found independently. Keep these checks with the handoff they exercise.

Have the consumer reviewer list the facts the consumer relies on for the decision under review. For each fact, record the producer field or context that supplies it, a valid control, one change that would make the evidence wrong, and the expected public result. Include relationships between fields and who supplied the evidence. For example, a byte column can be positive and still be impossible at its byte offset. A diagnostic record can be valid yet belong to a different test or a previous run of the same target. To test attribution, keep the record intact and change only its surrounding context.

Run every proposed mutation and its control through the same consumer. Restore the valid input between mutations. Record the expected and observed result for each pair, including which fact lost credit and whether unaffected facts kept theirs. If the input cannot reveal the answer, name the independent evidence needed. For example, detecting a missing diagnostic record requires some independent indication that the producer returned a refusal. Leave that claim unverified until the evidence exists.

Keep an independent open review alongside the inventory. Give the equivalent-input reviewer the contract and producer output, and let them choose their own cases before sharing the inventory or other findings. At sign-off, combine the reproduced failures from both reviews and group them by the decision that needs repair. Use the ranked findings to order repairs after replaying the full inventory. Distinguish newly exposed defects, correctly rejected mutations, and cases the available evidence could not settle. A count of probes alone cannot establish coverage.

After a repair, rerun the original failing input and the nearest lawful edge case through the repaired consumer. Assert the required outcome for each. For example, an L5 diagnostic reader should reject a dependency record that claims a local source position. A local record for a zero-length span has a valid line and column and an empty excerpt. Require the reader to preserve that location and credit the valid record. A rule that requires every local excerpt to contain text would lose it.

For each decision that matters to the lock, ask “Could this test pass if the compiler made the wrong decision?” When two choices could satisfy a weak assertion, inject the plausible wrong choice into a temporary copy of the producer. For example, substitute a neighboring generic binder or attach a precondition to an identically spelled call. Observe which assertion fails and why. If the test stays green, strengthen it at the public handoff and repeat. Verify it passes against the actual producer before reporting the result. When testing several reasons to refuse one receipt, restore the accepted receipt between cases. For evidence tied to a generic constructor, hold the occurrence, fields and typing pass fixed and change only the closed application. [Construction evidence tests](../../../layers/04_typed-trees-to-prepared-trees/src/evaluation/owned_values/tests.rs)

Try swapping two valid identities while preserving their count and distinctness. Check which declaration belongs to each defining file or call. When the identities are opaque, obtain the expected one from a small control program that explicitly names the intended declaration and has no competitor. If the product publishes the same decision in two places, change one while leaving the other correct. For a nested operator, inspect both the machine and operator visibility in Psi. [Imported declarations](../../../layers/02_syntax-trees-to-symbol-resolved-trees/tests/signature_origins.rs) · [Operator visibility](../../../layers/05_prepared-trees-to-terminal-psi/tests/operators.rs)

When a handoff carries generic arguments, run the same source occurrence at two closed applications in one package. Swap the enclosing and local arguments and assert distinguishable answers. Exercise the value through a helper as well as directly. In L4 a direct layout query succeeded while a generic helper lost its caller’s type argument. [Nested layout regression](../../../layers/04_typed-trees-to-prepared-trees/tests/target_layout.rs)

Make the field or result named in the claim depend on the argument being varied. Two swapped operands can still produce the same set of result domains. Use an overload that selects just one operand and assert the defining file. A generic record can still have a fixed-type omitted field. Omit a field of type `[u8; N]` and check the prepared array at two concrete lengths. First run the new case with the unmodified compiler. A refusal at an earlier contract leaves the intended decision untested. [Result-domain selection](../../../layers/03_symbol-resolved-trees-to-typed-trees/tests/calls/result_domain_selection.rs) · [Omitted field](../../../layers/04_typed-trees-to-prepared-trees/tests/owned_records.rs)

When a rule requires preserving which input a value depends on, choose two different inputs that yield the same value. Follow each reference from its consumer to the exact input in the public output. Then swap which input each consumer uses. For example, size and alignment can both yield 8. The array shapes, set of observations and whole-package replay can all agree even if both constants point to alignment. The assertion that distinguishes the programs reads the projection attached to each constant.
