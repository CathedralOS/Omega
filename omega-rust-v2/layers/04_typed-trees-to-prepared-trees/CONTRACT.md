# L4 Preparation

L4 computes the values that typing and lowering need. It consumes L3's selected calls, typed operands, constant initializers and application arguments. Its frozen product carries the typed package, owned constants, closed static identities and the inputs that determined them. For example, a machine returning `3u64` can determine an array extent. Lowering can read the element type and count directly from the prepared signature. ## Typing and target closure

When preparation stops, its diagnosed entry point identifies the pass that refused the source. L3 can refuse during initial typing or after L4 returns a static value. For example, a computed array width can expose a mismatch only when L3 checks the resulting array type. Both passes retain the original type error and source span. A caller that steps through rounds, supplies a target later, or provides a resource grant receives the same phase and diagnostic. [Failure phases](tests/preparation_failure_phases.rs) · [Target closure](tests/target_layout.rs)

Every refusal L4 renders carries its typed cause. An owned cause is one `PreparationReason`, and `PreparationReason::ALL` lists them all. The target contract's layout refusals and the shared integer primitive's refusals keep their owner's text and are marked as forwarded. Typing refusals have no preparation cause. Most reasons follow the admission prefix and may end with a call chain or recursive component. An unsupported floating operation and an assembly target mismatch are rendered without the prefix. [Reasons](src/reasons.rs) · [Observed reasons](tests/preparation_reasons.rs)

L3 publishes the operations ready to evaluate. L4 returns an answer for the exact source occurrence and enclosing arguments. L3 uses those answers to finish overload selection and check type identities. One field recipe can therefore yield different identities for two closed applications. The public preparation round accepts checked evidence for its immutable typing pass and collects each result into the same frozen product as ordinary source preparation. [Preparation rounds](src/preparation/mod.rs) · [Pass results](src/preparation/typing_pass.rs)

A specialized field request carries the declarations that own its arguments, in order from the enclosing declaration to the field’s immediate owner. Preparation uses those bindings when a field initializer calls a generic helper. A typed constructor uses the closed result type to prepare its fields. Pattern bindings in a constant initializer remain available until the selected arm finishes, including inside nested calls. [Nested layout query](tests/target_layout.rs) · [Record construction](tests/owned_records.rs) · [Constant matches](tests/boolean_calls.rs)

When a public type depends on an unselected target, the open package carries the provisional typed forest, pending requests, settled answers and their dependencies. Selecting a target resumes these requests. If the source package selected an instruction catalog, preparation requires any supplied layout target to have the same identity, including its realization. An otherwise complete package can retain an open constant's typed initializer. L4 takes `size_of<T>()` and `align_of<T>()` from the selected layout for exactly `T`. A dynamic extent can still have known alignment. A checker receipt can also record the exclusive bound of an address space, the endianness of a selected layout or the stack guarantee of a selected entry profile. These typed inputs retain their exact subjects and versions. [Layout tests](tests/target_layout.rs) · [Layout queries](../../../wiki/spec/layouts/plans.md#size-and-alignment-queries)

## Invocation admission

L4 specializes the selected body's published effects and checks the obligations for the actual operands. It rejects runtime service reach, suspension, blocking, escaping mutation and unhandled crash routes. A private scalar local can change inside the invocation. Preconditions and crash guards run before the body, and postconditions check its result. Proofs supplied by the checker must identify the typed occurrence, body, concrete application and the operands or result they justify. A changed target plan invalidates dependent proofs even when the value is unchanged. [Calls and contracts](src/invocation/admission.rs) · [Boolean calls](tests/boolean_calls.rs) · [Invocation admission](../../../wiki/spec/language/evaluation.md#invocation-admission)

A static callback selects an ordinary machine at a closed application. When a caller forwards a bounded callback, preparation follows the typed formal back to the application that selected the machine and checks its refinement there. A callback reached through a contract carries the refinement from the call that selected it, including when a short-circuited predicate skips that call. Each invocation still needs any evidence required by the bound for its actual operands. The selected body must satisfy its own contract. A provider selected for an outbound boundary needs the checked requirement-to-implementation mapping and the matching target selection. Preparation considers each candidate proof against the selected target. A stale proof can precede a valid proof for the same call. The package records the proof dependencies and selected realization even when the implementation returns a literal. [Static callbacks](tests/static_callbacks.rs) · [Provider evidence](src/invocation/admission/providers.rs)

An explicit discard evaluates its operand before continuing. A discarded constant read still contributes a dependency, and a failed precondition still refuses preparation. The evaluator can dispose of a copyable value whose complete type has no cleanup obligation. [Discard tests](tests/boolean_calls.rs)

A local declaration after a tail expression or transition contributes no execution step. A nested helper receives its enclosing static arguments both when called directly and when another machine invokes it as a callback. Before executing the callback, preparation checks the selected machines it may invoke, including callbacks it inherits from its enclosing machine. Preparation uses the resolved export status when deciding whether a machine needs a published termination promise. Acyclic local calls can establish termination from their closed call graph. For example, `apply::<apply::<bump>>` reaches `bump` after two calls. Preparation distinguishes those active applications and checks for a return to the same selection. A recursive component requires a checked ranking covering the actual members, specializations and internal calls. L4 validates the certificate's applicability at entry, including when the invocation will take the base case. Tests supply a single countdown, a two-machine cycle with one rank-preserving edge, and two independent recursive groups. [Termination tests](src/invocation/termination/tests.rs) · [Termination and sponsorship](../../../wiki/spec/language/evaluation.md#termination-and-sponsorship)

A bounded preparation compares a certified ceiling for the exact inputs with the root's grant before evaluating any demand. Work and peak live cells must each fit. The frozen package retains the grant, checked subject, work-schedule version and certified maxima. The checker owns the judgment establishing those maxima. [Sponsorship](src/preparation/sponsorship.rs) · [Logical work](../../../wiki/spec/resources/logical_work.md)

## Frozen values and reuse

L4 evaluates integers, Booleans, floating-point values, fixed arrays, tuples, records and sum cases. It walks the complete type for copy eligibility, including inactive payloads, and stores the active record or case fields in declaration order. The target selects floating operations. An unspecified NaN can survive evaluation, but materializing it reports the active component and its producer. A constrained construction and a canonical type index require separate judgments. [Frozen values](src/evaluation/owned_values.rs) · [Record tests](tests/owned_records.rs) · [Float tests](tests/owned_floats.rs) · [Constants](../../../wiki/spec/language/constants.md)

Named reads connect each prepared constant or static index to the constants it consumed. A target observation identifies the subject, projection and selected plan or realization. A provider that returns a literal still depends on its selection. A materialization request checks the package's recorded observations under the given target, then pairs the value with the selected layout for its declared carrier. The receiving layer owns field placement and byte emission. ## Evidence at the layer boundary

The L4 handoff was signed off on 2026-11-19 after the 151 preparation tests passed. The preparation tests supply checked judgments bound to an actual typed forest. They exercise successful and refused outcomes through the public preparation round. In the ordinary source command, the absence of a required judgment produces a refusal. Producing portable checker certificates, selecting validated target plans in Build, and emitting a Psi or native program are separate integration milestones. [Preparation evidence](src/preparation/typing_pass.rs) · [Sponsored recursive invocation](src/preparation/sponsorship.rs) · [Callable contracts](src/invocation/static_callbacks.rs)

`omega source prepare <files>` reports typing or evaluation refusals at their source locations. The producer and consumer tests run directly against the V2 preparation crate. The [spec corpus test](tests/spec_corpus.rs) reports which published fragments it covers.
