# L4 Preparation

L4 computes the values that typing and lowering need. It consumes L3's selected calls, typed operands, constant initializers and application arguments. Its frozen product carries the typed package, owned constants, closed static identities and the inputs that determined them. For a domain access policy on a compiler-owned scalar, L4 prepares the core TypeSchema record when Build supplies the requesting package’s key. Its shared byte view owns the version 2 schema image. The prepared demand distinguishes a missing package owner, an unsupported subject and a ready argument. The compiler driver projects the ready construction from these trees and compares every field with the checker’s retained inputs. The prepared product records the match against the Build owner, schema image and revision, selection and constructor sites, and original frozen occurrence. Checked construction still leaves policy execution pending. [Schema handoff](tests/frozen_handoff.rs) At publication, `read_returned_access_plan` checks the value from the executed policy against this domain’s frozen invocation. The plan's schema must be the same allocation as the schema argument, because an equal copy lives in another region. The issuance case decides who may introduce the domain: `Unrestricted` adds no restriction, and `Only` with no routes admits nobody. Validation refuses a plan it cannot judge completely: `Only` with routes, any field, reader or writer rule, any boundary reach, a count that disagrees with its slots, and an occurrence from another preparation. A refused plan leaves the domain pending. Preparation executes no policy itself: the caller that ran the policy supplies its return. [Validation](src/evaluation/policy_validation.rs) · [Validation tests](tests/access_plan_validation.rs) For example, a machine returning `3u64` can determine an array extent. Lowering can read the element type and count directly from the prepared signature. [Prepared representation](../../representations/prepared/src/lib.rs) · [Frozen handoff](tests/frozen_handoff.rs) · [Fixed-array consumer](tests/closed_indices.rs)

L3 supplies the exact operands of a wholly anonymous numeric comparison. L4 compares them as rationals and publishes the Boolean at the operation in its defining forest. Constant evaluation uses the same rule. [Preparation tests](tests/owned_floats.rs)

## Typing and target closure

When preparation stops, its diagnosed entry point identifies the pass that refused the source. L3 can refuse during initial typing or after L4 returns a static value. For example, a computed array width can expose a mismatch only when L3 checks the resulting array type. Both passes retain the original type error and source span. A caller that steps through rounds, supplies a target later, or provides a resource grant receives the same phase and diagnostic. [Failure phases](tests/preparation_failure_phases.rs) · [Target closure](tests/target_layout.rs)

Every refusal L4 renders carries its typed cause. An owned cause is one `PreparationReason`, and `PreparationReason::ALL` lists them all. The target contract's layout refusals and the shared integer primitive's refusals keep their owner's text and are marked as forwarded. Typing refusals have no preparation cause. An invocation refusal identifies the selected call even inside a larger initializer. A cyclic constant initializer identifies the read that closes the cycle, including its defining source file. A constant read identifies its source occurrence when its selection is ambiguous, its definition is missing or its carrier disagrees with the definition. Most reasons follow the admission prefix and may end with a call chain or recursive component. An unsupported floating operation and an assembly target mismatch are rendered without the prefix. [Reasons](src/reasons.rs) · [Observed reasons](tests/preparation_reasons.rs)

Preparation indexes each named constant by its declaration. Before storing a frozen value, it checks that the typed initializer belongs to that declaration and that the declaration occurs once. This prevents a second initializer from changing what a later read of the constant returns. For arithmetic in a direct initializer, the diagnostic highlights the operation that failed. In `1 + (BASE + 1)`, either addition can overflow depending on the value of `BASE`. [Constant identity tests](tests/owned_records/static_values.rs) · [Arithmetic location tests](tests/integer_constants/selected_rule.rs)

L3 publishes the operations ready to evaluate. L4 returns an answer for the exact source occurrence and enclosing arguments. L3 uses those answers to finish overload selection and check type identities. One field recipe can therefore yield different identities for two closed applications. The public preparation round accepts checked evidence for its immutable typing pass and collects each result into the same frozen product as ordinary source preparation. [Preparation rounds](src/preparation/rounds.rs) · [Pass results](src/preparation/typing_pass.rs)

A specialized field request carries the declarations that own its arguments, in order from the enclosing declaration to the field’s immediate owner. Preparation uses those bindings when a field initializer calls a generic helper. A typed constructor uses the closed result type to prepare its fields. Pattern bindings in a constant initializer remain available until the selected arm finishes, including inside nested calls. [Nested layout query](tests/target_layout.rs) · [Record construction](tests/owned_records.rs) · [Constant matches](tests/boolean_calls.rs)

When a public type depends on an unselected target, the open package carries the provisional typed forest, pending requests, settled answers and their dependencies. Selecting a target resumes these requests. `close` runs the remaining rounds without evidence. `resume` hands the caller an ordinary round under the target, so it can supply checked evidence for each resumed forest and reach the same product as stepping from the start. If the source package selected an instruction catalog, preparation requires any supplied layout target to have the same identity, including its realization. An otherwise complete package can retain an open constant's typed initializer. L4 takes `size_of<T>()` and `align_of<T>()` from the selected layout for exactly `T`. A query on a closed type without runtime storage carries the target contract’s refusal even before target selection. A runtime callable with finite service and crash ceilings can receive a descriptor layout from the target. A dynamic extent can still have known alignment. A checker receipt can also record the exclusive bound of an address space, the endianness of a selected layout or the stack guarantee of a selected entry profile. These typed inputs retain their exact subjects and versions. [Layout tests](tests/target_layout.rs) · [Layout queries](../../../wiki/spec/layouts/plans.md#size-and-alignment-queries)

## Invocation admission

L4 specializes the selected body's published effects and checks the obligations for the actual operands. It rejects runtime service reach, suspension, blocking, escaping mutation and unhandled crash routes. A private scalar local can change inside the invocation. Preconditions and crash guards run before the body, and postconditions check its result. [Calls and contracts](src/invocation/admission.rs) · [Boolean calls](tests/boolean_calls.rs)

Proofs supplied by the checker must identify the typed occurrence, body, concrete application and the operands or result they justify. A changed target plan invalidates dependent proofs even when the value is unchanged. Before a target is selected, such a proof neither applies nor counts as stale. Its demand reports missing target input, and a constant keeps its typed initializer for a later target. This applies to invocation facts, termination components, checked providers, callable judgments, data establishment and canonical identity. Without a checked provider, a boundary slot stays unselected whether or not a target is present. [Checked invocation proofs](src/invocation/admission/proofs/contract_tests.rs) · [Invocation admission](../../../wiki/spec/language/evaluation.md#invocation-admission)

A static callback selects an ordinary machine at a closed application. When a caller forwards a bounded callback, preparation follows the typed formal back to the application that selected the machine and checks its refinement there. A callback reached through a contract carries the refinement from the call that selected it, including when a short-circuited predicate skips that call. Each invocation still needs any evidence required by the bound for its actual operands. The selected body must satisfy its own contract. A provider selected for an outbound boundary needs the checked requirement-to-implementation mapping and the matching target selection. Preparation considers each candidate proof against the selected target. A stale proof can precede a valid proof for the same call. The package records the proof dependencies and selected realization even when the implementation returns a literal. [Static callbacks](tests/static_callbacks.rs) · [Provider evidence](src/invocation/admission/providers.rs)

A specialized initializer may invoke the exact machine in the slot named by its typed indirect call. The closed tuple is not a selecting call occurrence and supplies no refinement or callable-use judgment. Preparation checks the specialized callable contract, including the selected machine’s published crash bound, and admits the body normally. A missing judgment remains a refinement refusal even when the owner arguments are complete. [Specialized width tests](tests/static_callbacks/closure.rs)

An explicit discard evaluates its operand before continuing. A discarded constant read still contributes a dependency, and a failed precondition still refuses preparation. The evaluator can dispose of a copyable value whose complete type has no cleanup obligation. [Discard tests](tests/boolean_calls.rs)

A local declaration after a tail expression or transition contributes no execution step. A nested helper receives its enclosing static arguments both when called directly and when another machine invokes it as a callback. Before executing the callback, preparation checks the selected machines it may invoke, including callbacks it inherits from its enclosing machine. Preparation uses the resolved export status when deciding whether a machine needs a published termination promise. Acyclic local calls can establish termination from their closed call graph. For example, `apply::<apply::<bump>>` reaches `bump` after two calls. Preparation distinguishes those active applications and checks for a return to the same selection. A recursive component requires a checked ranking covering the actual members, specializations and internal calls. L4 validates the certificate's applicability at entry, including when the invocation will take the base case. Tests supply a single countdown, a two-machine cycle with one rank-preserving edge, and two independent recursive groups. [Termination tests](src/invocation/termination/tests.rs) · [Termination and sponsorship](../../../wiki/spec/language/evaluation.md#termination-and-sponsorship)

A bounded preparation compares a certified ceiling for the exact inputs with the root's grant before evaluating any demand. Work and peak live cells must each fit. The frozen package retains the grant, checked subject, work-schedule version and certified maxima. The checker owns the judgment establishing those maxima. A build report that links only the prepared product lists the grant and ceiling beside the frozen values of the constants a build names by declaration identity, package included. A larger grant or a reissued ceiling changes the admission record, not those values. Equal values do not identify a result: a literal and a countdown both freeze `VALUE` as 7. It distinguishes an unsponsored package from a zero ceiling and rejects a receipt checked for another subject. The receipt records a ceiling, not work used. Lowering does not read it, and no published build retains it until publication exists. [Sponsorship](src/preparation/sponsorship.rs) · [Build report](../05_prepared-trees-to-terminal-psi/tests/tree-consumer/src/resource_report.rs) · [Logical work](../../../wiki/spec/resources/logical_work.md)

## Frozen values and reuse

When preparation reads a closed aggregate argument, it checks the supplied value against its concrete type as it builds the prepared value. The length of an array, the owner and active case, and each field’s type come from the typing handoff. If the first field of a record holds 256 where it requires a `u8`, preparation refuses at the argument occurrence. This applies even when the machine returns the whole record or reads only its second field. The machine’s preconditions still apply to a value that fits. [Closed argument tests](tests/owned_records/value_witness.rs)

L4 evaluates integers, Booleans, floating-point values, fixed arrays, tuples, records and sum cases. It walks the complete type for copy eligibility, including inactive payloads, and stores the active record or case fields in declaration order. The target selects floating operations. An unspecified NaN can survive evaluation, but materializing it reports the active component and its producer. Preparation also lands every float literal that typing recorded, including those in runtime bodies, and publishes its rounded bits for lowering; landing needs no target. A constrained construction and a canonical type index require separate judgments. [Frozen values](src/evaluation/owned_values.rs) · [Record tests](tests/owned_records.rs) · [Float tests](tests/owned_floats.rs) · [Constants](../../../wiki/spec/language/constants.md)

An evaluation request identifies its expression by forest node and source site. Preparation checks that the file, node and source site agree before it freezes a value. A record or case construction schedules its own field initializers in authored order and writes each result to its selected field position once. When a nested literal requests a zero that preparation cannot supply, the diagnostic points to that literal.

Named reads connect each prepared constant or static index to the constants it consumed. A target observation identifies the subject, projection and selected plan or realization. A provider that returns a literal still depends on its selection. A materialization request checks the package's recorded observations under the given target, then pairs the value with the selected layout for its declared carrier. The receiving layer owns field placement and byte emission. [Dependencies](../../representations/prepared/src/dependencies.rs) · [Materialization](../../representations/prepared/src/materialization.rs) · [Target-dependent applications](../../../wiki/spec/language/evaluation.md#target-dependent-applications)

## Evidence at the layer boundary

The L4 handoff was signed off on 2026-11-19 after the 151 preparation tests passed. The preparation tests supply checked judgments bound to an actual typed forest. They exercise successful and refused outcomes through the public preparation round. In the ordinary source command, the absence of a required judgment produces a refusal. Producing portable checker certificates, selecting validated target plans in Build, and emitting a Psi or native program are separate integration milestones. [Preparation evidence](src/preparation/typing_pass.rs) · [Sponsored recursive invocation](src/preparation/sponsorship.rs) · [Callable contracts](src/invocation/static_callbacks.rs)

`omega source prepare <files>` reports typing or evaluation refusals at their source locations. The producer and consumer tests run directly against the V2 preparation crate. The [spec corpus test](tests/spec_corpus.rs) reports which published fragments it covers.
